# ADR-0019: 履歴への秘密の混入を独立した検証レイヤーとして扱う

- Status: Accepted
- Date: 2026-09-16
- Scope: repository-wide
- Related: ADR-0011, ADR-0012, ADR-0013, ADR-0016, ADR-0017

## Context

ADR-0013 決定4 が割り当てた道具は、いずれもTerraformコードの誤りを対象としている。リポジトリの履歴に秘密が入ることは、そのどれとも異なる故障モードであり、現在どの道具も担当していない。

Terraformリポジトリでこの経路が開くのは、設計の結果ではなく事故としてである。

- `terraform.tfstate` の誤コミット。stateは sensitive な値を平文で保持するため、1度の混入で全量が漏れる
- `*.tfvars` へ書いた接続情報や資格情報
- backend設定・provider設定への資格情報の直書き
- `terraform show` や plan の出力を貼り付けたファイル

ADR-0017 決定12 が長期のアクセスキーをCIから排除し、ADR-0006 決定4 が任意のJSON入力を禁じていることで、**設計に沿って書く限り**秘密がコードへ入る経路は狭い。しかし混入は設計の外で起きる。設計が狭めたのは意図的な経路であって、事故の経路ではない。

さらに、一度混入した秘密はファイルを削除しても履歴に残る。ADR-0013 決定4 のSecurityレイヤー（Trivy）が走査するのは作業ツリーのファイルであり、削除済みの過去のcommitは対象外である。**検出できる期間が、混入から削除までに限られる道具しか持っていない。**

本リポジトリはボイラープレートである。秘密を貼り付けるのはテンプレートを利用する側であり、この検出はテンプレートに含まれていなければ利用者へ届かない。

## Decision

### レイヤーの追加

1. 「リポジトリの履歴への秘密の混入」を独立した故障モードとし、ADR-0013 決定4 のレイヤー表へ次を加える。

   | レイヤー | 道具 | 実AWS |
   | --- | --- | --- |
   | Secret Scan | gitleaks（走査対象はcommitと履歴） | 不要 |

2. 本レイヤーの権威をgitleaksとする。Trivyのsecret scanningは無効化し、Trivyはmisconfigurationの走査に限定する。ADR-0016 決定3（1つの検査に権威は1つ）の適用である。
3. 本レイヤーはTerraformコードの正しさを検証しない。したがって `modules/` 配下に限らず、リポジトリ全体を対象とする。

### fail-closed

4. 検出時は通さない。報告のみを行い通過させる構成を採らない。
5. 秘密の検出を、ADR-0013 決定14（検査を無条件にskipしない）の適用対象とする。開発やテストを容易にする目的での無効化を認めない。

### 実行の契機と範囲

6. 実行契機ごとの走査範囲を次とする。

   | 契機 | 範囲 |
   | --- | --- |
   | Pull Request | base から HEAD までのcommit範囲 |
   | 定期実行 | 全履歴 |
   | ローカル（hookレイヤー導入後） | pushしようとしているcommit範囲 |

7. ローカルのhookはfast feedbackであり、強制はCIが持つ（ADR-0013 決定26）。hookレイヤーの導入前は、CIのみで本レイヤーが成立する。
8. 定期実行で全履歴を対象とするのは、検出ルールの更新によって、過去のcommitが後から検出対象になるためである。Pull Request契機の差分走査だけでは、ルール更新前に入った秘密を発見できない。

### 抑止

9. 抑止はADR-0013 決定13 に従う。単位はfingerprint（path + rule + 行）またはpathとし、ルールやスキャナ単位の無効化を認めない。
10. 各エントリに「なぜ秘密でないか」を記述する。理由を書けないものは抑止せず、値そのものを消す。

### 検出後の扱い

11. 秘密の混入を検出した場合、**第一手を当該資格情報の失効（rotate）とする。** 履歴からの除去を第一手としない。
12. 決定11 の理由は、履歴を書き換えても、当該commitがpush済みであれば漏洩の事実は取り消せないことにある。除去は露出の継続を止めるが、既に起きた露出を無効化しない。失効のみがそれを行う。
13. 履歴の書き換えは、失効とは独立した判断とする。実行は人の決定による（AGENTS.md のトリップワイヤ）。エージェントが自らの判断で履歴を書き換えない。
14. 防止と検出を混同しない。`.gitignore` によるstateの非追跡は防止であり、本レイヤーは防止が破れたことの検出である。防止があることを理由に検出を省かない。

## 検討した代替案

### 案A: Trivyのsecret scanningで代替する

道具が増えない。ただし走査対象が作業ツリーのファイルであるため、削除済みのcommitに残る秘密を検出できない。検出可能な期間が混入から削除までに限られ、最も危険な状態（削除されたが履歴に残る）が対象外になる。

### 案B: 検出するが通過させ、報告のみとする

導入時の摩擦が小さい。ただし秘密の混入は、他の検査結果と異なり時間の経過で悪化する（pushされた時点で露出が始まる）。報告を後追いで処理する運用は、露出時間をそのまま延ばす。

### 案C: GitHubのsecret scanning機能に委ねる

追加の配線が不要で、既知のprovider形式に対する精度も高い。ただし検出はpush後であり、混入を止められない。また対象となるパターンはプラットフォーム側が決めるため、本リポジトリ固有の値（backend設定、tfvars の慣習的なキー名）を対象に含められない。併用は妨げないが、本レイヤーの代替としない。

### 評価

| 評価軸 | 案A: Trivyで代替 | 案B: 報告のみ | 案C: プラットフォームに委譲 | 採用案: gitleaksでfail-closed |
| --- | --- | --- | --- | --- |
| Security | 低（履歴が対象外） | 低（露出時間が延びる） | 中（push後の検出） | 高 |
| Testability | 中 | 中 | 低（検出条件を制御できない） | 高 |
| Contract Clarity | 中 | 中 | 中 | 高（権威が1つ） |
| Scope Control | 高（道具が増えない） | 中 | 高 | 中（道具が1つ増える） |
| 導入時の摩擦 | 低 | 低 | 低 | 高（意図的） |

## 意図的に捨てるもの

- 道具の総数を初期導入の範囲に留めること
- 誤検知が出た際に、その場で通過させる手段
- 検出を後追いで処理する運用

## 保証範囲

- 保証すること: 検出ルールが対象とする形式の秘密について、Pull Requestの範囲で混入を止めること。ルール更新後に過去のcommitを再評価すること
- 保証しないこと: 検出ルールが対象としない形式の秘密の検出。既にpushされた秘密の露出が無かったことにできること

## 検証方法

- Static Analysis: Secret Scanのジョブが存在し、失敗時にPull Requestを通さない設定であること（決定4）
- Static Analysis: Trivyの実行にsecret scannerが含まれていないこと（決定2）
- Static Analysis: 抑止エントリがfingerprintまたはpath単位であり、理由を伴うこと（決定9・10）
- Static Analysis: 定期実行のジョブが全履歴を対象としていること（決定6・8）

## 影響

- ADR-0013 決定4 のレイヤー表に1行が加わり、pinする道具が1つ増える（同 決定19）。
- Trivyの実行にscannerの指定が必要になる。
- 秘密の混入が検出された場合、対応の起点は資格情報の失効になる。履歴の書き換えは、それとは別に判断される。

## 見直し条件

- 混入の検出がゼロのまま推移し、定期実行の全履歴走査が費用に見合わなくなった場合
- gitleaksが保守されなくなった場合
- Terraformが、stateおよびplanに sensitive な値を平文で含めない構成を標準とした場合
