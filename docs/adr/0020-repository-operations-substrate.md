# ADR-0020: リポジトリ運用機構を独立した区分とし、Goで実装する

- Status: Accepted
- Date: 2026-09-16
- Scope: repository-wide
- Related: ADR-0001, ADR-0012, ADR-0013, ADR-0016, ADR-0019, ADR-0021

## Context

ADR-0013 決定4 は、Terraformコードの故障モードごとに道具を割り当てた。しかしその表が扱わない検査対象が存在し、いずれも現在は所有者を持たない。

- ADRの構造（ADR-0001 検証方法が要求するファイル名規約、メタデータの存在、`Superseded by` の参照先の実在）
- CI定義そのもの（workflow、composite action、それらが起動する条件）
- 依存の固定（`uses:` の参照先、container image、ツールのversion）
- ブランチ運用（起点の解決、リリース線の表現）
- 保護設定の宣言と実態の突合（ADR-0021）
- CI からの outbound 通信の制限

これらはTerraformコードの正しさではなく、**リポジトリ自身の構造と運用**についての検査である。ADR-0013 決定4 の表へ足すのは筋が悪い。同表は「Terraformコードのどの故障モードを誰が検出するか」を述べており、対象が違う。

一方、これらを放置すると、ADR-0001 が自ら定めた検証方法が実行されないまま残る。ADR-0012 決定3 は検証できない決定を不完全とみなすが、**決定の側ではなく検査器の側が不在**という形で同じ状態が生じている。

既製品で覆える範囲もある（workflowの構文検査、template injection の検出、秘密の検出）。しかし本リポジトリ固有の宣言を入力とする検査（ruleset の宣言と実態の突合、固定の drift 検出、ADRの構造）には、既製品が存在しない。ADR-0013 決定3 の3条件のうち第1条件（既存ツールで実現できない）を満たす領域がここに限って存在する。

したがって、自前実装を置くための区分と、その実装言語、そして検査器自身が守るべき規律を決める必要がある。**検査器の故障は、エラーではなく「緑」として現れる**ため、規律を後回しにすると、動いていない検査が動いているように見える状態が残る。

## Decision

### 区分

1. 「リポジトリ運用機構」を、ADR-0013 決定4 のレイヤーとは独立した区分として定義する。対象は、Terraformコードの正しさではなく、リポジトリ自身の構造・CI定義・依存の固定・ブランチ運用・保護設定・outbound 制限を検査または適用するものとする。
2. 本区分はADR-0013 決定4 の表を変更しない。Terraformコードの検証の権威は同表が持ち続ける。運用機構が同表のレイヤーを代替または補完しない。

### 境界

3. 運用機構を `terraform` の実行経路へ入れない。`terraform fmt` / `validate` / `test` / `plan` / `apply` は、運用機構が1つも動作しない状態で成功しなければならない。
4. 決定3 の理由は、運用機構の故障がインフラの操作不能を意味しない状態を保つことにある。障害対応で必要になるのは apply であって lint ではない。
5. 運用機構をCIの必須検査に含めてよい。決定3 が禁じるのは実行経路への挿入であって、ゲートとしての採用ではない。両者を混同しない。

### 実装言語

6. 実装言語をGoとする。
7. 理由は、ADR-0013 決定32 がTerratestを次段階の導入対象としており、**Goはいずれ本リポジトリへ入るため**である。運用機構をGoで書けば言語ランタイムは増えない。他の言語を採ると純増になる。ADR-0008 決定6 が依存管理の対象をproviderとTerraform本体に寄せている方針と整合する。
8. 既製の単一バイナリで足りるものを自前実装しない。ADR-0013 決定3 の3条件を本区分にも適用する。
9. 少なくとも次は既製品を用いる。自前実装の対象としない。

   - workflow の構文および `run:` のシェル検査
   - template injection の検出
   - 秘密の検出（ADR-0019 決定1）

### 形

10. 宣言を1箇所に置き、適用がそれを各所へ書き込み、検査が drift で落ちる形を採る。同じ値を複数箇所へ直接記述しない。
11. **検査は適用と同じ判定を、書き換えなしで実行する。** 検査と適用を別実装にしない。別実装は、検査を通るが適用で壊れる状態、およびその逆を生む。
12. 可能な場合、宣言そのものを検査の入力とする。宣言と検査が同じ記述を読む構造を優先する。

### 検査の規律

13. **検査対象が0件の場合、成功として終了しない。** 非ゼロで終了する。「ゲートが外れた」と「合格した」を区別できない状態を作らない。
14. **解釈できない入力は、取りこぼしではなくエラーとして扱う。** 検査が黙って対象範囲を縮めることを許さない。
15. 抽出を伴う検査は、抽出した件数を独立した経路で得た件数と突き合わせる。片方の経路が壊れたときに件数差として現れる形にする。
16. **検査ロジックを entry point から分離し、テストを持つ。** 検査器が検査をやめたとき、報告されるのはエラーではなく緑であるため、検査器自身の検証を省略できない。ADR-0016 決定7-9 がPolicyに対して要求していることを、本区分の全機構へ適用する。
17. テストのフィクスチャは一時ディレクトリへ構築する。リポジトリの実物を入力にしない。実物を読むテストは、リポジトリの今日の内容によって通ったり落ちたりするようになり、機構についてのテストであることをやめる。
18. 検査を迂回する宣言（バイパス）を設ける場合、次をすべて満たす。

    - 期限を必須とする。期限の無いバイパスを認めない
    - 期限の上限を、宣言した時点から3ヶ月とする。遠い将来の期限は恒久的な許可と区別できない
    - 期限切れ、上限超過、および**対象が存在しないエントリ**は、ゲートを落とす
    - **期限は宣言が変わらなくても訪れるため、この検査を定期実行にも載せる。** Pull Request契機のみでは期限切れを誰も踏まない

19. 本区分の検査もADR-0013 決定26 に従い、権威をCIに置く。ローカルのhookは迂回される前提で設計し、**hookでのみ成立する検査を作らない**。

## 検討した代替案

### 案A: TypeScriptで実装する

YAML・TOML・JSONの取り扱いに不足はなく、記述量も小さい。ただし本リポジトリはNode.jsのランタイムを持たず、これを採ると言語ランタイムが純増1になる。Terratest導入時にGoも入るため、最終的に2つを抱えることになる。検査の内容にTypeScript固有の要求は無く、純増を正当化する根拠が見当たらない。

### 案B: シェルスクリプトで実装する

追加のランタイムが不要で、CI上の起動も速い。ただし本区分の検査はYAML・TOML・JSONの構造を読む処理が中心であり、シェルでは外部コマンドの連鎖になる。決定16（検査ロジックの分離とテスト）を満たす形にしにくく、決定14（解釈できない入力をエラーとする）の実装も脆くなる。

### 案C: 運用機構を持たず、既製品で覆える範囲に限る

実装資産が増えない。ただしADR-0001 が自ら定めた検証方法、ruleset の宣言と実態の突合、固定の drift 検出は、いずれも本リポジトリ固有の宣言を入力とするため既製品が存在しない。結果としてADR-0012 決定3 の状態（検査器が不在のまま規範だけが残る）が継続する。

### 評価

| 評価軸 | 案A: TypeScript | 案B: シェル | 案C: 持たない | 採用案: Go |
| --- | --- | --- | --- | --- |
| Security | 中 | 中 | 低（宣言と実態がずれ続ける） | 高 |
| Testability | 中 | 低（分離しにくい） | 低（検査器が不在） | 高 |
| Contract Clarity | 中 | 中 | 低 | 高 |
| Scope Control | 低（ランタイムが純増） | 高 | 高 | 中（既に来る言語に寄せる） |
| Maintainability | 中 | 低 | 高 | 中 |

## 意図的に捨てるもの

- 運用機構を持たないことによる実装資産の少なさ
- 検査の記述量を最小にすること
- ローカルのhookだけで完結する運用

## 保証範囲

- 保証すること: 運用機構が動作しない状態でも `terraform` の各コマンドが成功すること。配線された運用機構がテストを持つこと。検査が対象を持たないまま成功を報告しないこと
- 保証しないこと: 運用機構が検出しない構造上の誤りが存在しないこと

## 検証方法

- Static Analysis: `terraform` を実行する経路に運用機構が含まれないこと（決定3）
- Static Analysis: 各運用機構にテストが存在すること（決定16）
- 各機構のテスト: 対象0件の入力に対して非ゼロで終了すること（決定13）
- 各機構のテスト: 解釈できない入力に対してエラーを返すこと（決定14）
- 定期実行: バイパス宣言の期限検査が、Pull Request契機とは独立に実行されること（決定18）
- レビュー: 決定8・9（既製品で足りるものを自前実装しない）は機械判定できない。運用機構を追加するPull Requestのレビュー観点とする

## 影響

- 本リポジトリはGoのツールチェーンを持つことになる。versionはADR-0013 決定19 に従い pin する。
- ADR-0001 の検証方法に、初めて実行者が与えられる。
- 運用機構を追加するたびに、その機構自身のテストが必要になる。

## 見直し条件

- Terratestの導入が見送られ、Goが本リポジトリへ入る理由が運用機構だけになった場合
- 本区分の検査を覆う既製品が現れた場合
- 運用機構の規模が、単一の言語とディレクトリでは管理できなくなった場合
