# ADR-0021: 保護設定を宣言と実態の突合で管理し、required checkの基準を定める

- Status: Accepted
- Date: 2026-09-16
- Scope: repository-wide
- Related: ADR-0012, ADR-0013, ADR-0014, ADR-0019, ADR-0020

## Context

保護設定（ruleset）はGitHubのサーバ側が保持する状態であり、リポジトリ内のファイルではない。宣言をリポジトリへ置いても、それだけでは実態と一致する保証がない。初期化時に1度だけ適用して以後放置する形を採ると、次のいずれでも**兆候なくずれる**。

- Web UIから設定が外された
- 宣言を変更したが適用を忘れた
- 適用が部分的に失敗した

この状態の宣言が答えるのは「何を強制するつもりか」であって「何を強制しているか」ではない。読み手は前者を後者と読む。

required status check には、機構として2つの落とし穴がある。

1. `pull_request` トリガーに `paths:` や `branches:` のフィルタを置くと、除外されたPull Requestではrunが**1件も起動しない**。GitHubは報告されなかった context を「該当しない」とは解釈せず、報告を待ち続ける。そのPull Requestは**恒久的にマージ可能にならない**。
2. requiredに入れる対象の基準が無いと、変更が持ち込んでいない事象（既知の脆弱性、継承した状態）で赤が出て、Pull Requestが人質になる。

さらに本リポジトリには固有の事情がある。ADR-0014 決定4 によりmergeがapplyを起動するため、**requiredの集合が実質的にデプロイのゲートになる**。requiredの選定が、通常のリポジトリより重い判断になる。

## Decision

### 宣言と実態

1. 保護設定を宣言としてリポジトリへ置き、適用は宣言から行う。加えて、**実態と宣言を突き合わせる検査を持つ**（ADR-0020 決定10-12）。
2. 一方向の適用にしない。初期化時に1度適用して以後突合しない形を採らない。
3. 実態の取得には通常の読み取り権限で到達できる手段を用い、突合の検査に管理者の資格情報を要求しない。
4. 宣言には**実際に適用する値**を書く。「あるべき値」を宣言し、実態だけを別の値にする形を採らない。決定1 の突合が意味を失うためである。
5. 宣言した値が一時的な緩和である場合、その事実・理由・復帰条件を、宣言と同じ場所の `README.md` が持つ。宣言ファイル自身は値のみを持つ。

### requiredに入れる基準

6. required status check に入れる基準を次とする。

   > その赤が、周囲ではなく**変更そのものについての事実**であること。

7. 具体的には、lintの指摘、失敗したテスト、宣言とずれた生成物、宣言と実態のdriftを対象とする。
8. 継承した状態を報告する検査をrequiredに入れない。**変更が持ち込んでいない指摘でPull Requestを人質にしない。** 既知の脆弱性の報告がこれに当たる場合、ブロックの判定は別の契機へ置く。

### `terraform plan` の扱い

9. `terraform plan` の成功をrequiredに含める。
10. **決定9 は決定6 の基準からは導かれない。** planはAWS側の状態に依存し、checkoutのみでは再現しない。基準を満たさないことを認めたうえで、次の理由により例外として置く。

    > ADR-0014 決定4 によりmergeがapplyを起動する。planが成立しない変更をmergeすることは、**何が適用されるか分からないまま適用を起動すること**に等しい。

11. 決定9 の代償を受け入れる。AWS側の状態変化、credentialsの取得失敗、provider registryへの到達不能により、変更に誤りが無くてもPull Requestがマージ不能になる。ADR-0014 決定9（credentialsを要する検証を要さない検証より先に実行しない）は実行順序の規定であり、この代償を打ち消さない。
12. planが赤である原因が変更の外にある場合、requiredから外すことで解決しない。原因を解消するか、変更の側でplanが成立する形にする。この事象が恒常化した場合は本ADRの見直し条件とする。

### トリガーのフィルタ

13. requiredとする context を報告するworkflowの `pull_request` トリガーに、`paths:` および `branches:` のフィルタを置かない。
14. 起動条件はjobの `if:` に置く。**skipされたjobはskippedを報告し、required checkはこれを成功として数える。**
15. 決定13・14 により、対象外のPull Requestでもcontextが必ず報告される。フィルタによる除外は報告の不在を生み、報告の不在は合格ではなく未報告として扱われる。

### 整合の検査

16. 宣言の required status check の一覧を入力とし、次を検査する機構を持つ（ADR-0020）。

    - 各 context を報告するjobが実在すること
    - そのworkflowの `pull_request` トリガーにフィルタが無いこと（決定13）

17. 決定16 の検査は宣言そのものを入力とする。検査が独自の一覧を持たない（ADR-0020 決定12）。

### 承認要件

18. 承認者数の要件には、**実際に満たせる値**を宣言する。満たせる人間が存在しない値を宣言しない。
19. 単独メンテナ体制で承認者数を1以上にすると、自身のPull Requestを自身で承認できないため、保護ブランチ向けのPull Requestが恒久的にマージ不能になる。**この解決に bypass の列挙を用いない。** bypassはその ruleset の全ルールを迂回するため required status check も無効になり、ADR-0014 決定10（mergeの可否 = 実環境への適用の可否）が成立しなくなる。
20. 承認者数を緩和する場合も、次は緩和しない。いずれも承認者数とは独立に効く。

    - 全スレッドの解決
    - merge方式の限定（rebase mergeを除外）
    - fast-forwardでない更新の禁止
    - 削除の禁止
    - required status check

### 履歴の書き換えの禁止

21. force push、rebase merge、履歴の書き換えの禁止を、**サーバ側の宣言として置く**。ローカルの機構で止めない。ローカルでの阻止は迂回手段を持つため、「迂回した者だけが通る」穴を残す。
22. AGENTS.mdが同じ禁止をエージェントへ課していることと、決定21 は重複しない。前者は作業する主体への規範、後者は主体を問わない強制である。片方を理由にもう片方を省かない。

## 検討した代替案

### 案A: 保護設定を宣言せず、GitHubのUIで管理する

設定の変更が即座に反映され、宣言と実態のずれが原理的に生じない。ただし現在の設定を知る手段がUIしかなく、変更の履歴もレビューも残らない。ADR-0014 決定1（Gitを正とする）の外に、デプロイのゲートを決める状態が置かれることになる。

### 案B: 宣言を一方向に適用し、突合を持たない

配線が最小で、初期化も1回で済む。ただしずれが兆候なく進む。宣言が「何を強制しているか」を答えていない状態が、読み手からは区別できない。

### 案C: `terraform plan` をrequiredに含めない

決定6 の基準に素直で、AWS側の事情でPull Requestが止まらない。ただしmergeがapplyを起動する構成では、planを見ないままapplyを起動する経路が開く。planの赤を「読むもの」に留めると、赤のまま merge される可能性が残る。

### 評価

| 評価軸 | 案A: UIで管理 | 案B: 一方向適用 | 案C: planを外す | 採用案: 突合 + planをrequired |
| --- | --- | --- | --- | --- |
| Security | 低（履歴もレビューも無い） | 中（ずれが進む） | 中（未確認のapplyが通る） | 高 |
| Testability | 低（検査対象が無い） | 低（宣言を検査しても実態を見ていない） | 高 | 高 |
| Contract Clarity | 低 | 低（宣言が実態を表さない） | 高 | 高 |
| Scope Control | 高 | 高 | 高 | 中（機構が2つ増える） |
| Reproducibility | 低 | 中 | 中 | 高 |
| 可用性への耐性 | 高 | 高 | 高 | **低（意図的）** |

## 意図的に捨てるもの

- AWS側に障害がある間もmergeできること
- 変更と無関係な理由でPull Requestがブロックされない状態
- UIから保護設定を変更して即座に反映する運用
- 承認者数の要件を、満たせる人間が居ない状態でも宣言できること

## 保証範囲

- 保証すること: 宣言された保護設定が実態と一致すること（突合の検査が通っている限り）。requiredとされた context が、対象外のPull Requestでも必ず報告されること。merge されたものについて、適用内容がplanとして確認されていること
- 保証しないこと: 突合の検査と検査の間に生じたずれ。planの成功が、applyの成功を意味すること

## 検証方法

- 突合の検査: 宣言と実態の差分が存在しないこと（決定1）
- 整合の検査: requiredとされた全 context に、それを報告するjobが存在すること（決定16）
- 整合の検査: 該当workflowの `pull_request` トリガーにフィルタが存在しないこと（決定13・16）
- Static Analysis: 宣言に bypass の列挙が存在しないこと（決定19）
- Static Analysis: 決定20 が挙げる各設定が宣言に存在すること
- 定期実行: 突合の検査を、Pull Request契機とは独立に実行する。実態はリポジトリの変更なしに変わり得るため

## 影響

- 保護設定の変更は、宣言の変更とその適用として行われる。UIでの変更は突合の検査で赤になる。
- AWS側の事情でPull Requestがマージできない時間帯が生じ得る（決定11）。
- 承認者数の現在の値と、その緩和の理由・復帰条件は、宣言と同じ場所の `README.md` が持つ（決定5）。

## 見直し条件

- planの赤が、変更の外の理由で恒常的に発生するようになった場合（決定12）
- メンテナの人数が変わり、承認者数の要件を見直す場合
- GitHubが、報告されなかった context の扱いを変更した場合
- 保護設定の宣言と適用を、突合なしに冪等へ保てる手段が提供された場合
