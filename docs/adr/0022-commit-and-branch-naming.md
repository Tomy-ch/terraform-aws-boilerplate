# ADR-0022: commit messageとブランチ名の規約を定め、機械に課す範囲を限定する

- Status: Accepted
- Date: 2026-09-16
- Scope: repository-wide
- Related: ADR-0013, ADR-0014, ADR-0015, ADR-0020, ADR-0021

## Context

ADR-0015 決定8-9 は文書とcommit messageの言語を定めたが、形式は定めていない。`AGENTS.md` には暫定として「当面はConventional Commitsに従う」とだけ書かれており、これは決定ではなく保留の記録である。ブランチ名についても接頭辞の例示があるだけで、許容される集合が定義されていない。

規約を定めるにあたり、**何を機械に課し、何を散文に置くか**の切り分けが要る。両者を区別せずに機械へ寄せると、次が起きる。

- 文字数の上限を機械が課すと、上限に収めるために情報を落としたsubjectが量産される
- 文体を機械が課すと、規約は満たすが内容の無いメッセージが通る
- いずれも「規約を満たしている」と「伝わる」が乖離した状態になり、規約が体裁の検査に退化する

一方、列挙可能な集合と空でないことの検査は、機械が判定を誤らない。ここを人のレビューに委ねると、単純に見落とされる。

ブランチ名については、接頭辞の集合を定義しない運用の実測値が得られている。接頭辞をenumとして持たない運用では、同義の接頭辞が併存する状態（`fix/` と `bugfix/`、`feature/` と `feat/`）が発生し、誰も止めない。件数としては小さいが、**ブランチ名から何かを導く機構を後から作ると、その揺れがそのまま機能不全になる**。

本リポジトリは変更経路をGitに限定しており（ADR-0014 決定1）、ブランチが変更の単位そのものである。将来、ブランチ名から対象や契機を導く可能性は、他の構成より高い。

## Decision

### 機械に課す範囲

1. commit messageについて機械が検査するのは次に限る。

   - type が定義された集合に含まれること
   - type が空でないこと
   - subject が空でないこと

2. 次を機械の検査対象としない。散文の規約として置き、レビューで見る。

   - subject の長さ
   - subject の文体
   - 大文字小文字の別
   - scope の有無と値
   - body / footer の有無と形式

3. 決定2 の理由は、これらを機械が課すと**規約を満たすが伝わらないメッセージ**を量産する側へ倒れることにある。機械が判定を誤らない事実だけを機械に課す。
4. 一般的な規約集（Conventional Commits 等）の設定を丸ごと継承しない。継承すると決定2 の項目が意図せず有効になる。必要な規則のみを明示的に宣言する。

### commit message の形式

5. subject の形式を `<Type>: <日本語の要約>` とする。
6. type を次の11種とする。**先頭を大文字とする。**

   ```text
   Feat  Fix  Refactor  Perf  Docs  Test  Build  CI  Chore  Style  Revert
   ```

7. type の大文字小文字を機械の検査対象としない。`CI` のように全大文字となるものが混在するため、一律の規則を課せない。決定6 の集合そのものが表記を固定する。
8. scope を使用しない。`<Type>(<scope>): ` の形を採らない。
9. subject を日本語で書き、常体の終止形で終える。体言止めと命令形を用いない。
10. subject の長さは50文字程度を目安とする。上限として強制しない。
11. subject の末尾に句点を置かない。
12. body は任意とする。置く場合、subject の後に空行を1つ置く。**「何を」ではなく「なぜ」を書く。** 変更内容は差分が持つ。
13. `Revert` を決定6 の集合に含める。取り消しも規約の対象とする。revert のsubjectがtypeの検査を通ることを前提とする。
14. merge commit のsubjectを書き換えない。ツールの既定に従う。

### trailer

15. `Co-Authored-By` を必須とする。値に用いるモデルの識別子は、**実行環境が提示するものをそのまま書く**。推測で書かない。
16. モデルの識別子を、規約を述べる文書側へ書かない。書くと同じ事実が2箇所に存在し、参照されない側が古くなる（ADR-0015 決定1 の適用）。
17. 決定1 の検査対象に trailer を含めない。trailer の形式を機械で検査しない。

### merge 方式

18. Pull Request の統合方式を merge commit に限定する。squash と rebase merge を許容しない（ADR-0021 決定20 の限定を、さらに merge のみへ狭める）。
19. 決定18 の理由は、規約の置き場所を1つに保つことにある。squash を許容すると、統合後のsubjectがPull Requestのタイトルから生成されるため、**commit に課した規約をPull Requestのタイトルにも課す必要が生じる**。同じ規約が2つの対象へ分かれる。

### ブランチ名

20. 接頭辞を次の集合に限る。**機械の検査対象とする。**

    | 接頭辞 | 用途 |
    | --- | --- |
    | `feature/` | 機能の追加・変更 |
    | `fix/` | 不具合の修正 |
    | `hotfix/` | リリース済みの構成に対する緊急の修正 |
    | `release/` | リリース線 |

21. 自動化が生成するブランチは決定20 の対象外とし、生成元ごとに固定の接頭辞を宣言したうえで許容する。宣言していない接頭辞を許容しない。
22. `feature/` と `fix/` の形式を次とする。

    - issue 番号がある場合: `<接頭辞><issue番号>-<説明>`
    - ない場合: `<接頭辞><説明>`
    - 説明は英語の kebab-case とする。長さを規定しない

23. リリース線と hotfix の形式を `release/v<major>.<minor>.<patch>` および `hotfix/v<major>.<minor>.<patch>` とする。プレリリース識別子、ビルドメタデータ、先頭のゼロを許容しない。
24. 決定20・23 の定義を**単一の宣言として置く**。ツールは実行時にそれを読み、CIの起動条件など生成可能な箇所は生成する。同じパターンを複数箇所へ直接記述しない（ADR-0020 決定10）。
25. 保護対象のブランチを判定するパターンも決定24 の宣言に含める。保護設定の宣言（ADR-0021 決定1）とローカルの判定が別々のパターンを持つ状態を作らない。

### 適用範囲

26. 本ADRの規約を、本ADR以降に作成される commit とブランチへ適用する。既存の履歴へ遡って適用しない。
27. 決定26 の帰結として、規約の導入時点を検査から除外する設定を持たない。検査の範囲は Pull Request がベースの上に積んだ範囲であり、ベースに既に存在する commit は範囲の外にある。**除外の設定が必要になった場合、それは範囲の取り方が誤っているという兆候として扱う。**

## 検討した代替案

### 案A: 一般的な規約集の設定を継承する

記述量が最小で、規約が広く知られている。ただし決定2 で機械の検査対象から外した項目（subject の長さ、大文字小文字、末尾の句点、footer の形式）が同時に有効になる。type の表記を決定6 の形にすると大文字小文字の規則と衝突し、trailer の形式も制約を受ける。外すために個別の無効化が必要になり、結局は明示的な宣言と同じ記述量になる。

### 案B: 文体と長さも機械の検査対象にする

規約の遵守が機械的に保証される。ただし上限に収めるために情報を落としたsubject、文体だけを整えた内容の無いsubjectが、いずれも検査を通る。**規約が伝達の質ではなく体裁を保証する状態になる。** 検査が通ることと目的が達成されることの乖離を、検査自身が隠す。

### 案C: ブランチ名の接頭辞を規定せず、散文の例示に留める

自由度が高く、規約の維持コストがない。ただし同義の接頭辞が併存する状態が発生し、誰も止めない。ブランチ名から対象や契機を導く機構を後から作ると、その揺れがそのまま機能不全になる。**後から集合を定義しても、既存のブランチ名は直らない。**

### 評価

| 評価軸 | 案A: 規約集を継承 | 案B: 文体も機械化 | 案C: 接頭辞を規定しない | 採用案: 限定して課す |
| --- | --- | --- | --- | --- |
| Security | 中 | 中 | 中 | 中 |
| Testability | 中（意図しない規則が有効） | 高 | 低（ブランチ名を検査できない） | 高 |
| Contract Clarity | 中 | 低（検査の通過と目的が乖離） | 低 | 高 |
| Scope Control | 中 | 低（規則が増え続ける） | 高 | 高 |
| Cognitive Load | 低 | 高（体裁への配慮が増える） | 低 | 低 |
| Maintainability | 中 | 中 | 中（揺れが蓄積する） | 中 |

## 意図的に捨てるもの

- 一般的な規約集をそのまま名乗れること
- subject の長さと文体が機械的に保証されること
- squash による履歴の平坦化
- ブランチ名の自由度

## 保証範囲

- 保証すること: 本ADR以降の commit の type が決定6 の集合に含まれること。ブランチの接頭辞が決定20・21 の集合に含まれること
- 保証しないこと: subject の内容が変更を正しく説明していること。body が「なぜ」を述べていること

## 検証方法

- CI: Pull Request がベースの上に積んだ範囲の commit について、決定1 の3項目を検査する。検査対象が0件の場合は成功としない（ADR-0020 決定13）
- CI: 範囲の起点を、Pull Request のイベントが示すベースの断面ではなく、ベースの現在の先端とする。前者は Pull Request 作成後にベースが進んだ場合、**自身が作成していない commit を範囲へ含める**
- CI: 範囲の取得に完全な履歴を要する。浅い取得では範囲の両端を解決できない。失敗を握り潰して既定の分岐へ縮退させない
- Static Analysis: ブランチの接頭辞が決定20・21 の集合に含まれること
- Static Analysis: 決定24 の宣言以外の場所に、リリース線および保護対象のパターンが直接記述されていないこと
- ローカルの hook は速い検査として置く。権威はCIに置く（ADR-0013 決定26）。**自動化が生成する commit はローカルの hook を経由しないため、hook のみでは検査されない経路が残る**

## 影響

- `AGENTS.md` の Git 規約から、暫定の記述（一般的な規約集に従う旨）が除かれる。
- 統合方式が merge commit に固定されるため、履歴に merge commit が残る。
- ブランチ名の検査が加わり、接頭辞の誤りが機械的に検出される。
- 決定24 の宣言が、リリース線・保護対象・CIの起動条件の単一の出所になる。

## 見直し条件

- 決定6 の集合で表現できない変更の種別が反復して発生した場合
- 決定20 の接頭辞で表現できないブランチの用途が生じた場合
- 統合方式を merge commit に限定することが、履歴の可読性を損なうと判断された場合
- 自動化が生成するブランチの種類が増え、決定21 の宣言が実態を追えなくなった場合
