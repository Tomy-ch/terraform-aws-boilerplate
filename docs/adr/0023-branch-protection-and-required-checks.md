# ADR-0023: 分岐のパターンと保護設定を単一の宣言で管理し、required checkの基準を定める

- Status: Accepted
- Date: 2026-09-17
- Scope: repository-wide
- Related: ADR-0014, ADR-0017, ADR-0019, ADR-0020, ADR-0022

本ADRは repository-wide/ADR-0021 をsupersedeする。

0021 は保護設定の管理と required check の基準を定めたが、**保護対象のパターンをどこが持つか**を
定めていなかった。そのパターンは別のADRが持っていたが、そちらは commit message の形式を細かく
規定しており、**その大半は守られなくても何も壊れないもの**だった。形式の規定ごと落とし、
残るもの（分岐のパターンの単一宣言と、統合方式の限定）をここへまとめる。

## Context

分岐のパターン —— 保護対象のブランチ、リリース線の形、ブランチ名の接頭辞 —— は、複数の場所が
読む値である。

- 保護設定の宣言（どの ref を保護するか）
- 変更の経路を解決するツール（どこから切るか）
- CIの起動条件（どの push で走るか）
- 作業する主体への規範（どこへ commit してはならないか）

**同じパターンを複数箇所へ直接書くと、片方だけが更新された状態が生まれる。** そしてこの
ずれは、保護の穴として現れる。実測された事例がある。

> 保護設定は `hotfix/**/*` を保護しているのに、ローカルの停止条件は `hotfix` を見ていない。
> しかも hotfix の運用中はそれがデフォルトブランチになるため、**最も踏みやすい場面でローカルが
> 止まらない。**

原因は、同じパターンが宣言とローカルの判定に別々に書かれていたことにある。片方を直しても
もう片方は静かに古いままになり、両方を実行するまで検出できない。

保護設定そのものについては、別の問題がある。保護設定はホスティングサービス側が保持する状態で
あり、リポジトリ内のファイルではない。宣言を置いても、それだけでは実態と一致する保証がない。
初期化時に1度だけ適用して以後放置すると、次のいずれでも**兆候なくずれる**。

- 管理画面から設定が外された
- 宣言を変更したが適用を忘れた
- 適用が部分的に失敗した

この状態の宣言が答えるのは「何を強制するつもりか」であって「何を強制しているか」ではない。
読み手は前者を後者と読む。

required status check には、機構として2つの落とし穴がある。

1. `pull_request` トリガーに `paths:` や `branches:` のフィルタを置くと、除外された Pull Request では
   run が**1件も起動しない**。報告されなかった context は「該当しない」とは解釈されず、報告を
   待ち続ける。そのPull Requestは**恒久的にマージ可能にならない**。
2. requiredに入れる対象の基準が無いと、変更が持ち込んでいない事象（既知の脆弱性、継承した状態）で
   赤が出て、Pull Requestが人質になる。

さらに本リポジトリには固有の事情がある。ADR-0014 決定4 によりmergeがapplyを起動するため、
**requiredの集合が実質的にデプロイのゲートになる**。requiredの選定が、通常のリポジトリより
重い判断になる。

## Decision

### 分岐のパターンの単一宣言

1. 保護対象のブランチ、リリース線の形、ブランチ名の接頭辞を、**単一の宣言が持つ**。
2. この宣言を読む側は次とする。いずれもパターンを自分で持たない。

   - 保護設定の宣言（決定4 の適用対象）
   - 変更の経路を解決するツール
   - CIの起動条件のうち、生成できるもの
   - 作業する主体への規範を述べる文書

3. 生成できる箇所は生成する。生成できない箇所は、実行時に宣言を読む。**同じパターンを2箇所へ
   直接書かない。**

### 保護設定の宣言と実態

4. 保護設定を宣言としてリポジトリへ置き、適用は宣言から行う。加えて、**実態と宣言を突き合わせる
   検査を持つ**（ADR-0020 決定10-12）。
5. 一方向の適用にしない。初期化時に1度適用して以後突合しない形を採らない。
6. 実態の取得には通常の読み取り権限で到達できる手段を用い、突合の検査に管理者の資格情報を要求しない。
7. 宣言には**実際に適用する値**を書く。「あるべき値」を宣言し、実態だけを別の値にする形を採らない。
   決定4 の突合が意味を失うためである。
8. 宣言した値が一時的な緩和である場合、その事実・理由・復帰条件を、宣言と同じ場所の `README.md` が
   持つ。宣言ファイル自身は値のみを持つ。

### requiredに入れる基準

9. required status check に入れる基準を次とする。

   > その赤が、周囲ではなく**変更そのものについての事実**であること。

10. 具体的には、lintの指摘、失敗したテスト、宣言とずれた生成物、宣言と実態のdriftを対象とする。
11. 継承した状態を報告する検査をrequiredに入れない。**変更が持ち込んでいない指摘でPull Requestを
    人質にしない。** 既知の脆弱性の報告がこれに当たる場合、ブロックの判定は別の契機へ置く。

### `terraform plan` の扱い

12. `terraform plan` の成功をrequiredに含める。
13. **決定12 は決定9 の基準からは導かれない。** planはAWS側の状態に依存し、checkoutのみでは
    再現しない。基準を満たさないことを認めたうえで、次の理由により例外として置く。

    > ADR-0014 決定4 によりmergeがapplyを起動する。planが成立しない変更をmergeすることは、
    > **何が適用されるか分からないまま適用を起動すること**に等しい。

14. 決定12 の代償を受け入れる。AWS側の状態変化、credentialsの取得失敗、provider registryへの
    到達不能により、変更に誤りが無くてもPull Requestがマージ不能になる。ADR-0014 決定9 は実行順序の
    規定であり、この代償を打ち消さない。
15. planが赤である原因が変更の外にある場合、requiredから外すことで解決しない。原因を解消するか、
    変更の側でplanが成立する形にする。この事象が恒常化した場合は本ADRの見直し条件とする。

### トリガーのフィルタ

16. requiredとする context を報告するworkflowの `pull_request` トリガーに、`paths:` および
    `branches:` のフィルタを置かない。
17. 起動条件はjobの `if:` に置く。**skipされたjobはskippedを報告し、required checkはこれを成功として
    数える。**
18. 決定16・17 により、対象外のPull Requestでもcontextが必ず報告される。フィルタによる除外は報告の
    不在を生み、報告の不在は合格ではなく未報告として扱われる。

### 整合の検査

19. 宣言の required status check の一覧を入力とし、次を検査する機構を持つ（ADR-0020）。

    - 各 context を報告するjobが実在すること
    - そのworkflowの `pull_request` トリガーにフィルタが無いこと（決定16）

20. 決定19 の検査は宣言そのものを入力とする。検査が独自の一覧を持たない（ADR-0020 決定12）。

### 承認要件

21. 承認者数の要件には、**実際に満たせる値**を宣言する。満たせる人間が存在しない値を宣言しない。
22. 単独メンテナ体制で承認者数を1以上にすると、自身のPull Requestを自身で承認できないため、保護
    ブランチ向けのPull Requestが恒久的にマージ不能になる。**この解決に bypass の列挙を用いない。**
    bypassはその保護設定の全ルールを迂回するため required status check も無効になり、ADR-0014
    決定10（mergeの可否 = 実環境への適用の可否）が成立しなくなる。
23. 承認者数を緩和する場合も、次は緩和しない。いずれも承認者数とは独立に効く。

    - 全スレッドの解決
    - merge方式の限定
    - fast-forwardでない更新の禁止
    - 削除の禁止
    - required status check

### 統合方式

24. Pull Request の統合方式を merge commit に限定する。squash と rebase merge を許容しない。
25. 決定24 の理由は、規約の置き場所を1つに保つことにある。squash を許容すると、統合後の subject が
    Pull Request のタイトルから生成されるため、**commit に課した検査をPull Requestのタイトルにも
    課す必要が生じる**。同じ規約が2つの対象へ分かれる。

### 履歴の書き換えの禁止

26. force push、rebase merge、履歴の書き換えの禁止を、**サーバ側の宣言として置く**。ローカルの
    機構で止めない。ローカルでの阻止は迂回手段を持つため、「迂回した者だけが通る」穴を残す。
27. 作業する主体への規範が同じ禁止を課していることと、決定26 は重複しない。前者は主体への規範、
    後者は主体を問わない強制である。片方を理由にもう片方を省かない。

### 本ADRで定めないこと

28. **commit message の形式を定めない。** 機械が検査するのは commit の種別を表す語の集合と、
    その語および要約が空でないことに限る。その値と、なぜその範囲に限るのかは、検査の設定ファイル
    自身が持つ。
29. 決定28 の理由は、文体・長さ・構成を機械が課すと、**規約を満たすが伝わらないメッセージ**を
    量産する側へ倒れることにある。守られなくても何も壊れない規定は、決定として置かない。

## 検討した代替案

### 案A: パターンを各所へ直接書く

記述が短く、読む側が宣言を解決する手間を持たない。ただし片方だけが更新された状態を、両方を実行
するまで検出できない。保護対象のパターンでこれが起きると、**保護されているつもりの ref が
保護されていない**状態になる。

### 案B: 保護設定をホスティングサービスの管理画面で管理する

設定の変更が即座に反映され、宣言と実態のずれが原理的に生じない。ただし現在の設定を知る手段が
管理画面しかなく、変更の履歴もレビューも残らない。ADR-0014 決定1（Gitを正とする）の外に、
デプロイのゲートを決める状態が置かれることになる。

### 案C: commit message の形式まで規定する

書き方が揃い、履歴の見た目が均一になる。ただし揃うのは体裁であって内容ではない。長さや文体を
課すと、上限に収めるために情報を落とした要約や、文体だけを整えた内容の無い要約が検査を通る。
**検査が通ることと目的が達成されることの乖離を、検査自身が隠す。**

### 評価

| 評価軸 | 案A: 各所へ直接 | 案B: 管理画面 | 案C: 形式まで規定 | 採用案 |
| --- | --- | --- | --- | --- |
| Security | 低（保護の穴が生じる） | 低（履歴もレビューも無い） | 中 | 高 |
| Testability | 低（ずれを検出できない） | 低（検査対象が無い） | 中（体裁だけ検査できる） | 高 |
| Contract Clarity | 中 | 低 | 低（検査の通過と目的が乖離） | 高 |
| Scope Control | 高 | 高 | 低（規則が増え続ける） | 高 |
| Cognitive Load | 低 | 低 | 高（体裁への配慮が増える） | 低 |

## 意図的に捨てるもの

- パターンを読む側が、宣言を解決せずに値を得られること
- AWS側に障害がある間もmergeできること
- 変更と無関係な理由でPull Requestがブロックされない状態
- 管理画面から保護設定を変更して即座に反映する運用
- commit message の見た目の均一さ

## 保証範囲

- 保証すること: 分岐のパターンの出所が単一であること。宣言された保護設定が実態と一致すること
  （突合の検査が通っている限り）。requiredとされた context が、対象外のPull Requestでも必ず
  報告されること。merge されたものについて、適用内容がplanとして確認されていること
- 保証しないこと: 突合の検査と検査の間に生じたずれ。planの成功が、applyの成功を意味すること。
  commit message の内容が変更を正しく説明していること

## 検証方法

- Static Analysis: 決定1 の宣言以外の場所に、保護対象・リリース線・接頭辞のパターンが直接
  記述されていないこと
- 突合の検査: 宣言と実態の差分が存在しないこと（決定4）
- 整合の検査: requiredとされた全 context に、それを報告するjobが存在すること（決定19）
- 整合の検査: 該当workflowの `pull_request` トリガーにフィルタが存在しないこと（決定16・19）
- Static Analysis: 宣言に bypass の列挙が存在しないこと（決定22）
- Static Analysis: 決定23 が挙げる各設定が宣言に存在すること
- 定期実行: 突合の検査を、Pull Request契機とは独立に実行する。実態はリポジトリの変更なしに
  変わり得るため

## 影響

- 保護設定の変更は、宣言の変更とその適用として行われる。管理画面での変更は突合の検査で赤になる。
- AWS側の事情でPull Requestがマージできない時間帯が生じ得る（決定14）。
- 承認者数の現在の値と、その緩和の理由・復帰条件は、宣言と同じ場所の `README.md` が持つ（決定8）。
- commit message の形式は検査の設定ファイルが持ち、ADRは関与しない。

## 見直し条件

- planの赤が、変更の外の理由で恒常的に発生するようになった場合（決定15）
- メンテナの人数が変わり、承認者数の要件を見直す場合
- 報告されなかった context の扱いが、ホスティングサービス側で変更された場合
- 分岐のパターンを読む側が増え、単一の宣言では表現しきれなくなった場合
