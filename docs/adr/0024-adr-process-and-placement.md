# ADR-0024: ADRの採用と配置・所有権ポリシー

- Status: Accepted
- Date: 2026-09-17
- Scope: repository-wide
- Related: ADR-0002, ADR-0003, ADR-0005, ADR-0020

本ADRは repository-wide/ADR-0001 をsupersedeする。変更したのは**番号体系と identity の扱い**
（決定10-13）だけで、他の決定はそのまま引き継ぐ。

## Context

ADR-0001 は番号について2つを定めていた。

> 番号は採番後に再利用しない。欠番を許容する。
> ADRのidentityは `<scope>/ADR-<number>` とする。

この組み合わせは、**ADRを削除できない**ことを意味していた。削除すると欠番が残り、番号が identity
である以上その欠番は永久に埋められない。結果として、ADRの一覧は「今有効な決定」ではなく
「これまでに書かれた決定」の並びになる。

実際に問題が生じた。**書きすぎた決定を落とす**判断をしたとき、番号を詰めるか欠番を残すかの二択に
なった。欠番を残す側は、読み手に「ここに何かがあったが、それが何かは分からない」という空白を
渡す。詰める側は、既に git 履歴へ残った番号参照（commit message、Pull Request の本文）の意味を
変える。

どちらの代償が重いかは、番号が何であるかによる。

- 番号が**識別子**なら、詰めてはならない。参照の解決先が変わるため
- 番号が**順序**なら、詰めてよい。識別子は別にあるため

ADR-0001 は前者を採ったが、**識別子として使うには番号は弱い**。scope をまたげば重複し
（決定10）、読み手は番号だけでは決定の内容を推測できない。一方でファイル名の後半（kebab-case の
題）は、scope をまたいでも重複しにくく、内容を示す。

したがって、identity をファイル名の題に移し、番号を順序として扱うほうが、実態に合う。

## Decision

### ADRの採用

1. 設計判断はADRとして記録する。コード、コードコメント、Pull Requestの説明のみで設計判断を伝達しない。
2. ADRはimmutableとして扱う。内容の変更は、既存ADRの書き換えではなく新規ADRによるsupersedeで行う。
   誤字修正および参照リンク修正はこの限りではない。
3. Statusは `Proposed` / `Accepted` / `Superseded by <scope>/<slug>` / `Deprecated` のいずれかとする。

### 番号と identity

4. **ADRのidentityは `<scope>/<slug>` とする。** slug はファイル名の番号を除いた部分
   （`kebab-case-title`）である。`repository-wide/architecture-principles` と
   `ecs-web-service/architecture-principles` は別のADRである。
5. **番号は順序を表す。識別子ではない。** 読む順序と依存の向きを一覧から読み取れるようにするための
   ものであり、決定を指すためのものではない。
6. **ADRを削除した場合、後続の番号を詰めてよい。** 欠番を残す義務を負わない。
7. 決定6 を行う場合、次をすべて同一の変更で行う。分割すると、詰めた直後だけ参照が壊れた状態が残る。

   - ファイル名の変更
   - 索引の更新
   - 全ADR本文の相互参照の更新
   - ADR以外の文書（作業規約、設定ファイルのコメント）からの参照の更新

8. **決定6 の代償を受け入れる。** git の履歴に残った番号参照（commit message、Pull Requestの本文、
   会話の記録）は、詰め直しによって指す先が変わる。これらは遡って直せない。
9. 決定8 を軽くするため、**ADR本文からADRを参照するときは番号と題の両方を書く**。番号だけの参照は、
   詰め直しの後に読み手が誤った決定へ到達する。
10. ファイル名は `NNNN-kebab-case-title.md` とする。番号は4桁とする。
11. 番号体系はscopeごとに独立させる。リポジトリ全体で一意である必要はない。

### 配置

12. ADRは適用範囲に応じて2階層で管理する。

    - repository-wide ADR: `docs/adr/`
    - use-case-local ADR: `modules/<use-case>/docs/adr/`

13. 原則は以下とする。

    > Repository-wide decisions are stored at the repository level.
    > Use-case-specific decisions are colocated with the owning use case.

14. ADRの配置場所そのものが、その設計判断の所有範囲を表す。配置はADRレビューの対象とする。

### 所有権と主語

15. ADRの主語はAWS resourceではなく、architecture invariantまたはuse caseとする。「Security Groupを
    どう作るか」ではなく「当該ユースケースのネットワーク境界をどう保証するか」を主題とする。
16. 特定resourceに関する判断であっても、そのresourceが特定ユースケースの内部実装である場合、ADRは
    当該ユースケース配下へ置く。resource単位のroot ADRを新設しない。

### 依存方向

17. 依存方向は root ADR → use-case ADR とする。
18. use-case ADRはroot ADRを前提条件として参照してよい。
19. root ADRから特定ユースケースの実装詳細へ依存しない。root ADRが例示として特定ユースケースに
    触れる場合も、その存在を前提としない記述とする。

### 昇格

20. use-case ADRとして始まった判断は、以下のいずれかを満たす場合にroot ADRへの昇格を検討する。

    - 2つ以上のユースケースへ同一原則が適用される
    - セキュリティ上のrepository-wide invariantである
    - module間の公開契約に影響する
    - リポジトリ全体のtest policyへ影響する
    - 今後追加するユースケースでも原則として維持すべき
    - 各ユースケースで個別判断させること自体がリスクになる

21. 以下は昇格の理由としない。

    - 偶然同じAWS resourceを利用している
    - 現時点で実装が似ている
    - Providerのdefaultが同じ
    - コード重複を減らしたい
    - 将来共通化できるかもしれない

22. 昇格の根拠は「同じresourceを利用しているから」ではなく「同じarchitecture invariantを共有して
    いるから」とする。ADRの共通化はコードのDRYとは別問題として扱う。
23. 昇格時は、元のuse-case ADRを `Superseded by repository-wide/<slug>` とし、root ADRからは元ADRを
    参照しない（依存方向の維持）。

### 何をADRにしないか

24. **守られなくても何も壊れない規定をADRに置かない。** 見た目の均一さ、表記の揺れ、作業の順序の
    好みは、決定ではない。
25. 決定24 の判定は「その規定が破られたとき、何が壊れるか」を述べられるかで行う。述べられない
    ものは、ADRではなく作業規約か設定ファイルのコメントへ置く。

### レビュー

26. ADR追加・変更時は、内容に加えて以下を確認する。

    1. この判断はリポジトリ全体へ適用されるか。
    2. 特定ユースケースのみの判断ではないか。
    3. AWS resourceそのものを主語にしていないか。
    4. より上位のarchitecture invariantとして表現できないか。
    5. 他ユースケースへ強制する必要が本当にあるか。
    6. 同じ判断が既にroot ADRとして存在しないか。
    7. use-case ADRで十分なのにrootへ昇格させていないか。
    8. 複数ユースケースに共通する不変条件なのに各所へ重複していないか。
    9. **破られたときに何が壊れるかを述べられるか**（決定25）。

## 検討した代替案

### 案A: 番号を識別子のまま保ち、欠番を許容する（ADR-0001 の形）

参照の解決先が永久に変わらない。git 履歴の番号参照も安全である。ただしADRを削除できず、一覧は
「今有効な決定」ではなく「これまでに書かれた決定」の並びになる。**書きすぎた決定を落とす判断が、
一覧の可読性を犠牲にしなければ実行できない。**

### 案B: 番号を持たず、slug だけで管理する

詰め直しの問題が原理的に生じない。ただし読む順序と依存の向きを一覧から読み取れなくなる。ADRは
上位の決定から下位へ積む構造を持つため、順序は内容の一部である。

### 案C: 番号を詰めるが、旧番号との対応表を索引に残す

履歴の番号参照を解決できる。ただし対応表はADRが増えるたびに伸び、**何が有効な決定かを読む前に
何が動いたかを読ませる**。索引の目的が変わってしまう。

### 評価

| 評価軸 | 案A: 欠番を許容 | 案B: 番号なし | 案C: 対応表を残す | 採用案: 番号は順序 |
| --- | --- | --- | --- | --- |
| Contract Clarity | 中（一覧が履歴になる） | 中（順序が読めない） | 低（索引が二重の目的を持つ） | 高 |
| Maintainability | 低（削除できない） | 高 | 低（対応表が伸びる） | 高 |
| Scope Control | 低（書きすぎを落とせない） | 高 | 中 | 高 |
| Testability | 高 | 高 | 中 | 高（相互参照の実在を検査する） |
| 外部参照の安定性 | 高 | 高 | 中 | **低（意図的に捨てる）** |

## 意図的に捨てるもの

- git の履歴に残った番号参照が、常に同じ決定を指すこと
- 番号だけでADRを一意に指せること
- 「この番号は過去に何かがあった」という情報

## 保証範囲

- 保証すること: ADR本文どうしの相互参照が、常に実在するADRを指すこと。索引が実ファイルと一致すること
- 保証しないこと: リポジトリの外（git 履歴、Pull Requestの本文、会話の記録）に残る番号参照の解決

## 検証方法

以下を静的検査の対象とする（ADR-0012 の Static Analysis レイヤー）。

- ファイル名が `NNNN-kebab-case-title.md` に適合すること（決定10）
- 同一scope内で番号が重複しないこと（決定11）
- 先頭メタデータに Status / Date / Scope が存在すること
- Status が `Superseded by` の場合、参照先ADRが存在すること（決定3）
- **ADR本文が参照する `ADR-NNNN` が、すべて実在すること**（決定7・9）
- 索引が実ファイルと一致すること
- root ADR本文が `modules/<use-case>/` 配下のpathへ規範的に依存していないこと（決定19）

決定24-25（守られなくても何も壊れない規定を置かない）は機械判定できない。決定26 のレビュー観点9
として扱う。

## 影響

- ADRを削除し、後続を詰められるようになる。一覧は「今有効な決定」の並びになる。
- 詰め直しは全参照の更新を伴うため、単独の変更として行う。他の変更と混ぜない。
- git 履歴に残る番号参照は、詰め直しの後に別の決定を指す。**この代償は遡って解消できない。**
- ADR本文からの参照に題を併記することで、詰め直し後も読み手が誤った決定へ到達しにくくなる。

## 見直し条件

- 詰め直しの頻度が上がり、履歴の番号参照が実務上追えなくなった場合
- 相互参照の実在検査では捕まえられない参照の壊れ方が観測された場合
- ADRの数が、番号による順序付けでは扱えない規模に達した場合
