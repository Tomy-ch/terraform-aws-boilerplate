# ADR-0103: インフラは業務ロジックを持たず、リポジトリが持つ実行コードを人の判断に通す

- Status: Accepted
- Date: 2026-10-25
- Scope: repository-wide
- Related: ADR-0001, ADR-0101, ADR-0102, ADR-0401, ADR-0402, ADR-0501, ADR-0601, ADR-0603, ADR-0702

## Context

本リポジトリは AWS のリソースとその接続を持ち、利用者への表現と業務の処理は利用側のリポジトリが持つ。この割当が崩れる形のうち最も避けるべきものは、業務ロジックをインフラが所有することである。業務ロジックがインフラに入ると、業務要件の変更がインフラの変更になり、ADR-0102（ユースケース単位でスコープを定義する）が定める責務境界が、宣言とは別のところで決まる。

業務ロジックかどうかは、コードの形から判定できない。同じ形のコードが、ヘッダの正規化であることも、閲覧可否の判定であることもある。機械にできるのは、コードを実行させる構成要素を見つけることまでである。

コードは2つの経路で実行される。AWS 上の実行経路（Lambda、Lambda@Edge、CloudFront Functions、EC2 の `user_data` 等）と、`terraform` の実行経路（provisioner、`external` data source）である。後者の一部は plan の中で実行される。`external` data source は state を refresh するたびにプログラムを実行し、`aws_lambda_invocation` data source は関数が既知であれば plan のたびに関数を invoke する（各 provider の文書）。`terraform show -json` を入力とする検査（ADR-0402（Policy Testの適用範囲と、その検証方法を定める）決定11）は、判定より先に実行を許す。

コードを実行させる構成要素を列挙して検出する形は、列挙の漏れを全件の緑として返す。Lambda と provisioner のほかにも、CloudWatch Synthetics の canary、SSM Document、AppSync の resolver 等がコードを実行させる。

構成のソースからは、実行されるコードのソースを誰が持つかを判別できない。コンテナイメージや他所で build された artifact の参照は、本リポジトリで build したものも指せる。

## Decision

### 業務ロジックの判定

1. 本リポジトリは業務ロジックを所有しない。業務ロジックとは、業務要件が変わったときに変更を要するコードをいう。例: 閲覧可否、状態遷移、業務データの検証、通知内容の決定。
2. 業務要件が変わっても変更を要しないコードは技術的ロジックであり、本リポジトリに置いてよい。例: ヘッダの正規化、URL の書き換え、AWS サービス間の形式変換、プロトコル処理。
3. 仕組みと決定が同じ箇所に現れる場合、本リポジトリは仕組みを持ち、利用側のリポジトリが決定とデータを持つ。例: 拒否リストとの照合は本リポジトリが持ち、何を拒否するかとリストの中身は利用側のリポジトリが持つ。
4. 論理リソース（ルーティング、event pattern、フィルタ等）の宣言は、決定5 に当たらない限りコードとして扱わない。

### 対象

5. 本 ADR がインフラ内コードと呼ぶものは、Terraform の構成要素のうち、次のいずれかを AWS 上または `terraform` の実行中に実行させるものとする。

   - 引数に書いたプログラムの本文またはコマンド（例: CloudFront Functions の `code`、`user_data`、provisioner の `command` / `inline`）
   - 本リポジトリ内のファイルを指す path、またはそこから作る artifact（例: Lambda の `filename`、`external` data source の `program`）
   - 他所で build された artifact の参照（例: コンテナイメージ、他のリポジトリが持つ object）

6. 決定5 の第3項に当たり、コードのソースを他のリポジトリが持つものを、外部所有のインフラ内コードと呼ぶ。そのロジックの所有者は、ソースを持つリポジトリである。本リポジトリは実行基盤の設定だけを持ち、外部所有のインフラ内コードに決定13・17・18 を課さない。
7. リポジトリ運用機構（ADR-0702（リポジトリ運用機構を独立した区分とし、Goで実装する））は、AWS 上の実行経路にも `terraform` の実行経路にも入らないので（ADR-0702 決定3）、インフラ内コードではない。運用機構のプログラムを決定5 の構成要素から実行させた場合、その構成要素はインフラ内コードであり、他のインフラ内コードと同じ扱いを受ける。

### 検出

8. 業務ロジックかどうかは人が判定する。検査はインフラ内コードを検出し、許可リストに無いものを失敗させることで、人の判断へ回す。
9. 本リポジトリの構成に現れる resource と data source の型を、単一の宣言で、決定5 に当たる型と当たらない型に分類する。分類に無い型が現れたら失敗させる。`user_data` を持てる型、いずれかの引数で決定5 に当たりうる型、および他の構成要素のコードを呼び出して実行させる型（例: `aws_lambda_invocation` data source）は、決定5 に当たる型とする。
10. provisioner と、provider の設定によるコマンドの実行は、型の分類に依らず検出する。
11. 検出は、ADR-0501（検証と運用の道具を既存ツールの組み合わせで構成する）決定5 の、Conftest が HCL のソースを読む Static Analysis で行う。`terraform show -json` を入力とする検査で行わない。検出の検査は、入力が0件のとき成功として終えず、解釈できない入力をエラーとする（ADR-0702 決定13・14 と同じ規律）。入力は Terraform が読む構成のファイルすべて（`.tf`、`.tf.json`、override のファイル、`terraform test` が読む `.tftest.hcl`）とし、読んだファイルの件数を、検出とは独立の経路で数えた件数と突き合わせる（ADR-0702 決定15）。`terraform` を AWS credentials 付きで実行する job と検出の順序は、ADR-0601（変更経路を Git に限定し、apply を merge 後の CI/CD で行う）決定9 が持つ。AWS credentials を持たずに `terraform` を実行し、検出に依存しない job（`terraform test` 等）は、検出より先にコードを実行しうるので、次を満たす。

    - job の権限は、リポジトリの内容の読み取りに限る
    - checkout は資格情報を作業ツリーに残さない
    - outbound の通信は許可リストに限る
    - 復元するキャッシュは、内容を固定値と突き合わせてから使う

### 許可リスト

12. 検出したインフラ内コードは、許可リストの項目に当たる場合に限り通す。許可リストは単一の宣言とし、各項目は次を持つ。

    - 構成要素を一意に指す識別
    - 種別（本リポジトリ所有 / 外部所有）
    - 本リポジトリ所有の場合: コードのソースの所在、その言語、決定13 の ADR の参照
    - 外部所有の場合: ソースを持つリポジトリ

13. 本リポジトリ所有の項目が参照する ADR は、Status が `Accepted` であり、次の見出しの節を持つ。見出し名はこのとおりとする。

    - `ネイティブ統合で解けない理由`
    - `入出力`
    - `失敗時の扱い`
    - `業務要件の変更で修正が必要にならない理由` —— 決定1-3 の問いへの答え

    参照は ADR-0001（ADRの採用と配置・所有権ポリシー（番号は群とスロット、identityはslug））決定4 の identity（`<scope>/<slug>`）で書き、番号で書かない。

14. 次の変更は、code owner による review の対象とする。

    - 許可リストと、決定9 の型の分類
    - 検出の検査と、そのテストの入力
    - 本リポジトリ所有の項目が指すコードのソース
    - 検出の job を実行する workflow と、ADR-0601 決定9 の job の依存
    - 検出の job を required とする宣言
    - code owner の宣言そのもの

15. 許可リストの項目のうち、どの構成要素にも当たらないものがあれば失敗させる。本リポジトリ所有の項目について、ソースの所在が実在しない場合と、構成要素が参照する path がソースの所在の下に無い場合も失敗させる。この判定は次に従う。

    - path は、その構成要素を宣言した module のディレクトリを基準に解き、正規化し、symlink を解決してから判定する
    - 静的に確定できない path（変数や式で組む path）と、リポジトリの外を指す path は失敗させる
    - ソースの所在がリポジトリの root、またはユースケースや module の全体を指す項目は失敗させる
    - 外部所有の項目の構成要素がリポジトリ内の path を参照する場合は失敗させる
16. 許可リストは検査の入力となる宣言であり（ADR-0702 決定12）、ADR-0501 決定13 の検査結果の抑止でも、ADR-0702 決定18 のバイパスでもない。期限を持たない。検出そのものを抑止する場合は ADR-0501 決定13 に従う。

### 承認後

17. 本リポジトリ所有のインフラ内コードは、ソース、依存ライブラリ、ビルド手順を本リポジトリ内に置く。
18. 本リポジトリ所有のインフラ内コードの言語ごとに、lint と test を CI の required check とする。言語と、それを担う required context の対応は、許可リストと同じ宣言に置く。許可リストに項目を持つ言語は、対応する context が required に在ることを要する。対応に無い言語を持つ項目は失敗させる。

### `user_data`

19. EC2 と Lightsail の `user_data` は起動処理（エージェントの導入、イメージの取得）に限り、アプリのロジックを置かない。

## 検討した代替案

### 案A: コードを実行させる構成要素を列挙して検出する

Lambda、Lambda@Edge、CloudFront Functions、provisioner、`external` data source を列挙し、それに当たるものを検出する。分類の宣言が要らず、保守は軽い。ただし列挙に無い経路（CloudWatch Synthetics、SSM Document、AppSync の resolver、`aws_lambda_invocation` data source 等）は検出されず、漏れは全件の緑として現れる。

### 案B: `terraform show -json` を入力とする Policy 層で検出する

Policy Test と同じ入力で検出する。module の展開後の構成を見られる。ただし `external` data source と `aws_lambda_invocation` data source は plan の中で実行されるので、判定より先にコードが走る。

### 案C: リポジトリ運用機構をインフラ内コードに含める

`scripts/` のプログラムも許可リストと ADR の参照の対象にする。運用機構の変更のすべてに許可リストが掛かり、ADR-0702 決定1-2 の区分と権威が2つになる。運用機構は実行経路に入らないので（ADR-0702 決定3）、検出しても判定するものが無い。

### 案D: 外部所有のコードを検出から外す

ソースを他のリポジトリが持つものを検出しない。許可リストは小さく保てる。ただし構成のソースからはソースの所在を判別できないので、外部所有と称すれば、本リポジトリで build した artifact を検出なしで置ける。

### 案E: 許可リストの項目を構成要素の識別だけにする

項目を短く保てる。ただし許可された構成要素のソースを書き換える変更が、許可リストの変更を伴わず、人のレビューへ戻らない。

### 評価

| 評価軸 | 案A: 列挙 | 案B: Policy 層 | 案C: 運用機構を含む | 案D: 外部所有を外す | 案E: 識別だけ | 採用案 |
| --- | --- | --- | --- | --- | --- | --- |
| Security | 低（列挙外が通る） | 低（判定前に実行される） | 中 | 低（申告で外せる） | 低（ソースの差し替えが通る） | 高 |
| Testability | 中（漏れを検出できない） | 中 | 中 | 中 | 中 | 高 |
| Contract Clarity | 中 | 中 | 低（区分が2つの権威を持つ） | 中 | 中 | 高 |
| Maintainability | 高 | 中 | 低（運用機構の変更すべてに掛かる） | 高 | 高 | 中（型ごとに分類の行が要る） |
| Scope Control | 中 | 中 | 低 | 中 | 中 | 高 |

評価軸の定義は ADR-0101（保証可能性を自由度より優先する）を参照する。

## 意図的に捨てるもの

- 新しい resource / data source の型を、分類の宣言とその review なしに使うこと
- 外部所有の実行基盤（コンテナイメージで動く Compute 等）を、許可リストの項目なしに置くこと
- plan の中でコードを実行する構成要素を、AWS credentials を伴う job で、検出より先に plan で評価すること

## 保証範囲

- 保証すること:
  - 決定9 の分類に無い型、許可リストに無いインフラ内コード、どの構成要素にも当たらない許可リストの項目が、検出の検査を通らないこと
  - 本リポジトリ所有の項目が、Status が `Accepted` で決定13 の見出しを持つ ADR を参照していること
- 保証しないこと:
  - インフラ内コードが業務ロジックを含まないこと、および決定13 の各節の記載の妥当性。検査は節の存在を見て、内容を見ない
  - 分類の各行の正しさ。決定5 に当たる型を当たらない側へ分類する誤り、いずれかの引数で決定5 に当たりうる型の網羅、provider の更新で引数が増えた型の再分類は、分類の review（決定14）に委ねる
  - 外部所有と申告した項目のソースが、実際に他のリポジトリに在ること
  - `user_data` の内容が起動処理に限られること
  - code owner による review の承認が実際に得られること。承認者数の要件は ADR-0603（分岐のパターンと保護設定を単一の宣言で管理し、required checkの基準を定める）決定21-22 が持つ
  - Git を経由しない、AWS 上でのコードの差し替え
  - AWS credentials を持たずに `terraform` を実行する job（`terraform test` 等）で、検出より先にコードが実行されないこと。検出への依存を求めるのは、credentials を伴う job だけである（ADR-0601 決定9）。その job で実行されたコードが届く範囲は、決定11 の制約で狭める

## 検証方法

- Static Analysis（Conftest、HCL のソース）: 分類に無い型で失敗すること。`user_data` を持てる型と、決定9 が例に挙げる型が決定5 に当たる側に分類されていること（決定9）
- Static Analysis（同）: provisioner と provider の設定によるコマンドの実行を、型に依らず検出すること（決定10）
- Static Analysis（同）: 許可リストに無いインフラ内コードで失敗すること。どの構成要素にも当たらない項目で失敗すること（決定12・15）
- Static Analysis（同）: 本リポジトリ所有の項目の参照先が実在し、Status が `Accepted` で、決定13 の見出しの節を持つこと。外部所有の項目がソースを持つリポジトリを持つこと（決定12-13）
- Static Analysis（同）: 入力が0件のとき成功しないこと。解釈できない入力でエラーになること。読んだファイルの件数が独立の経路の件数と一致すること（決定11）
- Static Analysis（同）: ソースの所在が実在しない項目、構成要素が参照する path が所在の下に無い項目、静的に確定できない path、リポジトリの外を指す path、広すぎる所在、リポジトリ内の path を参照する外部所有の項目で失敗すること。`..` と symlink を解決してから判定すること（決定15）
- Static Analysis: AWS credentials を持たずに `terraform` を実行し、検出に依存しない job が、決定11 の4つの制約を満たすこと（決定11）
- 検査自身のテスト: 上の各検査が、違反する入力と違反しない入力の両方で検証されていること（ADR-0402 決定7-9 の規律を本検査に課す）
- Static Analysis: 検出の context が required の宣言に在ること（決定14）
- 整合の検査: 検出の job が required context を報告すること（ADR-0603 決定19）
- Static Analysis: code owner の宣言が、決定14 の各対象を持つこと
- Static Analysis: 許可リストに項目を持つ言語について、対応する context が required の宣言に在ること。対応に無い言語の項目で失敗すること（決定18）
- レビュー（機械判定できない）: 決定1-4 による判定、決定13 の各節の内容、決定19 の `user_data` の内容

## 影響

- コードを実行させる構成要素を持つユースケースは、許可リストの項目を伴う。本リポジトリ所有の項目は、決定13 の節を持つ ADR を伴う。
- コンテナイメージで動く Compute のように、ソースを利用側が持つ実行基盤も、外部所有の項目を伴う。
- 新しい型を使う変更は、分類の宣言の1行を伴い、その行は code owner による review の対象になる。
- 検出の検査が、`terraform` を AWS credentials 付きで実行する job の前段に入る。

## 見直し条件

- 単独メンテナ体制で、code owner による review を成立させる手段が決まった場合
- 分類の行の追加が、変更の経路を妨げるほど頻繁になった場合
- HCL のソースから検出できない、コードを実行させる経路が見つかった場合
- 外部所有と申告した項目に、本リポジトリで build した artifact が置かれた事例が観測された場合
