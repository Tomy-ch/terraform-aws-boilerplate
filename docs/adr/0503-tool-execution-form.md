# ADR-0503: 道具の宣言を1つに保ち、実行環境を3経路に分ける

- Status: Accepted
- Date: 2026-09-17
- Scope: repository-wide
- Related: ADR-0501, ADR-0602, ADR-0302, ADR-0702

## Context

ADR-0501 決定19 は道具の版を単一の manifest で pin することを定めたが、**その道具をどこで実行するか**は定めていない。決定20 は「道具はそのまま実行する。version manager のサブコマンドで包まない」とだけ述べており、これは `PATH` の解決失敗を wrapper で誤魔化すことへの禁止であって、実行環境そのものの選択には答えていない。

本リポジトリには実行環境が3つある。

- 利用者の手元
- CIの使い捨ての実行環境
- 検査のためのコンテナ

**同じ検査が環境ごとに違う道具で走ると、CIと手元の食い違いを切り分けられない。** 版が一致していても、依存の解決結果が違えば結果は変わる。したがって設計の目的は、実行環境をどれか1つに統一することではなく、**どの経路でも同じ道具が走ることを保証すること**にある。

manifest が版を固定できる範囲には限りがある。

- **単一の静的バイナリ**は、版を固定すれば実行できる。取得したバイナリがそのまま道具である
- **パッケージエコシステムの成果物**（npm / PyPI）は、ランタイムの版を固定しても**依存の install が残る**。manifest が置けるのはランタイムまでであり、そこから先は lockfile と install 手順が必要になる

本リポジトリは後者の道具を必要とする。Markdown はこのリポジトリの主要な成果物であり（ADR 群、`AGENTS.md`、各ユースケースの `README.md`）、その体裁を検査する既製品は npm エコシステムにある。commit message の検査（正本は `commitlint.config.js`）も同様で、ADR-0501 決定3 の第1条件（既存ツールで実現できない）を満たさない以上、自前実装を選ぶ理由がない。

加えて、**同じ検査に定義が2つあると片方が腐る**。実行環境ごとに別のターゲットを持つ構成は、同じコマンドを2箇所へ書くことになり、片方だけが更新された状態を両方実行するまで検出できない。

## Decision

### 宣言は1つ

1. 道具の版の宣言を単一の manifest が持つ。**3つの実行経路すべてがこの manifest を読む。**

   | 経路 | 道具の用意のされ方 |
   | --- | --- |
   | 手元 | version manager が manifest を読んでホストへ導入する。パッケージエコシステムの道具は除く |
   | CI | 主要なランタイムは各 setup アクションが用意し、残りを manifest から読み込む。パッケージエコシステムの道具は除く |
   | コンテナ | イメージのビルドが manifest を読んで install する |

   ただし、決定4 の「上流がコンテナイメージとして配布する道具」は manifest に載せず、版の出所は決定10 が定める。

   パッケージエコシステムの道具も版の宣言は manifest が持つが、version manager にはそれを install させない。
   version manager の install はリポジトリの lockfile を読まず、推移的な依存を install のたびに解決し直す。
   どの経路も、manifest の宣言を写した同じ lockfile から入れる（決定17）。
2. 版を並べ直した設定を、イメージ側にも CI の定義側にも置かない。第二の出所を作らない。決定10 の道具も、版の出所は1つである。

   イメージのビルドが要る写し（ランタイムの照合値、パッケージマネージャの版と配布物の照合値）と、mise の lockfile（mise.lock。manifest の各道具について、解決した版と、platform ごとの取得元と照合値を持つ）は、manifest の宣言から生成し、宣言との一致を検査する。手で並べ直さない。CI とイメージのビルドは、道具を mise.lock からだけ解決する設定で入れる（lock に宣言と同じ版の entry が無ければ、version manager が入れずに失敗する）。
3. **ベースイメージが提供するランタイムの版が manifest の宣言と一致することを、イメージのビルド時に検査する。** 一致しない場合はビルドを失敗させる。3経路の版が黙って割れるのを、ビルドの時点で止める。

### 実行環境

4. 実行環境を次で分ける。

   | 対象 | 手元での実行 |
   | --- | --- |
   | 実行エンジン（`terraform`） | ホスト |
   | 単一の静的バイナリの検査ツール | コンテナ。ホストにも導入されるが、検査の既定の経路はコンテナとする |
   | パッケージエコシステムの install を要する道具（npm / PyPI） | コンテナ |
   | 運用機構（ADR-0702）の実行 | コンテナ |
   | 運用機構のうち、実環境の資格情報で `aws` を起動するもの（ADR-0702 決定26） | ホスト |
   | 上流がコンテナイメージとして配布する道具 | コンテナ（上流のイメージを digest で固定する）。ホストのパスを mount せず、検査対象をコンテナへ複写して走らせる。CI も同じ |
   | パッケージエコシステムの lockfile の生成と照合（pnpm） | ホスト |

   lockfile の生成と照合をホストで行うのは、コンテナのイメージがその lockfile から組まれるためである。lockfile が manifest からずれた時点でイメージが組めず、ずれを直す道具をコンテナに置くと、直す手段が先に壊れる。

5. `terraform` をコンテナへ入れない。理由を次とする。

   - 単一の静的バイナリであり、版を固定すれば実行できる
   - ADR-0602 決定12 の OIDC による資格情報の受け渡しに、コンテナ境界を1つ増やすと経路が増える
   - 人とCIが最も頻繁に起動する道具であり、起動ごとの追加時間が累積する

6. 運用機構をコンテナで実行するのは、隔離のためではなく**道具が揃っていることを保証するため**である。運用機構は `git` などホスト側の道具を呼び、テストもそれらを実際に起動して組み立てた引数列を検査する。揃っていない環境では検査自体が成立しない。
7. **CIでは、用意した道具を直接実行する。** 使い捨ての実行環境をさらにコンテナで包まない。既に隔離されている環境の上の二重の隔離は、新たに塞ぐ故障モードを持たない。

   ただし、決定4 の「上流がコンテナイメージとして配布する道具」は CI でもそのイメージで実行する。ここでのコンテナは隔離のためではなく配布の形である。runner の通信制限（ADR-0702 決定21）の下では daemon がホストのパスの mount を拒むので、検査対象は複写で渡す。

   パッケージエコシステムの道具は、コンテナと同じ lockfile から決定17 の形でホストへ入れたものを直接実行する。
   手元でホストの経路を選んだ場合も同じとする。

### 定義は1箇所

8. **同一の検査に対して、実行環境ごとの定義を作らない。** 検査の定義は1箇所に置き、実行環境の差は起動の前置きだけで表す。
9. 決定8 が禁じるのは定義の重複であって、実行環境の差ではない。前置きを切り替える手段は、定義そのものを変えない形とする。

### コンテナ

10. ベースイメージを digest で固定する。tag のみの参照を認めない。tag は付け替えられた時点で別のイメージを黙って引く。上流のイメージで実行する道具も同じとし、版は `image:` の tag が、digest はベースイメージと同じ lockfile が持つ。manifest に重ねて宣言しない（ADR-0501 決定19）。
11. 道具をビルドする段と、道具を提供する段を分ける。提供する段に version manager 本体と install のキャッシュを残さない。
12. ビルド時に必要な資格情報を build 引数で渡さない。イメージの履歴に残るため、履歴に残らない受け渡し手段を用いる。
13. **ベースイメージの libc を、CIの実行環境と揃える。** 揃えないと、上流が一方の配布物しか公開していない道具がコンテナでのみ install できない。これは環境差分そのものであり、道具の追加時に初めて判明する。

### パッケージマネージャ

14. npm エコシステムのパッケージ管理を pnpm、PyPI エコシステムを uv とする。
15. PyPI 側の lockfile は全エントリが版とハッシュを持つこととし、install 時にハッシュの照合を必須とする。記載漏れのある lockfile は install ごと失敗する。**ハッシュ照合そのものが検査を兼ねる。**
16. PyPI 側はビルド済み配布物のみを受け付ける。ハッシュが一致した source distribution であっても install 時に setup script が走るため、ハッシュ照合だけでは任意コードの実行を塞げない。
17. npm 側は、in-tree のパッケージの有無に関わらず、道具とその推移的な依存を lockfile で固定して frozen で install し、依存のライフサイクルスクリプトの実行可否を宣言する。宣言に無い依存が script を持ち込んだ時点で install を失敗させる。

    lockfile と宣言は1組とし、イメージのビルドも、ホストで直接実行する経路も、その1組から入れる。
    ホストの経路は道具を起動するたびに frozen の install を通し、lockfile が宣言の写しからずれているか、
    integrity が合わなければ、道具を起動する前に失敗させる。PATH に在る同名の道具へ退かない。
18. 決定17 の宣言の既定は空とし、install 時の script を一律で実行しない。

   推移的な依存へは、manifest の道具と同じ供給網の窓を lockfile の解決時に掛ける。直接の依存の窓は manifest に対して掛け、二重に掛けない。

### 導入の範囲

19. ADR-0501 決定33 に従い、走らせる道具が存在しない runner を置かない。PyPI 側の runner は、対象の道具を導入する変更で同時に置く。

## 検討した代替案

### 案A: すべてをホストで実行する

起動が最も速く、Docker への依存が無い。ただし npm / PyPI の道具は、各利用者のホストで install と実行をすることになる。lockfile で依存の版と integrity は揃えられても、それを動かすランタイムと OS は利用者ごとに揃わず、**同じ検査が利用者ごとに異なる環境で走る**。CIと手元で結果が食い違ったとき、原因の切り分けができない。

### 案B: 手元でもCIでもコンテナを使う

起動経路が完全に1つになり、切り分けが最も単純になる。ただしCIの実行環境は既に使い捨てであり、そこでイメージを組み立てる時間が全ジョブに乗る。得られる隔離は二重であって、新たに塞ぐ故障モードが無い。

### 案C: 実行環境ごとに検査の定義を持つ

各環境で最短の記述にできる。ただし同じコマンドが2箇所へ書かれ、片方だけが更新された状態を、両方を実行するまで検出できない。

### 評価

| 評価軸 | 案A: 全てホスト | 案B: 全てコンテナ | 案C: 定義を2つ | 採用案: 宣言1つ・経路3つ |
| --- | --- | --- | --- | --- |
| Security | 中（install 環境が不定） | 高 | 中 | 高 |
| Testability | 低（結果が利用者ごとに違い得る） | 高 | 低（片方が腐る） | 高 |
| Contract Clarity | 中 | 高 | 低（どちらが正か不定） | 高 |
| Scope Control | 高 | 中 | 低（記述が二重） | 高 |
| Reproducibility | 低 | 高 | 中 | 高 |
| 実行の速さ | 高 | 低 | 高 | 中 |

## 意図的に捨てるもの

- 3つの実行環境が同一であること
- すべての検査を Docker 無しで実行できること
- 検査の起動が最短であること

## 保証範囲

- 保証すること: 道具ごとに版の出所が単一であること（manifest、または決定10 の `image:` の tag）。同一の検査の定義が1箇所にあること。install を要する道具が、利用者の環境に依らず同じ依存で実行されること。ランタイムの版が3経路で一致していること（ビルド時に検査する）。npm 側の道具の推移的な依存が、コンテナでもホストの経路でも、同じ lockfile の版と integrity で入ること（決定17・18）
- 保証しないこと: 3つの実行環境が同一であること。Docker が利用できない環境での全検査の実行。手元でホストの経路を選んだときに、npm 側の道具を動かすランタイムの版が manifest の宣言と一致すること。手元の導入（make host-tools-install）が、mise.lock の取得元と照合値で道具を入れること。版は manifest が固定する。配布元が照合値を公開しない道具（AWS CLI）の mise.lock の照合値が、配布元の公開した値であること。その照合値は、lock を作るときに version manager が配布物から計算した値であり、その時点の配布物を信じる。

## 検証方法

- Static Analysis: 同一の検査に対して、実行環境ごとの定義が存在しないこと（決定8）
- Static Analysis: CIの定義が道具を用意する手段が、決定1 の manifest を読むものであること（決定2）
- Static Analysis: ベースイメージと上流のイメージが digest で固定されていること（決定10）
- **イメージのビルド**: ランタイムの版が manifest の宣言と一致しない場合にビルドが失敗すること（決定3）
- **イメージのビルド**: 配布物の照合値と lockfile の integrity が一致しない場合にビルドが失敗すること（決定2・17、`make node-tools-image-check` を CI が走らせる）
- Static Analysis: PyPI の lockfile の全エントリが版とハッシュを持つこと（決定15）
- Static Analysis: npm 側の lockfile が manifest の宣言を満たすこと（決定17・18、`make node-tools-lock-check`）
- Static Analysis: lockfile の解決に掛ける供給網の窓と、窓から外す直接の依存が、manifest 側の窓と道具に一致すること（決定18、`make versions-check`）
- Static Analysis: イメージが取るパッケージマネージャの版が manifest の宣言と一致し、配布物の照合値が揃っていること（決定2、`make pin-pnpm-check`）
- Static Analysis: mise.lock が manifest の道具を宣言と同じ版で持ち、lockfile_platforms の各 platform の取得元が道具の配布元を指すこと、と、CI とイメージのビルドが mise.lock からだけ道具を入れる設定を持つこと（決定2、`make versions-check`）
- Static Analysis: version manager の install から外す宣言が、manifest の npm 側の道具の集合と一致すること（決定1、`make versions-check`）
- **実行**: version manager が manifest の npm 側の道具を install の対象にしないこと（決定1、`make mise-npm-disabled-check` を CI が走らせる）
- **実行**: ホストの経路が、宣言の写しが lockfile からずれたとき、および lockfile の integrity が合わないときに道具の起動の前に失敗し、PATH の同名の道具へ退かないこと（決定17、`make node-tools-lock-check` の Go の入口が本走査の前に走らせる canary）
- Static Analysis: 走らせる道具を持たない runner が存在しないこと（決定19）

## 影響

- Docker が手元の前提に加わる。ただし `terraform` の実行には要らない（決定5）。
- 検査の定義を読んでも実行環境は分からない。どこで走るかは決定4・7 が答える。
- npm / PyPI の道具を追加する変更は、イメージの再ビルドを伴う。
- ADR-0501 決定4 の Security レイヤーのうち Trivy、および ADR-0302 決定2 の Secret Scan の道具は単一の静的バイナリであり、決定4 の第2行に当たる。Checkov / KICS / Semgrep CE は、上流のイメージで実行する行に当たる。

## 見直し条件

- CIの実行環境が、道具の用意に要する時間でコンテナを上回らなくなった場合
- 3つの実行環境の差に起因する食い違いが反復して発生した場合
- npm / PyPI の道具がすべて不要になった場合
- PyPI の道具の経路（決定14-16）が配線され、上流のイメージで実行している道具をその経路で同じく再現できるようになった場合
- runner の通信制限が、ホストのパスの mount を許すようになった場合（複写の手順が要らなくなる）
- 資格情報の受け渡しが、コンテナ境界を越えても経路を増やさない形で標準化された場合
- version manager のパッケージエコシステムの backend が、リポジトリの lockfile と install 時の script の宣言を読めるようになった場合（ホストの経路の install を version manager へ戻せる）
