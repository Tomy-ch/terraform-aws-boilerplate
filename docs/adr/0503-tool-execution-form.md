# ADR-0503: 道具の宣言を1つに保ち、実行環境を3経路に分ける

- Status: Accepted
- Date: 2026-09-17
- Scope: repository-wide
- Related: ADR-0501, ADR-0602, ADR-0302, ADR-0702

## Context

ADR-0501 決定19 は道具の版を単一の manifest で pin することを定めたが、**その道具をどこで実行するか**は定めていない。決定20 は「道具はそのまま実行する。version manager のサブコマンドで包まない」とだけ述べており、これは `PATH` の解決失敗を wrapper で誤魔化すことへの禁止であって、実行環境そのものの選択には答えていない。

本リポジトリには実行環境が3つある。

- 利用者の手元
- CIの使い捨ての実行環境
- 検査のためのコンテナ

**同じ検査が環境ごとに違う道具で走ると、CIと手元の食い違いを切り分けられない。** 版が一致していても、依存の解決結果が違えば結果は変わる。したがって設計の目的は、実行環境をどれか1つに統一することではなく、**どの経路でも同じ道具が走ることを保証すること**にある。

manifest が版を固定できる範囲には限りがある。

- **単一の静的バイナリ**は、版を固定すれば実行できる。取得したバイナリがそのまま道具である
- **パッケージエコシステムの成果物**（npm / PyPI）は、ランタイムの版を固定しても**依存の install が残る**。manifest が置けるのはランタイムまでであり、そこから先は lockfile と install 手順が必要になる

本リポジトリは後者の道具を必要とする。Markdown はこのリポジトリの主要な成果物であり（ADR 群、`AGENTS.md`、各ユースケースの `README.md`）、その体裁を検査する既製品は npm エコシステムにある。commit message の検査（正本は `commitlint.config.js`）も同様で、ADR-0501 決定3 の第1条件（既存ツールで実現できない）を満たさない以上、自前実装を選ぶ理由がない。

加えて、**同じ検査に定義が2つあると片方が腐る**。実行環境ごとに別のターゲットを持つ構成は、同じコマンドを2箇所へ書くことになり、片方だけが更新された状態を両方実行するまで検出できない。

## Decision

### 宣言は1つ

1. 道具の版の宣言を単一の manifest が持つ。**3つの実行経路すべてがこの manifest を読む。**

   | 経路 | 道具の用意のされ方 |
   | --- | --- |
   | 手元 | version manager が manifest を読んでホストへ導入する |
   | CI | 主要なランタイムは各 setup アクションが用意し、残りを manifest から読み込む |
   | コンテナ | イメージのビルドが manifest を読んで install する |

2. 版を並べ直した設定を、イメージ側にも CI の定義側にも置かない。第二の出所を作らない。
3. **ベースイメージが提供するランタイムの版が manifest の宣言と一致することを、イメージのビルド時に検査する。** 一致しない場合はビルドを失敗させる。3経路の版が黙って割れるのを、ビルドの時点で止める。

### 実行環境

4. 実行環境を次で分ける。

   | 対象 | 手元での実行 |
   | --- | --- |
   | 実行エンジン（`terraform`） | ホスト |
   | 単一の静的バイナリの検査ツール | コンテナ。ホストにも導入されるが、検査の既定の経路はコンテナとする |
   | パッケージエコシステムの install を要する道具（npm / PyPI） | コンテナ |
   | 運用機構（ADR-0702）の実行 | コンテナ |

5. `terraform` をコンテナへ入れない。理由を次とする。

   - 単一の静的バイナリであり、版を固定すれば実行できる
   - ADR-0602 決定12 の OIDC による資格情報の受け渡しに、コンテナ境界を1つ増やすと経路が増える
   - 人とCIが最も頻繁に起動する道具であり、起動ごとの追加時間が累積する

6. 運用機構をコンテナで実行するのは、隔離のためではなく**道具が揃っていることを保証するため**である。運用機構は `git` などホスト側の道具を呼び、テストもそれらを実際に起動して組み立てた引数列を検査する。揃っていない環境では検査自体が成立しない。
7. **CIでは、用意した道具を直接実行する。** 使い捨ての実行環境をさらにコンテナで包まない。既に隔離されている環境の上の二重の隔離は、新たに塞ぐ故障モードを持たない。

### 定義は1箇所

8. **同一の検査に対して、実行環境ごとの定義を作らない。** 検査の定義は1箇所に置き、実行環境の差は起動の前置きだけで表す。
9. 決定8 が禁じるのは定義の重複であって、実行環境の差ではない。前置きを切り替える手段は、定義そのものを変えない形とする。

### コンテナ

10. ベースイメージを digest で固定する。tag のみの参照を認めない。tag は付け替えられた時点で別のイメージを黙って引く。
11. 道具をビルドする段と、道具を提供する段を分ける。提供する段に version manager 本体と install のキャッシュを残さない。
12. ビルド時に必要な資格情報を build 引数で渡さない。イメージの履歴に残るため、履歴に残らない受け渡し手段を用いる。
13. **ベースイメージの libc を、CIの実行環境と揃える。** 揃えないと、上流が一方の配布物しか公開していない道具がコンテナでのみ install できない。これは環境差分そのものであり、道具の追加時に初めて判明する。

### パッケージマネージャ

14. npm エコシステムのパッケージ管理を pnpm、PyPI エコシステムを uv とする。
15. PyPI 側の lockfile は全エントリが版とハッシュを持つこととし、install 時にハッシュの照合を必須とする。記載漏れのある lockfile は install ごと失敗する。**ハッシュ照合そのものが検査を兼ねる。**
16. PyPI 側はビルド済み配布物のみを受け付ける。ハッシュが一致した source distribution であっても install 時に setup script が走るため、ハッシュ照合だけでは任意コードの実行を塞げない。
17. npm 側で in-tree のパッケージを持つ場合、lockfile を frozen で install し、依存のライフサイクルスクリプトの実行可否を宣言する。宣言に無い依存が script を持ち込んだ時点で install を失敗させる。
18. in-tree のパッケージを持たず、道具を大域へ導入するだけの間は、install 時のライフサイクルスクリプトを一律で実行しない。決定17 の形へ移すのは in-tree のパッケージが現れた時点とする。

### 導入の範囲

19. ADR-0501 決定33 に従い、走らせる道具が存在しない runner を置かない。PyPI 側の runner は、対象の道具を導入する変更で同時に置く。

## 検討した代替案

### 案A: すべてをホストで実行する

起動が最も速く、Docker への依存が無い。ただし npm / PyPI の道具は、manifest がランタイムを pin したうえで各利用者が install を実行することになる。lockfile があっても install の実行環境は揃わず、**同じ検査が利用者ごとに異なる依存で走る**。CIと手元で結果が食い違ったとき、原因の切り分けができない。

### 案B: 手元でもCIでもコンテナを使う

起動経路が完全に1つになり、切り分けが最も単純になる。ただしCIの実行環境は既に使い捨てであり、そこでイメージを組み立てる時間が全ジョブに乗る。得られる隔離は二重であって、新たに塞ぐ故障モードが無い。

### 案C: 実行環境ごとに検査の定義を持つ

各環境で最短の記述にできる。ただし同じコマンドが2箇所へ書かれ、片方だけが更新された状態を、両方を実行するまで検出できない。

### 評価

| 評価軸 | 案A: 全てホスト | 案B: 全てコンテナ | 案C: 定義を2つ | 採用案: 宣言1つ・経路3つ |
| --- | --- | --- | --- | --- |
| Security | 中（install 環境が不定） | 高 | 中 | 高 |
| Testability | 低（結果が利用者ごとに違い得る） | 高 | 低（片方が腐る） | 高 |
| Contract Clarity | 中 | 高 | 低（どちらが正か不定） | 高 |
| Scope Control | 高 | 中 | 低（記述が二重） | 高 |
| Reproducibility | 低 | 高 | 中 | 高 |
| 実行の速さ | 高 | 低 | 高 | 中 |

## 意図的に捨てるもの

- 3つの実行環境が同一であること
- すべての検査を Docker 無しで実行できること
- 検査の起動が最短であること

## 保証範囲

- 保証すること: 道具の版の出所が単一であること。同一の検査の定義が1箇所にあること。install を要する道具が、利用者の環境に依らず同じ依存で実行されること。ランタイムの版が3経路で一致していること（ビルド時に検査する）
- 保証しないこと: 3つの実行環境が同一であること。Docker が利用できない環境での全検査の実行

## 検証方法

- Static Analysis: 同一の検査に対して、実行環境ごとの定義が存在しないこと（決定8）
- Static Analysis: CIの定義が道具を用意する手段が、決定1 の manifest を読むものであること（決定2）
- Static Analysis: ベースイメージが digest で固定されていること（決定10）
- **イメージのビルド**: ランタイムの版が manifest の宣言と一致しない場合にビルドが失敗すること（決定3）
- Static Analysis: PyPI の lockfile の全エントリが版とハッシュを持つこと（決定15）
- Static Analysis: 走らせる道具を持たない runner が存在しないこと（決定19）

## 影響

- Docker が手元の前提に加わる。ただし `terraform` の実行には要らない（決定5）。
- 検査の定義を読んでも実行環境は分からない。どこで走るかは決定4・7 が答える。
- npm / PyPI の道具を追加する変更は、イメージの再ビルドを伴う。
- ADR-0501 決定4 の Security レイヤーおよび Secret Scan レイヤーの道具は単一の静的バイナリであり、決定4 の第2行に当たる。

## 見直し条件

- CIの実行環境が、道具の用意に要する時間でコンテナを上回らなくなった場合
- 3つの実行環境の差に起因する食い違いが反復して発生した場合
- npm / PyPI の道具がすべて不要になった場合
- 資格情報の受け渡しが、コンテナ境界を越えても経路を増やさない形で標準化された場合
