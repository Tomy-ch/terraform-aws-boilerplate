# ADR-0603: 分岐のパターンと保護設定を単一の宣言で管理し、required checkの基準を定める

- Status: Accepted
- Date: 2026-10-21
- Scope: repository-wide
- Related: ADR-0601, ADR-0602, ADR-0302, ADR-0702, ADR-0503, ADR-0103

本ADRは、保護設定を宣言と実態の突合で管理していた先行ADRをsupersedeする。

0021 は保護設定の管理と required check の基準を定めたが、**保護対象のパターンをどこが持つか**を
定めていなかった。そのパターンは別のADRが持っていたが、そちらは commit message の形式を細かく
規定しており、**その大半は守られなくても何も壊れないもの**だった。形式の規定ごと落とし、
残るもの（分岐のパターンの単一宣言と、統合方式の限定）をここへまとめる。

## Context

分岐のパターン —— 保護対象のブランチ、リリース線の形、ブランチ名の接頭辞 —— は、複数の場所が
読む値である。

- 保護設定の宣言（どの ref を保護するか）
- 変更の経路を解決するツール（どこから切るか）
- CIの起動条件（どの push で走るか）
- 作業する主体への規範（どこへ commit してはならないか）

**同じパターンを複数箇所へ直接書くと、片方だけが更新された状態が生まれる。** そしてこの
ずれは、保護の穴として現れる。実測された事例がある。

> 保護設定は `hotfix/**/*` を保護しているのに、ローカルの停止条件は `hotfix` を見ていない。
> しかも hotfix の運用中はそれがデフォルトブランチになるため、**最も踏みやすい場面でローカルが
> 止まらない。**

原因は、同じパターンが宣言とローカルの判定に別々に書かれていたことにある。片方を直しても
もう片方は静かに古いままになり、両方を実行するまで検出できない。

保護設定そのものについては、別の問題がある。保護設定はホスティングサービス側が保持する状態で
あり、リポジトリ内のファイルではない。宣言を置いても、それだけでは実態と一致する保証がない。
初期化時に1度だけ適用して以後放置すると、次のいずれでも**兆候なくずれる**。

- 管理画面から設定が外された
- 宣言を変更したが適用を忘れた
- 適用が部分的に失敗した

この状態の宣言が答えるのは「何を強制するつもりか」であって「何を強制しているか」ではない。
読み手は前者を後者と読む。

required status check には、機構として2つの落とし穴がある。

1. `pull_request` トリガーに `paths:` や `branches:` のフィルタを置くと、除外された Pull Request では
   run が**1件も起動しない**。報告されなかった context は「該当しない」とは解釈されず、報告を
   待ち続ける。そのPull Requestは**恒久的にマージ可能にならない**。
2. requiredに入れる対象の基準が無いと、変更が持ち込んでいない事象（既知の脆弱性、継承した状態）で
   赤が出て、Pull Requestが人質になる。

さらに本リポジトリには固有の事情がある。ADR-0601 決定4 によりデプロイブランチへの merge が
apply を起動し、リリース線へ merge した commit はそのままそこへ運ばれるため、
**requiredの集合が実質的にデプロイのゲートになる**。requiredの選定が、通常のリポジトリより
重い判断になる。

## Decision

### 分岐のパターンの単一宣言

1. 保護対象のブランチ、リリース線の形、ブランチ名の接頭辞、env ごとのデプロイブランチ（ADR-0601 決定4）と
   それが変更を受け取る線を、**単一の宣言が持つ**。
2. この宣言を読む側は次とする。いずれもパターンを自分で持たない。

   - 保護設定の宣言（決定4 の適用対象。役割ごとの ruleset の対象と、env を持つデプロイブランチの ruleset の
     required の一覧を含む）
   - 変更の経路を解決するツール
   - CIの起動条件のうち、生成できるもの
   - 作業する主体への規範を述べる文書

3. 生成できる箇所は生成する。生成できない箇所は、実行時に宣言を読む。**同じパターンを2箇所へ
   直接書かない。**

### 保護設定の宣言と実態

4. 保護設定を宣言としてリポジトリへ置き、適用は宣言から行う。加えて、**実態と宣言を突き合わせる
   検査を持つ**（ADR-0702 決定10-12）。保護設定は、ブランチの保護規則と、デプロイの environment
   （名前、deployment branch policy、管理者による保護の迂回の可否）を含む。environment の
   deployment branch policy のパターンは、決定1 の宣言から生成する（決定3）。
5. 一方向の適用にしない。初期化時に1度適用して以後突合しない形を採らない。
6. 実態の取得には通常の読み取り権限で到達できる手段を用い、突合の検査に管理者の資格情報を要求しない。
7. 宣言には**実際に適用する値**を書く。「あるべき値」を宣言し、実態だけを別の値にする形を採らない。
   決定4 の突合が意味を失うためである。承認者数の要件（決定21）は除く。
8. 宣言した値が一時的な緩和である場合、その事実・理由・復帰条件を、宣言と同じ場所の `README.md` が
   持つ。宣言ファイル自身は値のみを持つ。

### requiredに入れる基準

9. required status check に入れる基準を次とする。

   > その赤が、周囲ではなく**変更そのものについての事実**であること。

10. 具体的には、lintの指摘、失敗したテスト、宣言とずれた生成物、宣言と実態のdriftを対象とする。

11. 継承した状態を報告する検査をrequiredに入れない。**変更が持ち込んでいない指摘でPull Requestを
    人質にしない。** 既知の脆弱性の報告がこれに当たる場合、ブロックの判定は別の契機へ置く。

### `terraform plan` の扱い

12. `terraform plan` の成功を required に含める。線の ruleset では、その線を `from` に持つ env の plan を
    gate（決定17）が見る。env を持つデプロイブランチの ruleset では、その env の plan を直接 required とする。
13. **決定12 は決定9 の基準からは導かれない。** planはAWS側の状態に依存し、checkoutのみでは
    再現しない。基準を満たさないことを認めたうえで、次の理由により例外として置く。

    > ADR-0601 決定4 により、デプロイブランチへの merge が apply を起動する。planが成立しない
    > 変更をそこへmergeすることは、**何が適用されるか分からないまま適用を起動すること**に等しい。
    > リリース線へのmergeはapplyを起動しないが、そのcommitは昇格でそのまま適用される。リリース線宛の
    > planは、そのenvの今の状態（デプロイブランチの木）に対する差分であり、
    > 未昇格の変更も差分に含む。

14. 決定12 の代償を受け入れる。AWS側の状態変化、credentialsの取得失敗、provider registryへの
    到達不能により、変更に誤りが無くてもPull Requestがマージ不能になる。ADR-0601 決定9 は実行順序の
    規定であり、この代償を打ち消さない。
15. planが赤である原因が変更の外にある場合、requiredから外すことで解決しない。原因を解消するか、
    変更の側でplanが成立する形にする。この事象が恒常化した場合は本ADRの見直し条件とする。

### トリガーのフィルタ

16. ruleset が直接 required とする context を報告する workflow の `pull_request` トリガーに、`paths:` を
    置かない。`branches:` は、その context を required とする ruleset の対象と同じ集合を、決定1 の宣言から
    生成した一覧に限って置ける（決定3）。gate（決定17）が呼ぶ検査の workflow は、`pull_request` で起動しない。
17. Pull Request の検査は、1つの gate が呼ぶ。gate は、検査と path の対応の単一の宣言を Pull Request の
    base の commit から読み、その Pull Request で走るべき検査を決める。走るべきでない検査は呼ばない。
    **検査を走らせるかどうかの条件は gate だけが持つ。** gate が呼ぶ検査は、自身の起動条件で job を skip
    しない。各検査の結果は、gate と同じ run の job の結果として受け取る。走るべき検査がすべて成功した
    ときだけ、gate は成功する。
18. gate は次をいずれも失敗とする。

    - 走るべき検査の skipped・cancelled・failure
    - 走るべきでない検査の failure
    - 宣言の検査の集合と、run の中の検査の集合の食い違い
    - 走るべき検査の集合を決められなかったこと

    gate の job は、run が取り消されても走り、取り消しを失敗として報告する。gate の run が起動できない
    とき（定義の誤りなど）は gate が報告されず、merge は止まる。報告の不在は合格ではなく未報告として
    扱われる。直すのは gate の定義であり、required から外して解決しない（決定15）。

### 整合の検査

19. ruleset の宣言と、検査と path の対応の宣言を入力とし、次を検査する機構を持つ（ADR-0702）。

    - 直接 required とする各 context を報告する job がちょうど1つ実在し、reusable workflow の中の job で
      ないこと
    - その workflow の `pull_request` トリガーが決定16 に従うこと
    - gate と線の検証（決定37）が受け取る検査の集合が、宣言と両方向で一致すること
    - gate と線の検証の job が、取り消されても走る形であること
    - gate が呼ぶ workflow が、`pull_request` で起動せず、自身の起動条件で job を skip せず、呼び手と
      取り消しの group を共有しないこと
    - 線の検証の context の名前が、ほかのイベントで起動する workflow に無いこと（決定38）

20. 決定19 の検査と gate と線の検証は、宣言そのものを入力とする。どれも独自の一覧を持たない
    （ADR-0702 決定12）。

### 承認要件

21. 承認者数の要件には、配布する参照実装の値として1以上を宣言する。満たせる人間がいないことを理由に宣言の値を下げない。
22. 単独メンテナ体制で承認者数を1以上にすると、自身のPull Requestを自身で承認できないため、保護
    ブランチ向けのPull Requestが恒久的にマージ不能になる。**この解決に bypass の列挙を用いない。**
    bypassはその保護設定の全ルールを迂回するため required status check も無効になり、ADR-0601
    決定10（デプロイブランチへのmergeの可否 = 実環境への適用の可否）が成立しなくなる。ここでいう bypass はブランチの
    保護規則に列挙する迂回者を指す。environment の管理者による保護の迂回は決定4 の宣言値であり、
    ADR-0602（bootstrapをCLIとimportで立ち上げ、CI認証をOIDCとする）決定14 がこれを無効とする。
23. 承認者数の値にかかわらず、次は緩和しない。いずれも承認者数とは独立に効く。

    - 全スレッドの解決
    - merge方式の限定
    - fast-forwardでない更新の禁止
    - 削除の禁止
    - required status check

    承認者数の値にかかわらず、code owner による review の要求を宣言から外さない。この要求が merge を
    止めるかは承認者数と独立ではなく、本 ADR はそれを保証しない。

### 統合方式

24. Pull Request の統合方式を merge commit に限定する。squash と rebase merge を許容しない。
25. 決定24 の理由は、規約の置き場所を1つに保つことにある。squash を許容すると、統合後の subject が
    Pull Request のタイトルから生成されるため、**commit に課した検査をPull Requestのタイトルにも
    課す必要が生じる**。同じ規約が2つの対象へ分かれる。

### 履歴の書き換えの禁止

26. force push、rebase merge、履歴の書き換えの禁止を、**サーバ側の宣言として置く**。ローカルの
    機構で止めない。ローカルでの阻止は迂回手段を持つため、「迂回した者だけが通る」穴を残す。
27. 作業する主体への規範が同じ禁止を課していることと、決定26 は重複しない。前者は主体への規範、
    後者は主体を問わない強制である。片方を理由にもう片方を省かない。

### 本ADRで定めないこと

28. **commit message の形式を定めない。** 機械が検査するのは commit の種別を表す語の集合と、
    その語および要約が空でないことに限る。その値と、なぜその範囲に限るのかは、検査の設定ファイル
    自身が持つ。
29. 決定28 の理由は、文体・長さ・構成を機械が課すと、**規約を満たすが伝わらないメッセージ**を
    量産する側へ倒れることにある。守られなくても何も壊れない規定は、決定として置かない。

### 保護設定の適用の担い手

30. 保護設定の適用は、管理者の資格情報を持つ人が宣言から行う。CI に保護設定を書き込む資格情報を
    置かない。保護設定を書き込める主体は保護そのものを外せるので、その資格情報を守る仕組みは保護より
    強くなれない。CI に置けば、保護ブランチへ merge できる主体へそれを渡すことになる。merge の後の
    適用し忘れは、管理者が適用の後に決定4 の突合を手元で走らせて確かめる。突合を CI に定期実行させない。
    保護設定を守るのは管理者の資格情報を持つ人であり、CI の補強はその責任の所在をぼかすだけで、
    ずれを直す権限を持たない。

### デプロイブランチへの経路

31. デプロイブランチ（ADR-0601 決定4）へ入る Pull Request を、次をすべて満たすものに限る。デフォルトブランチが、
    宣言がそのデプロイブランチに名指す線のどれかであること。head の commit がデフォルトブランチから到達できること。
    merge の結果の木が head の木と一致すること。これによりデプロイブランチの木は、常にその線でレビューされた
    commit の木と一致する。head のブランチ名では限らない —— 保護パターンに当たるブランチは書き込み権限で
    新しく作れるが、デフォルトブランチを変えられるのは管理者だけである。ruleset は Pull Request の head を
    限る規則を持たないので、env を持つデプロイブランチの ruleset が直接 required とする check で見る。
    検査は base の commit の宣言とコードで走らせる。
32. **決定31 の検査は決定9 の基準からは導かれない。** デフォルトブランチの名前と到達性はデフォルトブランチの
    今の状態に、木の一致はデプロイブランチの今の木に依り、どちらも変更の外の状態である。基準を満たさないことを
    認めたうえで、デプロイブランチへの merge が apply を起動し、レビューを経ない commit とリリース線から分かれた
    木の apply を止めるものがこの検査のほかに無いことを理由に、例外として置く。この検査を required とするのは
    env を持つデプロイブランチの ruleset だけなので、決定11 の人質はデプロイブランチ宛の Pull Request に限られる。赤の原因が状態にあるときは
    required から外さず、状態を直す（決定15 と同じ）。
33. sandbox への apply（ADR-0601 決定4 の例外）の成功を required に含める。**決定9 の基準からは導かれない。**
    apply の成否は sandbox の AWS の状態と、ほかの Pull Request の apply に依り、変更の外の状態である。
    基準を満たさないことを認めたうえで、リリースされていない変更を実環境の前に確かめる場所が sandbox の
    ほかに無いことを理由に、例外として置く。required とするのはデプロイブランチの ruleset だけなので、
    決定11 の人質はデプロイブランチ宛の Pull Request に限られる。赤の原因が
    変更の外にあるときは required から外さず、原因を直す（決定15・32 と同じ）。

### required check の報告元

34. required とする context は、報告する主体を GitHub Actions に限る（ruleset の `integration_id`）。context の
    名前だけで照合すると、書き込み権限を持つ主体が commit status の API で同じ名前の status を投稿して
    required を満たせる。デプロイブランチへの merge が apply を起動する（ADR-0601 決定4）以上、required の
    偽装はデプロイの迂回である。gate（決定17）と線の検証（決定37）の context も同じとする。`integration_id` は
    報告した workflow を区別しないので、同じリポジトリの Pull Request が、自身の job で同じ名前の context を
    報告することは防がない。

### 役割ごとの ruleset と線の検証

35. 保護対象に、役割ごとの ruleset を重ねる。

    - 共通の ruleset は、すべての保護対象に決定21-26 の規則を課す
    - 線の ruleset は、各線と env を持たないデプロイブランチに gate を required とする
    - env を持つデプロイブランチごとの ruleset は、決定31 の検査と、その env の plan と、線の検証を required
      とする

    どの ruleset の対象も、決定1 の宣言から生成する。
36. env を持たないデプロイブランチには、決定31 の検査が効かない。このため線の ruleset に入れ、コードの検査を
    課す。env を配線したときに、生成によって env を持つデプロイブランチの ruleset へ移る。
37. 線への push ごとに、その commit の木に対して、木だけで決まる検査を path で絞らずにすべて走らせ、1つの
    context で報告する（線の検証）。これにより、gate が path で省いた検査も、デプロイブランチへ入る commit に
    ついては走っている。線の先頭にならなかった commit は線の検証の報告を持たないので、到達できても
    デプロイブランチへ入らない。
38. 線の検証の context は、線の ref への push で起動した run のものだけを成功とする。その名前は、ほかの
    イベントで起動する workflow の job に置かない。skip された job の check が、同じ commit の成功として
    数えられるためである。
39. **決定37 は決定9 の基準からは導かれない。** 線の検証は、Pull Request の変更ではなく、merge した結果の木に
    ついての事実を報告する。基準を満たさないことを認めたうえで、昇格の Pull Request が検査を走らせ直さない
    とき、デプロイブランチへ入る木が全検査を通ったことを確かめる場所がほかに無いことを理由に、例外として
    置く。人質は、デプロイブランチ宛の Pull Request に限られる。線の検証が変更の外の理由で赤になると昇格が
    止まる。この代償を受け入れ、赤の原因が変更の外にあるときは required から外さず、原因を直す（決定15 と
    同じ）。

## 検討した代替案

### 案A: パターンを各所へ直接書く

記述が短く、読む側が宣言を解決する手間を持たない。ただし片方だけが更新された状態を、両方を実行
するまで検出できない。保護対象のパターンでこれが起きると、**保護されているつもりの ref が
保護されていない**状態になる。

### 案B: 保護設定をホスティングサービスの管理画面で管理する

設定の変更が即座に反映され、宣言と実態のずれが原理的に生じない。ただし現在の設定を知る手段が
管理画面しかなく、変更の履歴もレビューも残らない。ADR-0601 決定1（Gitを正とする）の外に、
デプロイのゲートを決める状態が置かれることになる。

### 案C: commit message の形式まで規定する

書き方が揃い、履歴の見た目が均一になる。ただし揃うのは体裁であって内容ではない。長さや文体を
課すと、上限に収めるために情報を落とした要約や、文体だけを整えた内容の無い要約が検査を通る。
**検査が通ることと目的が達成されることの乖離を、検査自身が隠す。**

### 案D: CI が GitHub App で保護設定を適用する

merge が適用になり、人の手順が残らない。ただし保護を外せる資格情報を CI に置く。その鍵には保護
ブランチへ merge された workflow から届き、届いた主体は保護を外せる。書き込みの前に App の権限と
install 先を確かめても、鍵を直接使う主体には効かない。

### 案E: workflow_run の gate が head に status を付ける

workflow_run で起動した job の check は、必須の判定に数えられない（GitHub の文書が明記する）。API で付けた
status が数えられるかは文書に無い。`integration_id` は workflow を区別しないので、gate の定義が default branch に
あっても偽装は防がない。

### 案F: pull_request_target の gate が検査の完了を待つ

偽装は案E と同じく防げない。待つ間 runner を占め、時間切れを失敗と読むと遅い検査を人質にする。path の判定が、
GitHub の `paths:` と別の実装になる。

### 案G: ruleset を役割ごとに分けるだけ

path の skip で報告を埋める形が残る。

### 案H: gate だけで、線の検証を置かない

昇格の Pull Request が検査を走らせ直さないと、デプロイブランチへ入る木が全検査を通ったことを誰も確かめない。

## 意図的に捨てるもの

- パターンを読む側が、宣言を解決せずに値を得られること
- AWS側に障害がある間もmergeできること
- 変更と無関係な理由でPull Requestがブロックされない状態
- 管理画面から保護設定を変更して即座に反映する運用
- commit message の見た目の均一さ
- 宣言の merge が、そのまま保護設定の適用になること
- 各検査が、ruleset の上で個別の required context として見えること（gate の宣言を読めば分かる）
- 昇格の Pull Request で、全検査を走らせ直すこと（線の検証に置き換える）
- 検査の workflow が、単独で `pull_request` によって起動すること

## 保証範囲

- 保証すること: CI の起動条件と、ref を比べる式について、分岐のパターンの出所が単一であること。
  宣言された保護設定が、突合の検査を走らせた時点で実態と一致すること。ruleset が直接 required とする context が、
  その ruleset の対象の Pull Request で必ず報告されること。gate が成功したとき、宣言が走るべきとした検査が、すべて
  同じ run で成功していること。env を持つデプロイブランチへ入る commit に、線の検証の成功が付いていること。
  merge されたものについて、適用内容がplanとして確認されていること
- 保証しないこと: 突合の検査を走らせていない間に生じたずれ。planの成功が、applyの成功を意味すること。
  commit message の内容が変更を正しく説明していること。merge から管理者による適用までの間に、宣言と
  実態がずれること（決定30）。検査の後にデプロイブランチかデフォルトブランチが進み、merge の結果が
  検査した木と違うこと（決定31。required check は base の更新を要求しない）。Pull Request が検査の job の
  定義を書き換えること（決定31。検査のコードと宣言は base の commit のものだが、job の定義は Pull Request
  の側のものである）。`env:` へ移した ref の値や、シェルの中の変数を、宣言の外の文字列と比べること。
  規範と説明の文書がブランチの名前を持つこと（決定2 の4つ目の読み手は検査しない）。
  承認者数の実態が宣言と一致すること（決定7・21）。検査と path の対応の宣言が、検査の実際の入力を覆っていること
  （覆っていなければ gate は省き、線の検証が線の push で走らせる）。宣言の「木だけで決まる検査」の分類が正しい
  こと。同じリポジトリの Pull Request が、gate や線の検証と同じ名前の context を自身の job で報告すること
  （決定34）。同じ commit に同じ名前の gate の check が複数あるとき（取り消しと再実行）の、必須の判定

## 検証方法

- Static Analysis（make repo-settings-check）: workflow と composite action の起動条件の `branches` /
  `branches-ignore` の一覧が、決定1 の宣言から生成されていること。式（`${{ }}` と `if:` の値）が、ブランチの
  名前か ref を値に持つ値（`github` と `inputs` の下の値と、それを関数や演算で加工した値。見分ける規則は
  make repo-settings-check の検査が持つ）を、宣言から生成していない文字列と比べていないこと。式として
  読めないものは合格にしない
- Unit Test: 宣言を実行時に読むツール（base-branch / release / repo-setup）が、宣言のブランチの名前を
  変えた入力に追随すること
- 突合の検査: 宣言と実態の差分が存在しないこと（決定4）
- 整合の検査（make required-check-lint）: 決定19 の各項目。件数は両方向で突き合わせる（決定16-20・38）
- Unit Test（scripts/ci-gate）: gate が決定18 の各入力で失敗すること。宣言が0件・読めないとき、走るべき検査の
  集合を決められないときを含む
- Static Analysis（make repo-settings-check）: 各 ruleset の対象が宣言から生成されていること。共通の ruleset の
  対象が、保護対象の全集合であること。env を持つデプロイブランチごとに ruleset がちょうど1つあり、その required が
  生成した一覧であること
- 突合の検査: 各 ruleset について、宣言と実態の差分が無いこと。宣言に無い ruleset が実在しないこと
- Static Analysis: 宣言に bypass の列挙が存在しないこと（決定22）
- Static Analysis: environment の宣言で、管理者による保護の迂回が無効であること（決定4・22）
- Static Analysis: 決定23 が挙げる各設定と、code owner による review の要求が宣言に存在すること、および宣言の承認者数が1以上であること（決定21）
- 整合の検査（required の deploy-source-check）: デプロイブランチへの Pull Request について、デフォルト
  ブランチが宣言の線であり、head がデフォルトブランチから到達でき、merge の結果の木が head の木と
  一致すること（決定31）
- 整合の検査（make required-check-lint）: sandbox の apply の context を報告する job が実在し、その
  workflow の pull_request にフィルタが無いこと（決定16・33）
- 整合の検査（make repo-settings-check）: 宣言の required の context が、すべて GitHub Actions の
  integration_id を持つこと（決定34）

## 影響

- 保護設定の変更は、宣言の変更とその適用として行われる。管理画面での変更は、次に突合の検査を走らせたときに差分として現れる。
- AWS側の事情でPull Requestがマージできない時間帯が生じ得る（決定14）。
- commit message の形式は検査の設定ファイルが持ち、ADRは関与しない。
- 宣言を変える Pull Request は、merge の後に管理者が適用する手順を残す（決定30）。
- 線への merge のたびに、線の検証が全検査を1回走らせる。
- 昇格の Pull Request は、線の検証が終わるまで merge できない。
- ruleset の適用は複数になり、適用と突合は ruleset ごとに行う。
- gate の定義が壊れると、すべての Pull Request の merge が止まる（決定18）。

## 見直し条件

- planの赤が、変更の外の理由で恒常的に発生するようになった場合（決定15）
- メンテナの人数が変わり、承認者数の要件を見直す場合
- 報告されなかった context の扱いが、ホスティングサービス側で変更された場合
- 分岐のパターンを読む側が増え、単一の宣言では表現しきれなくなった場合
- workflow_run の job か、API で付けた status が必須の判定に数えられると文書化された場合
- merge queue か workflows の規則が、このリポジトリで使えるようになった場合
- 報告した workflow を区別できる `integration_id` の手段が得られた場合
- 線の ruleset の gate が待つ plan の数が増え、待ちが長くなった場合
