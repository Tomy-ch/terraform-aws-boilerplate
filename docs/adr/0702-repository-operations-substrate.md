# ADR-0702: リポジトリ運用機構を独立した区分とし、Goで実装する

- Status: Accepted
- Date: 2026-09-16
- Scope: repository-wide
- Related: ADR-0001, ADR-0401, ADR-0501, ADR-0402, ADR-0302, ADR-0603, ADR-0103, ADR-0601, ADR-0503, ADR-0504

## Context

ADR-0501 決定4 は、Terraformコードの故障モードごとに道具を割り当てた。しかしその表が扱わない検査対象が存在し、いずれも現在は所有者を持たない。

- ADRの構造（ADR-0001 検証方法が要求するファイル名規約、メタデータの存在、`Superseded by` の参照先の実在）
- CI定義そのもの（workflow、composite action、それらが起動する条件）
- 依存の固定（`uses:` の参照先、container image、ツールのversion）
- ブランチ運用（起点の解決、リリース線の表現）
- 保護設定の宣言と実態の突合（ADR-0603）
- CI からの outbound 通信の制限

これらはTerraformコードの正しさではなく、**リポジトリ自身の構造と運用**についての検査である。ADR-0501 決定4 の表へ足すのは筋が悪い。同表は「Terraformコードのどの故障モードを誰が検出するか」を述べており、対象が違う。

一方、これらを放置すると、ADR-0001 が自ら定めた検証方法が実行されないまま残る。ADR-0401 決定3 は検証できない決定を不完全とみなすが、**決定の側ではなく検査器の側が不在**という形で同じ状態が生じている。

既製品で覆える範囲もある（workflowの構文検査、template injection の検出、秘密の検出）。しかし本リポジトリ固有の宣言を入力とする検査（ruleset の宣言と実態の突合、固定の drift 検出、ADRの構造）には、既製品が存在しない。ADR-0501 決定3 の3条件のうち第1条件（既存ツールで実現できない）を満たす領域がここに限って存在する。

したがって、自前実装を置くための区分と、その実装言語、そして検査器自身が守るべき規律を決める必要がある。**検査器の故障は、エラーではなく「緑」として現れる**ため、規律を後回しにすると、動いていない検査が動いているように見える状態が残る。

## Decision

### 区分

1. 「リポジトリ運用機構」を、ADR-0501 決定4 のレイヤーとは独立した区分として定義する。対象は、Terraformコードの正しさではなく、リポジトリ自身の構造・CI定義・依存の固定・ブランチ運用・保護設定・outbound 制限を検査または適用するものとする。人が手元から terraform を動かす入口が terraform に渡す値を算出し、検証するものも対象とする。人が手順書の完了条件として実行し、実環境の状態を読んで期待と突き合わせる確認も対象とする。人が手順書の手順として実行し、実環境へ書き込む操作（以下、手順の実行）も対象とする。
2. 本区分はADR-0501 決定4 の表を変更しない。Terraformコードの検証の権威は同表が持ち続ける。運用機構が同表のレイヤーを代替または補完しない。

### 境界

3. 運用機構の有無で、`terraform` を実行できるかどうかを変えない。`terraform fmt` / `validate` / `test` / `plan` / `apply` は、運用機構が1つも動作しない状態でも、人が同じ引数と値を与えれば成功しなければならない。検査と CI の入口では、運用機構が terraform を起動してよい。そのとき起動の引数は段ごとに固定し、運用機構が持つのは、terraform に渡す値の算出と、起動の順序と、出力の判定だけとする。
4. 決定3 の理由は、運用機構の故障がインフラの操作不能を意味しない状態を保つことにある。障害対応で必要になるのは apply であって lint ではない。
5. 運用機構をCIの必須検査に含めてよい。決定3 が求めるのは運用機構なしで terraform を実行できることであって、ゲートとしての採用を妨げるものではない。両者を混同しない。

### 実装言語

6. 実装言語をGoとする。
7. 理由は、ADR-0501 決定32 がTerratestを次段階の導入対象としており、**Goはいずれ本リポジトリへ入るため**である。運用機構をGoで書けば言語ランタイムは増えない。他の言語を採ると純増になる。ADR-0205 決定6 が依存管理の対象をproviderとTerraform本体に寄せている方針と整合する。
8. 既製の単一バイナリで足りるものを自前実装しない。ADR-0501 決定3 の3条件を本区分にも適用する。
9. 少なくとも次は既製品を用いる。自前実装の対象としない。

   - workflow の構文および `run:` のシェル検査
   - template injection の検出
   - 秘密の検出（ADR-0302 決定1・2）

### 形

10. 宣言を1箇所に置き、適用がそれを各所へ書き込み、検査が drift で落ちる形を採る。同じ値を複数箇所へ直接記述しない。
11. **検査は適用と同じ判定を、書き換えなしで実行する。** 検査と適用を別実装にしない。別実装は、検査を通るが適用で壊れる状態、およびその逆を生む。
12. 可能な場合、宣言そのものを検査の入力とする。宣言と検査が同じ記述を読む構造を優先する。

### 検査の規律

13. **検査対象が0件の場合、成功として終了しない。** 非ゼロで終了する。「ゲートが外れた」と「合格した」を区別できない状態を作らない。
14. **解釈できない入力は、取りこぼしではなくエラーとして扱う。** 検査が黙って対象範囲を縮めることを許さない。
15. 抽出を伴う検査は、抽出した件数を独立した経路で得た件数と突き合わせる。片方の経路が壊れたときに件数差として現れる形にする。
16. **検査ロジックを entry point から分離し、テストを持つ。** 検査器が検査をやめたとき、報告されるのはエラーではなく緑であるため、検査器自身の検証を省略できない。ADR-0402 決定7-9 がPolicyに対して要求していることを、本区分の全機構へ適用する。
17. テストのフィクスチャは一時ディレクトリへ構築する。リポジトリの実物を入力にしない。実物を読むテストは、リポジトリの今日の内容によって通ったり落ちたりするようになり、機構についてのテストであることをやめる。ただし、写しと正本のずれを検出する検査は、その正本である実物を読んでよい。
18. 検査を迂回する宣言（バイパス）を設ける場合、次をすべて満たす。

    - 期限を必須とする。期限の無いバイパスを認めない
    - 期限の上限を、宣言した時点から3ヶ月とする。遠い将来の期限は恒久的な許可と区別できない
    - 期限切れ、上限超過、および**対象が存在しないエントリ**は、ゲートを落とす
    - **期限は宣言が変わらなくても訪れるため、この検査を定期実行にも載せる。** Pull Request契機のみでは期限切れを誰も踏まない

19. 本区分の検査もADR-0501 決定26 に従い、権威をCIに置く。ローカルのhookは迂回される前提で設計し、**hookでのみ成立する検査を作らない**。

### outbound 制限

20. CI のすべての job は、最初の step で runner の外向き通信を許可リストへ固定する。最初の step が落ちたときに限り、2番目の step で待ってから apt の索引を更新し、同じ設定の3番目の step で1度だけやり直す。2番目の step は生成した固定の字面で、sudo を apt の索引の更新だけに使い、時間の上限を持ち、その失敗は job を落とさない。3番目の step が落ちれば job は落ちる。間を置かないやり直しは、数秒以上続く取得の失敗と、runner の apt の索引に無いパッケージを吸わないためである。最初の3つの step の後で status の関数（`always()`・`failure()`・`cancelled()`）を持つ step の `if:` は、最初か3番目の step が成功したことを先頭の条件に持つ。status の関数は暗黙の成功の条件を外すので、無ければ最初と3番目の step が2つとも落ちた job で、通信の制限の無いまま走る。`oidc-job-lint` と `contents-write-lint` は、生成した三つ組の6行（最初の step の `continue-on-error:`、2番目の step の `if:`・`continue-on-error:`・`timeout-minutes:`・`run:`、3番目の step の `if:`）を見逃す。見逃すのは、`make egress-check` が生成の形と一字一句同じであることを求める行に限る。許可リストは決定10 の形で持つ —— 宣言は `.github/egress.toml`、適用は `make egress-apply`、検査は `make egress-check` である。Terraform を実行する job の許可リストは、その root が使う resource / data source の型が呼ぶ宛先を含む。`make egress-check` は、usecase の `reference/` の root でも、ブロックの `region` を解けることを確かめる。reference の root が無いか、reference の root を持たない usecase（ADR-0401 決定11）があれば落ちる。CI の root がその usecase を呼ぶ前に、解けない形をその usecase の変更で落とすためである。
21. 名前解決も、許可したドメインに限る。遮断を始めた後の step に sudo を残さない。sudo が残る job では、step の中から通信制限そのものを外せる。決定20 の2番目の step は例外とし、生成した固定の字面で sudo を apt の索引の更新だけに使う。
22. 手段は `bullfrogsec/bullfrog` とする。契約なしで遮断し、`api-token` を渡さなければ接続の記録を外へ送らない。
23. 手段の挙動についての本 ADR の記述は、`.github/actions-pin.toml` が固定した版のソースから読んだものとする。版を上げる Pull Request は、その記述を確かめ直す。

### 起動の分担

24. 運用機構の1回の起動は1つの目的を持ち、その目的の道具だけを起動する。目的の違う道具（例: plan を作る `terraform`、全文を置く `aws`、Policy を掛ける `conftest`）を1回の起動の中で続けて呼ばない。目的の間の順序と値の受け渡しは make が持ち、値の算出と判定は運用機構が持つ。複数の目的を1回の起動に抱えると、各目的の失敗の扱いが1つのコマンドに埋もれ、目的ごとに差し替えることもテストすることもできなくなる。前の目的の結果によって後の目的を省くかどうかも判定であり、運用機構が持つ。後の目的の入口が、前の目的の結果を読んで何もせずに終える形にする。
25. make のレシピは、運用機構と道具を決まった順に呼び出すことと、軽い条件分岐だけを持つ。判定・計算・繰り返しと、特定の処理を行うスクリプトはレシピに置かない。レシピが処理のスクリプトを持った時点で、その機構を丸ごと運用機構の Go へ置き換える。テストは運用機構の Go のテストが持ち、`.mk` にテストを書かない。検査が落ちるべき入力で落ちることを確かめる canary は、その検査を走らせる運用機構の Go が、本走査の前に同じ起動の中で走らせる。canary が落ちれば本走査を行わずに失敗する。canary を make のターゲットとして別に置かない。ADR-0601（change-delivery-path）決定18 の書き込みの job が呼ぶレシピは、その job が道具を導入しないので、運用機構へ置き換えず、runner に在るコマンド（`git`・`gh`）を決まった順に呼び出す形にする。
26. 決定1 の確認と手順の実行は、その目的の道具として `aws` を起動してよい。手順の実行に限り、GitHub の environment に secret を置くために `gh secret set` を、置いたことを確かめるために `gh secret list` を起動してよく、値は標準入力で渡す。確認が起動する操作は読み取り（get・list・describe・head と、権限の評価の simulate）に限る。資格情報を変える環境変数を外すことと、使う profile と region を渡すことは make が持ち、外す変数の一覧は人が terraform を動かす入口と同じものを使う。運用機構は profile が渡されなければ確認と手順の実行をせずに終える。実環境の資格情報を使うので、ホストで実行する（ADR-0504 決定1・3 と同じ理由）。
27. 手順の実行は、1回の起動の中で、前提と現状を読み取りで確かめ、書き込む差分を示し、人の確認の入力を受け、書き込み、読み取りで結果を確かめる。起動する書き込みの操作は、入口ごとに運用機構が閉じた一覧として持ち、一覧の外の操作を組まない。現状が既に望む状態であれば何も書かずに成功で終え、前提が崩れていれば書かずに非ゼロで終える。取り消せない操作と、apply との順序の縛りがある操作は、確認の入力に project の名前の打ち込みを求める。標準入力が端末でなければ書かない。秘密になる値は、引数と shell の履歴に残さず端末から読み、aws へは権限を所有者に限った一時ファイルで渡す。手順書は make の入口を名指し、コマンドを写さない。値を手で組み、コマンドを写す手順は、組み違いと手順の飛ばしを何も検出しないためである。実環境への書き込みは人が実行し、エージェントは手順の実行を起動しない（AGENTS.md のトリップワイヤ8 と同じ理由）。

## 検討した代替案

### 案A: TypeScriptで実装する

YAML・TOML・JSONの取り扱いに不足はなく、記述量も小さい。ただし本リポジトリはNode.jsのランタイムを持たず、これを採ると言語ランタイムが純増1になる。Terratest導入時にGoも入るため、最終的に2つを抱えることになる。検査の内容にTypeScript固有の要求は無く、純増を正当化する根拠が見当たらない。

### 案B: シェルスクリプトで実装する

追加のランタイムが不要で、CI上の起動も速い。ただし本区分の検査はYAML・TOML・JSONの構造を読む処理が中心であり、シェルでは外部コマンドの連鎖になる。決定16（検査ロジックの分離とテスト）を満たす形にしにくく、決定14（解釈できない入力をエラーとする）の実装も脆くなる。

### 案C: 運用機構を持たず、既製品で覆える範囲に限る

実装資産が増えない。ただしADR-0001 が自ら定めた検証方法、ruleset の宣言と実態の突合、固定の drift 検出は、いずれも本リポジトリ固有の宣言を入力とするため既製品が存在しない。結果としてADR-0401 決定3 の状態（検査器が不在のまま規範だけが残る）が継続する。

### 案D: outbound 制限の手段を `step-security/harden-runner` とする

無料版は public リポジトリでしか遮断せず、private では step が緑のまま遮断しない。遮断の開始直後に許可済みの宛先への接続が失敗し、全 step の終了後に job が完了を報告しないまま残る失敗がある。

### 案E: outbound 制限の手段を GitHub 純正の egress firewall とする

hosted runner 向けは technical preview であり、設定の形式が変わると予告されている。

### 案F: outbound 制限の手段を自前で実装する

runner の DNS 構成の変更（egress proxy による `/etc/resolv.conf` の書き換え）に追随し続ける費用を負う。決定8 の既製品で足りる範囲に当たる。

### 案G: make のレシピを対象とするテストを、運用機構の Go のテストとして書く

レシピを `make -n` で展開して引数を数える、偽の道具を置いてレシピを実走させる、といった形で、レシピの振る舞いを Go のテストで固定する。テストの書き方は決定16 の規律に乗る。ただし、テストが要るのはレシピが判定・分岐・繰り返しを持つからであり、テストを Go に置いてもその判定はレシピに残る。判定の在処が make と Go の2か所に割れ、Go のテストは make の展開と実行の細部に結び付く。レシピを起動の列だけにすれば、レシピに確かめる振る舞いは残らず、このテストは要らなくなる。

### 案H: 既存の `.mk` のテストを、期限つきの例外として残しながら移す

`.mk` のテストを一覧に載せ、期限の間は検査から外し、ロジックを移すたびに一覧から消す。移す前に検査を必須にできる。ただし、一覧はテストを置く形そのものを期限まで正当化し、新しい規則の下でも同じ形の追加を許す前例になる。ロジックを移す変更の中でテストを同時に消し、移し終えた範囲から検査を掛ければ、例外を置かずに済む。

### 評価

| 評価軸 | 案A: TypeScript | 案B: シェル | 案C: 持たない | 採用案: Go |
| --- | --- | --- | --- | --- |
| Security | 中 | 中 | 低（宣言と実態がずれ続ける） | 高 |
| Testability | 中 | 低（分離しにくい） | 低（検査器が不在） | 高 |
| Contract Clarity | 中 | 中 | 低 | 高 |

| Maintainability | 中 | 低 | 高 | 中 |

## 意図的に捨てるもの

- 運用機構を持たないことによる実装資産の少なさ
- 検査の記述量を最小にすること
- ローカルのhookだけで完結する運用
- 処理のスクリプトを `.mk` の中に書いて済ませる手軽さ
- レシピの振る舞いをテストで固定する手段。レシピは起動の列だけにし、確かめる振る舞いを持たせない

## 保証範囲

- 保証すること: 運用機構が動作しない状態でも `terraform` の各コマンドが成功すること。配線された運用機構がテストを持つこと。検査が対象を持たないまま成功を報告しないこと
- 保証しないこと: 運用機構が検出しない構造上の誤りが存在しないこと
- 保証しないこと（決定25）: `.mk` が処理のスクリプトとテストを持たないこと。レビューが持つ
- 保証しないこと（決定26）: 確認の表が手順書の完了条件を漏れなく覆うこと。対応はレビューが持つ
- 保証しないこと（決定27）: 手順書の書き込みの手順を漏れなく入口が覆うこと。対応はレビューが持つ
- 保証しないこと（決定20-22）: port による絞り込み。bullfrog は宛先の IP で判定するため、許可したドメインの IP へは任意の port で繋がり、同じ IP を共有する別のホストへも繋がる。`*.example.com` は添字の回る宛先をまとめて許す。agent が既定で許す宛先（runner の結果と cache の置き場）は宣言に現れない
- 受け入れた限界（決定22）: 上流の保守の継続を本リポジトリは保証しない。agent に SLSA provenance が無く、action の SHA が固定する sha256 だけで検証される。遮断の前に `nftables` を版の固定なしに `apt-get` で取る。最初の step が落ちたときは、その前に apt の索引を更新する（決定20）。最初の step が agent を起動した後で落ちた場合、待った後の3番目の step は、sudo を外された後の導入で落ちうる。安全側に落ちるが、遅れて起動した agent の準備の印で成功する経路は失う。GitHub-hosted の Ubuntu runner 専用である

## 検証方法

- Static Analysis: 運用機構が起動する terraform の引数が段ごとに固定されていること（決定3。各道具のテストが引数の列を固定する）
- Static Analysis: 各運用機構にテストが存在すること（決定16）
- 各機構のテスト: 対象0件の入力に対して非ゼロで終了すること（決定13）
- 各機構のテスト: 解釈できない入力に対してエラーを返すこと（決定14）
- 各機構のテスト: 確認が組む aws の操作が読み取りの動詞に限ること、profile が渡されなければ確認と手順の実行をせずに終えること（決定26）
- 各機構のテスト: 手順の実行が組む書き込みの操作が、その入口の一覧に限ること。確認の入力が無いとき、前提が崩れているとき、標準入力が端末でないときに書き込みを組まないこと。既に望む状態のときに書き込みを組まないこと（決定27）
- `egress-check`: steps を持つ job に bullfrog の step が無いこと、それが最初の step でないこと、2番目の step が、最初の step が落ちたときだけ待って apt の索引を更新する生成済みの形でないこと、3番目の step が、最初の step が落ちたときだけ同じ設定で走り、自身の失敗で job を落とす形でないこと、3番目の step の後ろで status の関数を持つ step の `if:` が、最初か3番目の step の成功を `&&` で先頭に持たないか、その後ろの括弧の外に `||` を持つこと、status の関数を名指す行が読めた `if:` の式の外にあること、`enable-sudo: false` を含む生成済みの `with:` からずれていることで落ちる（決定20・21）。宣言の root が module を辿って使う resource / data source の型が宣言の type に当たらないこと、root が呼ぶ type の宛先を root を実行する job の許可リストが持たないこと、type の宛先を許す job がどの root にも名指されていないこと、job が CI の plan / apply の入口を通して実行する root と宣言の root がその job を名指す先が食い違うこと、root が type の resource / data source を置く region（ブロックの `region` 引数のリテラル。持たないブロックは root の aws の provider のただ 1 つの region）に、その region を含む type の宛先が無いこと、region を含む type の宛先の region に、どの root もその type を置かないこと、ブロックの `region` 引数が region の形のリテラルでないことでも落ちる。ただし、AWS が region を固定した global のサービスの宛先（organizations.us-east-1.amazonaws.com）は、運用機構が閉じた一覧として持ち、この突き合わせから外す（決定20）
- 定期実行: バイパス宣言の期限検査が、Pull Request契機とは独立に実行されること（決定18）
- レビュー: 決定8・9（既製品で足りるものを自前実装しない）は機械判定できない。運用機構を追加するPull Requestのレビュー観点とする
- レビュー: 決定22・23（手段の挙動）は機械判定できない。`bullfrogsec/bullfrog` の版を上げるPull Requestのレビュー観点とする
- レビュー: 決定24 のうち、1回の起動の目的が1つであることは機械判定できない。決定25 のうち、`.mk` が処理のスクリプトとテストを持たないことも機械判定できない。make のレシピか運用機構を足すPull Requestのレビュー観点とする

## 影響

- 本リポジトリはGoのツールチェーンを持つことになる。versionはADR-0501 決定19 に従い pin する。
- ADR-0001 の検証方法に、初めて実行者が与えられる。
- 運用機構を追加するたびに、その機構自身のテストが必要になる。

## 見直し条件

- Terratestの導入が見送られ、Goが本リポジトリへ入る理由が運用機構だけになった場合
- 本区分の検査を覆う既製品が現れた場合
- 運用機構の規模が、単一の言語とディレクトリでは管理できなくなった場合
- GitHub 純正の hosted runner 向け egress firewall が public preview 以上になり、本リポジトリで使えるようになった場合（決定22）
- bullfrog の更新が止まるか、sudo や DNS の迂回についての advisory が修正されないまま残った場合（決定22）
- bullfrog が agent の取得とパッケージの導入を、待ちと apt の索引の更新を伴って再試行するようになった場合（決定20 の2番目と3番目の step と、status の関数を持つ step の先頭の条件を外す。`oidc-job-lint` と `contents-write-lint` が生成した三つ組の6行を見逃す例外も、同じときに外す）
