# ADR-0201: CI の role の権限を、Provider が呼ぶ API から導いた Action の列挙で与える

- Status: Accepted
- Date: 2026-10-25
- Scope: deployment-identity
- Related: repository-wide/ADR-0602, repository-wide/ADR-0604, repository-wide/ADR-0301, repository-wide/ADR-0402

## Context

repository-wide/ADR-0602 (bootstrap-and-ci-authentication) 決定16 は、apply の role の権限の与え方（Action の列挙か permissions boundary か）を use-case の ADR に委ねる。同 決定13 は、plan の role に変更系の権限を与えず、apply の role に bootstrap の構成物を変更する権限を与えないことを求める。repository-wide/ADR-0604 (state-split-by-apply-role) 決定8-10 は、plan の role が state にも lock file にも書かないこと、apply の role が自分の root の key と lock file にだけ書けること、apply の role が state Bucket の設定を変更する有効な権限を持たないことを求める。同 決定13 は、lock の解除の role に、lock file の一覧・読み取り・削除と、その lock file の復号だけを持たせる。

AWS Provider は、resource の refresh で、設定していない属性の API も呼ぶ。6.70.0 の `aws_s3_bucket` の Read は、Bucket の Policy・ACL・CORS・website・版管理・accelerate・request payment・logging・lifecycle・replication・暗号化・Object Lock・tag を読み、拒否を許容しない。読み取りの権限が1つ欠けると、plan は AccessDenied で失敗する。apply-identity の role の読み取りが欠けると、その role 自身の policy を直す apply が refresh で失敗し、repository-wide/ADR-0602 決定9 の回復の契機になる。

管理アカウントの identity root は、統制の構成物（repository-wide/ADR-0602 決定1）を持つ `organization-baseline` も呼ぶ。apply-identity の role は、それを変更する権限を持つ。apply の role は持たない（同 決定13、repository-wide/ADR-0604 決定10）。Organizations と root の資格情報の中央管理には、resource-level の権限を持たない書き込みの Action（`organizations:CreateOrganization`・`EnableAWSServiceAccess`、`iam:EnableOrganizationsRoot*` など）がある。これらは Resource の ARN ごとの Deny では拒めない。

workload root の usecase（`ops-notification`）は、SNS の Topic、KMS の鍵、EventBridge Scheduler の schedule、Amazon Q Developer in chat applications（以下 Chatbot）の Slack の channel の構成と、それらが使う IAM の role と customer managed policy を作る。apply の role が IAM の role を作り、その role に権限を書ける時点で、apply の role は作った role を経由して、自分に Deny された bootstrap の構成物と統制の構成物へ届きうる。AWS は、他者に role の作成を委ねるときの機構として permissions boundary を示す（IAM User Guide「Permissions boundaries for IAM entities」の「Delegating responsibility to others using permissions boundaries」）。委ねられる側は、決めた boundary を付けるときだけ作成と変更ができ、boundary の policy の変更と boundary の除去を拒まれる。boundary は role の ARN を名指す resource-based policy の許可も削る（同文書「Resource-based policies for IAM roles」）。IAM の inline policy は role あたり 10,240 文字、customer managed policy は1つ 6,144 文字が上限で、permissions boundary は role に1つしか付かない。

## Decision

1. 5つの role の権限を、role ごとの inline policy に Action を列挙して与える（apply の role の workload の権限は決定17 の customer managed policy に置く。未配線で、PR-2b（#25）で配線する）。Allow の文に `*` と `service:*` の Action、`"*"` の Resource、部分的なワイルドカード（`s3:GetBucket*` 等）を使わない。5つの role に permissions boundary を課さない（apply の role が作る role には決定14 で課す）。ただし、resource-level 権限を持たない Action（Service Authorization Reference で判定する。`kms:ListAliases`）は、`"*"` の Resource を Action ごとの別の文で与える（repository-wide/ADR-0301 (least-privilege-policy) 決定9）。Key Policy の書き込みでの lockout の安全チェックの迂回（`kms:BypassPolicyLockoutSafetyCheck`）は Deny で拒む。
2. 列挙は、identity root の resource について AWS Provider 6.70.0 の source（`internal/service/s3`・`internal/service/iam`・`internal/service/kms`、管理アカウントの apply-identity と plan の role では `internal/service/organizations`・`internal/service/cloudformation` も）の Read・Create・Update・Delete が呼ぶ API から導く。対応は下の表が持つ。Provider の版を上げる変更は、この表を見直す。
3. 権限は段4 の構成物と、決定13 の workload root の usecase の構成物（段4 の構成物は OIDC provider、5つの role と inline policy、state Bucket の段1-4 の設定とその lifecycle、plan の出力の Bucket とその lifecycle、workload root の apply の出力の Bucket（CI の apply-identity が作る）、state の鍵（鍵、Key Policy、alias））に要る分に限る。identity root に構成物を足す変更は、その構成物に要る権限を足す変更を先に merge する。apply-identity の role に、鍵と alias を作る権限は与えない。state の鍵と alias は、新しいアカウントでは段4 の apply が一時 IAM user の権限で作る。state の鍵と alias の作り直しは CI では行えず、要るときは作成の権限を足す変更を先に merge する。apply の role は workload の鍵を作る（決定13。未配線で、PR-2b（#25）で配線する）が、state の鍵とその alias は決定5 の Deny で変えられない。5つの role の暗号操作は IAM では与えず、state の鍵の Key Policy が role を名指して許す（repository-wide/ADR-0301 (least-privilege-policy) 決定12）。 管理アカウント（env が `admin`）の apply-identity の role には、加えて `organization-baseline` の構成物に要る分を与える。対象は、組織・OU・policy とその付け先、IAM の信頼アクセス、root の資格情報の中央管理、break-glass の IAM user・group・role、IAM の password policy、メンバーアカウントへ break-glass の role を配る CloudFormation の StackSet とその stack instance である。StackSet の名前は break-glass の role の名前と同じとし、Resource をその StackSet の ARN（末尾の ID は pattern）に限る。次の3つは意図して与えない: 組織の削除（`organizations:DeleteOrganization`）、メンバーの閉鎖（`organizations:CloseAccount`・`account:CloseAccount`）、組織からの除外（`organizations:RemoveAccountFromOrganization`）。`prevent_destroy` と `plan.stateful_protection` に加えて、権限の側でも止める。サービスが service-linked role を作る Action のために、`iam:CreateServiceLinkedRole` を `iam:AWSServiceName` の条件で該当するサービスに限って与える。env が `admin` でない role には、これらを与えない。統制の構成物の作成と設定の権限は、決定7 の customer managed policy に置く。読み取りは plan の role と同じ文で inline policy に置く。
4. Resource は、state Bucket と plan の出力の Bucket と apply の出力の Bucket の ARN とその key、5つの role と OIDC provider、state の鍵で限定する。role の ARN は、resource 参照ではなく、partition・アカウント・role 名から組んだ完全な ARN で書く。prefix の pattern ではないので、repository-wide/ADR-0301 (least-privilege-policy) 決定11 の対象ではない。apply-identity の role の inline policy は、他の role より先に書き込む。他の role の作成は、apply-identity の inline policy の書き込みに依存させる。role を足す変更は、1回の apply で、その role を管理する権限を apply-identity へ足してから role を作る。state の鍵の ARN は入力の `state_key_arn`（`state-backend` の出力）で受け、role と同じ partition・リージョン・アカウントの鍵であることを plan で（ARN が plan で決まらなければ apply で）確かめる。 `organization-baseline` の構成物の Resource は、作る前に組織の ID が決まらないので、ARN の pattern で書く。例: `arn:<partition>:organizations::<管理アカウント>:ou/o-*/ou-*`。pattern は repository-wide/ADR-0301 決定11 の対象で、その根拠をこの決定に置く。break-glass の IAM の Resource は、path（`/break-glass/`）と名前から組んだ完全な ARN で書く。メンバーへ break-glass の role を配る StackSet の Resource は、ARN の末尾の ID が作るまで決まらないので、`stackset/<名前>:*` の pattern で書く。StackSet の書き込みと stack instance の操作が要る stackset-target の resource は、同じ理由で `stackset-target/<名前>:*` で書く。type の resource は、StackSet のテンプレートが作る型（`AWS::IAM::Role`）に限り、アカウントを `*` にした `type/resource/AWS-IAM-Role` で書く。AWS の resource 型の ARN はアカウントを持たないことがあるからである。stack instance の操作は `cloudformation:TargetRegion` を provider の region に限る。`UpdateStackSet` には条件を付けない。region を渡さない更新の要求は、このキーを持たず、`StringEquals` で拒まれるからである。
5. apply の role に、次を Deny で与える（repository-wide/ADR-0301 (least-privilege-policy) 決定8 は Deny の wildcard を許す）。名前が `<project>-<env>-ci-` で始まる IAM の role と customer managed policy（`role/<project>-<env>-ci-*`・`policy/<project>-<env>-ci-*`。5つの role、決定7 の統制の policy、決定15 の boundary、決定17 の policy を含む）と OIDC provider、identity root の key と lock file、plan の出力の Bucket とそのすべての object への、すべての Action（`*`）。CI の role と policy を名前の pattern で書くのは、CI の構成物が増えても文書が伸びず、apply の role が CI の構成物と紛らわしい名前の role や policy を作ることも、小文字で綴る限り拒むためである。IAM の Resource の照合は大文字・小文字を区別するので、この Deny は大文字で綴った ARN を拒まない。主な守りは、IAM の書き込みの Allow を小文字の usecase の接頭辞に限る決定13 であり、この Deny は二重の守りである。この pattern は repository-wide/ADR-0301 決定11 の対象で、その根拠をこの決定に置く。state Bucket への、`s3:ListBucket` と `s3:GetEncryptionConfiguration` を除くすべての Action（`NotAction`）。state Bucket のすべての object への `s3:DeleteObjectVersion`。state の鍵への、`modules/kms` が Key Policy でアカウントへ委任する管理の Action のすべて（repository-wide/ADR-0604 (state-split-by-apply-role) 決定10）。Deny を Action の列挙やサービスの wildcard（`s3:Put*`、`iam:*`）で書くと、AWS が足す変更系の Action（tag や metadata の設定）と、別のサービスの名前で同じ ARN を対象とする Action（role の ARN への `sts:AssumeRole`）を覆わない。S3・IAM の構成物への Deny は、`*` か、許す読み取りの名前だけを除く `NotAction` で書く。`s3:GetEncryptionConfiguration` を除くのは、init の前に運用機構が Bucket の既定の暗号化と鍵の一致を確かめるためである（state-backend/ADR-0101 決定3）。workload root の key と lock file への書き込みは apply の role が行うので拒まない。鍵の Deny は `kms:*` にしない。Key Policy が role を名指して許す暗号操作（決定3）まで塞ぐからである。KMS では IAM の Allow は Key Policy がアカウントへ委任した Action にしか効かないので、委任の Action を覆えば足りる。alias の削除と付け替えは鍵への権限も要るので、鍵の Deny が塞ぐ。以後 workload の usecase のための Allow を足しても、bootstrap の構成物、identity root の state、3つの Bucket の設定、state の版、plan の出力、state の鍵の設定を変えられないようにする。apply の出力の Bucket（決定12）への、すべての Action（`*`）。apply の出力の Bucket のすべての object への、`s3:PutObject` を除くすべての Action（`NotAction`）。ただし、apply の role の書き込み先として宣言した構成物の子（apply の出力の Bucket の object）への Deny は、その書き込みの名前だけを除く `NotAction` で書き、読み取りも除かない。 apply の role に、統制の構成物を変更する Action を Deny で与える（`DenyGovernanceChange`）。Resource は `"*"`、条件は付けない。対象は次の書き込みの Action である。Organizations は、書き込みの動詞（Accept・Attach・Cancel・Close・Create・Decline・Delete・Deregister・Detach・Disable・Enable・Invite・Leave・Move・Put・Register・Remove・Tag・Terminate・Untag・Update）を接頭辞で拒む。Account Management は `account:CloseAccount`。IAM は `iam:EnableOrganizationsRoot*`・`iam:DisableOrganizationsRoot*` と、password policy の書き込み（`iam:UpdateAccountPasswordPolicy`・`iam:DeleteAccountPasswordPolicy`）。Identity Center は permission set と割当の書き込み。CloudFormation は StackSet と stack instance の作成・更新・削除、既存の stack の取り込み（`cloudformation:ImportStacksToStackSet`）、操作の停止（`cloudformation:StopStackSetOperation`）と、組織への信頼アクセスの有効化と無効化（`cloudformation:ActivateOrganizationsAccess`・`DeactivateOrganizationsAccess`）。`cloudformation:TagResource`・`UntagResource` は拒まない。Resource `"*"` の Deny は、workload の stack と change set の tag まで塞ぐからである。STS は `sts:AssumeRoot`。読み取り（Describe・List・Get）は拒まない。委任管理者のアカウントの CI が、組織を読んで行う運用を塞がないためである。この Deny は、管理アカウントの外でも同じ文で置く。メンバーで Organizations の書き込みを呼ぶ正当な経路は、委任管理者の設定に限る。どの Action がそれに当たるかは、#22 の交差の表で確かめ、当たる Action をこの列挙から外すか、その委任をこの usecase の外で行うかを、その時点で決める。break-glass の IAM user・group・role の ARN には、`DenyBreakGlassChange` として Action `"*"` を Deny で与える。ARN は `organization-baseline` の出力 `break_glass_arns` で受ける。管理アカウントの決定7 の統制の customer managed policy も、名前が `<project>-<env>-ci-` で始まるので、5つの role と OIDC provider と同じ Deny（Action `*`）の対象に入る。workload の apply の role が、apply-identity の role に付く統制の権限を書き換えられないようにするためである。接頭辞で拒む Deny は、AWS が後から足す書き込みの Action の名前が、その接頭辞に当たる限りで覆う。当たらない名前の Action を覆わないことは、repository-wide/ADR-0602 の保証しないことに在る。 `DenyIdentityChange` から `DenyBreakGlassChange` までの Deny の文は、決定15 の boundary にも同じ文で置く（未配線。PR-2b（#25）で配線する）。apply の role の Deny を変える変更は、boundary の Deny を変える変更である。
6. apply-identity の role は、自分を含む5つの role の信頼条件と policy を変更できる。誤った信頼条件が apply されると CI は締め出され、回復は repository-wide/ADR-0602 決定9 の回復の契機になる。
7. CI の role に AWS managed policy を付けない。customer managed policy は、管理アカウント（env が `admin`）の apply-identity の role に、統制の構成物（決定3）の作成と設定の権限を持つ1つ（`<project>-admin-ci-apply-identity-governance`）を、apply の role に、workload の権限を持つ1つ（決定17。`<project>-<env>-ci-apply-workload`）を付ける（未配線。PR-2b（#25）で配線する）。ほかの3つの role と、env が `admin` でない apply-identity の role には、managed policy を付けない。 統制の権限を inline policy に置かないのは、IAM の role の inline policy の合計が 10,240 文字を上限とし、統制の分を足すと入力の境界でそれを超えるためである。AWS も、多くの場合に inline policy より managed policy を使うことを勧める（IAM User Guide「Choose between managed policies and inline policies」）。統制の権限が増えるとき（Identity Center の permission set と割当など）は、同じ役割の customer managed policy を足して伸ばす。そのときはこの決定の「1つ」を改める。 apply-identity の role には、その customer managed policy の作成・読み取り・版の更新・削除の Action を、Resource をその policy の ARN に限って inline policy で与える。対象は `iam:CreatePolicy`・`iam:GetPolicy`・`iam:GetPolicyVersion`・`iam:ListPolicyVersions`・`iam:ListPolicyTags`・`iam:CreatePolicyVersion`・`iam:SetDefaultPolicyVersion`・`iam:DeletePolicyVersion`・`iam:DeletePolicy` である。 自分の role への付け外しとして、`iam:AttachRolePolicy` を Resource を apply-identity の role の ARN に、条件 `iam:PolicyARN` をその policy の ARN に限って与える（`iam:DetachRolePolicy` は CI の role に既に与えている）。apply-identity の role が自分に付く policy を自分で変えられる性質は、inline policy と同じである（決定6）。 plan の role には、その policy の読み取り（`iam:GetPolicy`・`iam:GetPolicyVersion`・`iam:ListPolicyVersions`・`iam:ListPolicyTags`）を同じ ARN に限って与える。 customer managed policy の文書にも、決定1 と決定4 の Action と Resource の規則を当てる。 `aws_iam_role_policies_exclusive` と `aws_iam_role_policy_attachments_exclusive` で、帯域外で足された policy を次の apply で剥がす。apply-identity の role の `aws_iam_role_policy_attachments_exclusive` には統制の customer managed policy の ARN だけを、apply の role のそれには決定17 の policy の ARN だけを載せる（未配線。PR-2b（#25）で配線する）。 AWS managed policy は、管理アカウントの apply-identity の role が break-glass の role に `AdministratorAccess` を付けるもの（repository-wide/ADR-0301 決定19）のほかは付けない。そのために `iam:AttachRolePolicy`・`iam:DetachRolePolicy` を、Resource を break-glass の role の ARN に、条件 `iam:PolicyARN` を `AdministratorAccess` に限って与える。
8. plan の role に、plan の出力の Bucket の `pr/*` と `branch/*` の key への `s3:PutObject` を与える（repository-wide/ADR-0602 決定13 の例外）。Pull Request の plan と保護ブランチの plan を key の接頭辞で分ける。`s3:DeleteObject` と `s3:DeleteObjectVersion` は与えない。plan の出力を state の鍵で暗号化するのに要る `kms:GenerateDataKey` は IAM では与えず、Key Policy が plan の role を名指して許す（決定3）。
9. unlock-identity の role に、state Bucket への `s3:ListBucket`（Condition `s3:prefix` を identity root の lock file の key に `StringEquals` で限る）と、identity root の lock file への `s3:GetObject` と `s3:DeleteObject` だけを与える。列挙は Provider ではなく、lock を外す手順が呼ぶ API から導く。ListObjectsV2 は `s3:ListBucket` を、GetObject は `s3:GetObject` を要する。If-Match の条件付きの DeleteObject は `s3:DeleteObject` と `s3:GetObject` を要する。`s3:PutObject` と `s3:DeleteObjectVersion` を与えない。lock file の復号に要る `kms:Decrypt` は IAM では与えない。state の鍵の Key Policy が、この role を、暗号化コンテキスト `aws:s3:arn` で identity root の lock file の object に限って名指す（決定3）。この role は Deny を持たない。Allow を足すことを Policy Test が拒む。
10. apply-identity の role に、plan の出力の Bucket の `apply/*` の key への `s3:PutObject` を与える（repository-wide/ADR-0602 決定13）。plan の role の `pr/*`・`branch/*` と接頭辞を分け、Pull Request のコードが apply の出力を偽れないようにする。`s3:DeleteObject` と `s3:DeleteObjectVersion` は与えない。暗号化に要る `kms:GenerateDataKey` は、state の鍵の Key Policy が既に apply-identity の role に許している。列挙は Provider ではなく、apply の出力を置く手順が呼ぶ API（1回の PutObject）から導く。決定3 の構成物に要る分の外の権限である。
11. unlock の role に、state Bucket への `s3:ListBucket`（Condition `s3:prefix` を workload root の lock file の key に `StringEquals` で限る）と、workload root の lock file への `s3:GetObject` と `s3:DeleteObject` だけを与える。lock file の復号は、state の鍵の Key Policy が workload root の lock file の object に限って許す。列挙と与えないもの、Deny を持たないことは決定9 の unlock-identity の role と同じとする。identity root と workload root の lock の解除を別の role に分け、片方の environment から他方の root の lock に届かないようにする（repository-wide/ADR-0602 決定13 の「対応する root の lock file」）。
12. apply の role に、apply の出力の Bucket（state-backend/ADR-0201 決定7）の object への `s3:PutObject` だけを与える（repository-wide/ADR-0602 決定13）。その object へのほかの Action は決定5 で拒む。暗号化に要る `kms:GenerateDataKey` は、state の鍵の Key Policy が apply の role に許す。列挙は Provider ではなく、apply の出力を置く手順が呼ぶ API（1回の PutObject）から導く。apply-identity と plan の role は、この Bucket の設定を、state Bucket と plan の出力の Bucket と同じ列挙で読み書きする。
13. apply の role に、workload root の usecase の構成物に要る権限を与える（apply の role の Allow は決定17 の policy に置き、PR-2b（#25）で配線する。plan の role の読み取りと、apply の role の `kms:BypassPolicyLockoutSafetyCheck` の Deny は配線済み）。列挙は決定2 の方法で、Provider 6.73.0 の `internal/service/{sns,kms,scheduler,chatbot,iam}` から導き、対応は下の表が持つ。Resource は、usecase が構成物の名前の先頭に置く `<project>-<env>-` の pattern（例: 14. apply の role が作る IAM の role には、決定15 の permissions boundary を必ず付けさせる（`iam:DeleteRolePermissionsBoundary` の Deny は配線済み。ほかは決定17 の policy に置き、PR-2b（#25）で配線する）。`iam:CreateRole`・`iam:PutRolePolicy`・`iam:AttachRolePolicy`・`iam:PutRolePermissionsBoundary`・`iam:DeleteRolePolicy`・`iam:DetachRolePolicy`・`iam:DeleteRole`・`iam:UpdateAssumeRolePolicy`・`iam:UpdateRole`・`iam:UpdateRoleDescription` を、条件 `iam:PermissionsBoundary` を決定15 の boundary の ARN のいずれかに `StringEquals` で限って与える（Service Authorization Reference で、これらの Action はこの条件キーを受ける）。boundary を持たない role（5つの CI の role、break-glass の role、service-linked role、AWS が作る role）は、この条件で変更できない。条件キーを受けない読み取り（`iam:GetRolePolicy`・`iam:ListRolePolicies`・`iam:ListAttachedRolePolicies`・`iam:ListInstanceProfilesForRole`）は、条件を付けない別の文で与える。`iam:AttachRolePolicy` は、加えて条件 `iam:PolicyARN` を、決定13 の小文字の usecase の接頭辞の customer managed policy（ops-notification は `policy/<project>-<env>-ops-*`）に限る。この pattern は `<project>-<env>-ci-*` と重ならず、大文字で綴った ARN にも当たらない（決定13）。AWS managed policy と、CI の customer managed policy（決定7 の統制の policy、決定15 の boundary、決定17 の policy）を、作る role に付けさせない。boundary を permissions policy として付けると、その role の権限が boundary の上限まで広がるからである。`iam:DeleteRolePermissionsBoundary` は Resource `"*"` の Deny で拒む。`iam:PassRole` は、条件 `iam:PassedToService` を、作る role を渡すサービス（`scheduler.amazonaws.com`・`chatbot.amazonaws.com`）に限って与える。`iam:PassRole` は `iam:PermissionsBoundary` を受けないので、boundary を持つ role に限れない。CI の role を渡すことは、決定5 の `DenyIdentityChange`（Action `*`）が塞ぐ。Chatbot が初めの構成の作成で作る service-linked role のために、`iam:CreateServiceLinkedRole` を `iam:AWSServiceName` を `management.chatbot.amazonaws.com` に限って与える。
15. permissions boundary の customer managed policy を（未配線。PR-2b（#25）で配線する）、IAM の role を作る workload root の usecase ごとに1つ（`<project>-<env>-ci-boundary-<usecase>`。`ops-notification` は `<project>-<env>-ci-boundary-ops-notification`）、この usecase（identity root）が持つ。apply-identity の role が作り、その作成・読み取り・版の更新・削除の Action を、Resource をその ARN に限って inline policy で与える（決定7 の統制の policy と同じ Action と同じ文）。plan の role には、その読み取りを同じ ARN に限って与える（この2つは配線済み）。ARN は出力 `permissions_boundary_arns`（usecase の名前を key にした map）で公開する（未配線。PR-2b（#25）で配線する）。role を作る usecase は、自分の名前の boundary の ARN を入力で受け、作るすべての role に付ける。boundary の中身（何を上限とするか）はこの usecase が決め、role を作る usecase は決めない。 boundary の文書は Allow と Deny から成る。Allow は、その usecase が作る role の要る Action の和で、決定1 と決定4 の Action と Resource の規則を当てる（Action を列挙し、`service:*` を使わない。repository-wide/ADR-0301 決定8）。AWS の例は boundary の Allow をサービスの wildcard で書くが、この ADR はそれを採らない。Deny は、apply の role の Deny（決定5）のうち、`DenyIdentityChange` から `DenyBreakGlassChange` までの文を、同じ文（同じ local）で持つ。作った role を経由して、apply の role に拒んだ変更（統制の構成物、break-glass、bootstrap の構成物、identity root の state、3つの Bucket、state の鍵）を行えないようにするためである。boundary の名前は `<project>-<env>-ci-` で始まるので、決定5 の `DenyIdentityChange` に入る。apply の role も、作った role も、boundary の policy を変更・削除できない。 `ops-notification` の boundary の Allow は、心拍の role の `sns:Publish`（Topic の pattern）、Chatbot の channel role の CloudWatch の読み取り（alarm の pattern と、resource-level 権限を持たない5つの Action の Resource `"*"` の別の文）、心拍の role が暗号化した Topic へ publish するための `kms:Decrypt`・`kms:GenerateDataKey`（決定16）である。
16. boundary の Allow に（未配線。PR-2b（#25）で配線する）、KMS の暗号操作 `kms:Decrypt`・`kms:GenerateDataKey` を、Resource を鍵の pattern に、条件 `kms:ViaService` を `sns.<region>.amazonaws.com` に限って置く。`modules/kms` の Key Policy は心拍の role の ARN を名指して暗号操作を許すが、IAM の role の ARN を名指す resource-based policy の許可は permissions boundary の暗黙の拒否に削られる。boundary に暗号操作が無いと、心拍の publish が暗号化で失敗する。repository-wide/ADR-0301 決定12 の「暗号操作を IAM policy で与えない」を、boundary は上限を置くだけで権限を与えないと読み、これはそれに反しないとする。KMS は、Key Policy がアカウントへ委任しない暗号操作に IAM の Allow を効かせず、`modules/kms` は暗号操作を委任しないので、boundary があっても Key Policy に名指されない主体は鍵を使えない。Policy Test の `PLAN-IAM-04`（IAM の Allow の暗号操作の禁止）は、宣言した boundary の文書の、`kms:ViaService` の条件を持つ文だけを外す（未配線。PR-2b（#25）で配線する）。 repository-wide/ADR-0207 決定11 の記録として: 外れる対象は repository-wide/ADR-0301 決定12 の字義（IAM policy の文書に暗号操作の Allow を書かない）である。理由は上のとおりで、影響は次のとおりである。security: boundary の文書に暗号操作の Allow が現れ、`PLAN-IAM-04` に除外ができる。実効の暗号操作は、Key Policy が名指す主体に限られる。availability: これを置かないと、心拍の publish が暗号化で失敗する。cost: 無い。代替案と採らない理由: (a) Key Policy が role の session の ARN を名指す。session の ARN は Scheduler が assume するたびに決まり、前もって書けない。(b) 心拍の role に boundary を付けない。決定14 の、作るすべての role に boundary を付けることが崩れる。(c) KMS の grant で許す。`kms:CreateGrant` は repository-wide/ADR-0301 決定12 が IAM で与えることを禁じ、使う主体を Key Policy の1箇所に揃える性質も崩れる。(d) Topic を暗号化しないか、AWS managed key で暗号化する。`modules/sns` の暗号化と、CloudWatch・EventBridge などの送り手が AWS managed key の Topic へ送れないことに反する。見直し条件: `PLAN-IAM-04` の除外を、`kms:ViaService` で限った文の外へ広げる必要が出たとき。boundary に SNS のほかの `kms:ViaService` の暗号操作が要るとき。AWS が、permissions boundary と role の ARN を名指す resource-based policy の評価を変えたとき。
17. apply の role の workload の Allow（決定13・14 の読み取りと管理）は、customer managed policy（`<project>-<env>-ci-apply-workload`）に置き、apply の role に付ける（policy の作成と付与は未配線で、PR-2b（#25）で配線する。apply-identity の inline の作成と付与の権限は配線済み）。apply の role の inline policy には、state の読み書き（決定12 まで）と、決定5・13・14 の Deny を残す。inline に workload の Allow を置くと、入力の境界で 10,240 文字を超えるからである。policy は apply-identity の role が作り、その作成・読み取り・版の更新・削除と、apply の role への付け外し（`iam:AttachRolePolicy`、Resource を apply の role の ARN に、条件 `iam:PolicyARN` をその policy の ARN に限る）を inline policy で与える（決定7 の統制の policy と同じ形）。`aws_iam_role_policy_attachments_exclusive` は、apply の role にこの policy の ARN だけを載せる。 workload の Allow が 6,144 文字を超えるときは、同じ役割の customer managed policy を足して伸ばす。
18. apply の role に、`aws_kms_key`・`aws_kms_key_policy`・`aws_sns_topic` の削除（`kms:ScheduleKeyDeletion`、`sns:DeleteTopic`）を与えない。これらは `plan.stateful_protection` の保護の型であり、決定3 の「権限の側でも止める」と同じ扱いにする。Scheduler・Chatbot の構成・alias・IAM の role と policy の削除は与える。置換と、usecase から外す変更に要るからである。sandbox の apply と destroy の経路（repository-wide/ADR-0601 決定3・4）が鍵と Topic の削除を要するときは、その経路の role で与え、apply の role には足さない。
19. Chatbot の構成の作成で、apply の role に `sns:Subscribe` を与えない。Topic への購読は Chatbot の service-linked role（`AWSServiceRoleForAWSChatbot`）が自分の権限で作る（Chatbot Administrator Guide「Service-linked role for performing operations on Amazon SNS topics and CloudWatch Logs」）。Service Authorization Reference も、`CreateSlackChannelConfiguration` の依存に `sns:Subscribe` を挙げない。

## 検討した代替案

### 案A: 5つの role 自身に permissions boundary を課し、Allow を広く与える

5つの role の権限は Action の列挙で閉じており、boundary を重ねても上限は変わらない。boundary の内側の Allow を広く与えると、repository-wide/ADR-0301 決定8 の Action wildcard に当たる。apply の role が作る role に課す boundary は決定14・15 が持つ。

### 案B: AWS managed policy（`ReadOnlyAccess` 等）を plan の role に付ける

plan の role は Pull Request の作者が任意のコードで使える資格情報であり、アカウントの全 resource を読める。repository-wide/ADR-0301 決定10 に反する。

### 案C: 後から足す構成物の権限を、まとめて先に入れる

構成物の形が決まる前は正しく列挙できず、使わない権限を先に与えることになる。鍵の権限は、鍵の形（`modules/kms`）から Provider が呼ぶ API を列挙できるので、鍵を作る変更と同じか、それより前に入れる（決定3）。

### 案D: 作る role を完全な ARN に限り、permissions boundary を課さない

作る role の ARN と、それに付ける policy の ARN を、usecase の名前から組んで列挙する。role を作る usecase を足すたびにこの ADR の書き換えを要し、`iam:PutRolePolicy` で書く文書の中身は IAM の条件で限れないので、作った role を経由した bootstrap の構成物への到達は Policy Test でしか止まらない。

### 案E: boundary の Allow を AWS の例のようにサービスの wildcard で書く

文書が短く、usecase を足しても伸びにくい。repository-wide/ADR-0301 決定8 の例外を要し、作る role の inline policy が上限まで広がりうる。

### 案F: workload の構成物の Resource を usecase ごとの完全な ARN にする

最も狭い。usecase の構成物の名前を変える変更が、そのたびにこの ADR の書き換えを要する。

### 案G: permissions boundary を1つにする

boundary は role に1つしか付かず、文書は 6,144 文字が上限である。Deny の文を共有すると、入力の境界で Allow に使える文字が少なく、role を作る2つ目の usecase で上限を超える。

### 評価

| 評価軸 | 案A | 案B | 案C | 採用案 |
| --- | --- | --- | --- | --- |
| Security | 中（boundary の中が広い） | 低（全 resource を読める） | 中（未使用の権限） | 高 |
| Testability | 低（有効な権限の計算が要る） | 中 | 中 | 高（文書の完全一致） |
| Contract Clarity | 中 | 低 | 中 | 高 |
| Maintainability | 中 | 高 | 低 | 中（Provider の版ごとに見直す） |
| Scope Control | 中 | 低 | 低 | 高 |

評価軸の定義は repository-wide/ADR-0101 (architecture-principles) を参照する。

## 意図的に捨てるもの

- Provider の版を上げても権限を見直さずに済むこと
- apply-identity の role を、自分の権限を広げられないようにすること

## 保証範囲

- 保証すること: 5つの role の policy の文書が、上の表と決定5 の Deny と決定9 から組まれていること（Unit Test）。reference の plan で、apply の role に付く inline policy が、決定5 の S3・IAM の各 ARN への読み取り以外の Action（identity root の key と lock file へはすべての Action）と、state Bucket のすべての object への `s3:DeleteObjectVersion` を条件なしの Deny で拒み、鍵ごとの ARN への Deny が `modules/kms` が Key Policy でアカウントへ委任する Action を覆うこと。bootstrap の構成物の設定を変える resource が、bootstrap の構成物を指すこと。apply の role に、その inline policy のほかの policy が付かないこと（role の引数、`aws_iam_role_policy_attachment`、`aws_iam_policy_attachment` を含む）（Policy Test。決定17 の policy を付けるまでの形で、PR-2b（#25）で「inline policy と決定17 の policy のほかの policy が付かないこと」へ改める）。plan の role の Allow の Action の service の名前が wildcard を含まないこと（Policy Test。`PLAN-ROLE-05`）。unlock-identity の role の Allow が決定9 の範囲に限られ、Key Policy がその復号を同じ lock file の object に限ること。unlock の role の Allow が決定11 の範囲に限られること（Policy Test）。他の role の作成が、apply-identity の inline policy の書き込みに依存すること（Static Analysis）。apply-identity の role の、plan の出力の Bucket の object に届く Allow が、`apply/*` への `s3:PutObject` だけであること。宣言した inline policy と統制の customer managed policy（決定7）の外から apply-identity の role に権限が付かず、その customer managed policy の文書も plan の出力の Bucket の object に `apply/*` への `s3:PutObject` のほかを許さないこと。apply の role に付く inline policy が、apply の出力の Bucket の object へ、`s3:PutObject` のほかのすべての Action を条件なしの Deny で拒むこと（Policy Test）。apply の role に付く inline policy が、宣言した統制の書き込みの Action のそれぞれを、Resource `"*"` の条件なしの Deny で拒むこと（Policy Test。`PLAN-APPLY-06`）。unlock の role への復号が workload root の lock file の object に限られること（決定11。Policy Test）
- 保証しないこと: 列挙が Provider の実際の呼び出しを漏れなく覆うこと（段4 の後の人の確認と、CI の plan が見る）。apply の role の Deny が実際の要求で文書どおりに評価されることと、Deny の形から導く保証の外（repository-wide/ADR-0602 の保証範囲の「保証しないこと」）。resource type を持たず Resource `"*"` でしか与えられない Action を経た、bootstrap の構成物の変更（決定5 の Deny は構成物の ARN を名指す）。Policy Test の宣言（`conftest/plan/decl.json`）の型の分類のうち、親の resource の ARN で守られるとした型の設定を変える API が実際に親の ARN への Action であること（検査は無く、宣言の変更のレビューに依る）。apply-identity の inline policy の書き込みが、同じ apply の role の作成までに IAM の評価へ反映されること。反映が遅れると、その apply は `iam:CreateRole` の AccessDenied で失敗する。plan の role の Allow が、読み取りの動詞を持ちながら data を返す Action（ログの event、secret の値など）を含まないこと。Policy Test は動詞で読み取りを判定する。Identity Center の permission set と割当のほかの書き込み（instance・application の書き込み）と、identitystore の書き込み（user・group・グループの membership）。`DenyGovernanceChange` はこれらを拒まないので、apply の role にこれらの Allow を足すと、グループの membership を通して permission set の割当の受け手を変えられる。大文字で綴った名前を渡した要求を、IAM が既存の小文字の role や policy に解決するか（確かめていない。決定13 の IAM の書き込みの Allow は小文字の usecase の接頭辞に限るので、大文字の ARN は Allow に当たらず、拒まれる側に倒れる）。apply-identity の role が break-glass の StackSet のテンプレートを変えられること。service-managed の StackSet は、メンバーで `stacksets-exec-*` の role として実行されるので、管理アカウントの apply-identity の role の侵害は、すべてのメンバーアカウントへ届く。権限はテンプレートの中身を限れない（`CreateStackSet`・`UpdateStackSet` の条件キーはテンプレートの本文を見ない）

## 検証方法

- Unit Test: `internal/github-oidc/tests/permissions.tftest.hcl` が、5つの role の policy の文書と、統制の customer managed policy の文書と、inline policy と managed policy の排他（managed policy は管理アカウントの apply-identity の role の統制の policy だけ）を完全一致で確かめる
- 手順: `docs/setup/bootstrap.md` の段4 の手順9 と段5 の手順4 が、apply の後に `aws iam simulate-principal-policy` で、表の Action が plan と apply-identity の role に許され、与えないものと apply の role の bootstrap の構成物への変更が拒否されることを確かめる
- Policy Test（`make tf-policy`）: Allow の Action の `*`・`service:*` の不在（repository-wide/ADR-0301 (least-privilege-policy) 決定8）と、`NotAction`・`NotResource` の Allow の不在、Allow の Resource `"*"` が決定1 の Action（`kms:ListAliases` と、Action の導出の表の後に挙げた統制の読み取り。`resource_wildcard_actions` の宣言）に限られること（同 決定9）、KMS の暗号操作と `kms:CreateGrant` の Allow の不在（決定3、同 決定12）
- Policy Test（`make tf-policy`）: plan の role の Allow が読み取りと、plan の出力の Bucket の `pr/*`・`branch/*` への `s3:PutObject` だけであることと、宣言した policy の外から plan の role に権限が付かないこと（決定8）。Action の service の名前に wildcard を使わないこと（`PLAN-ROLE-05`）
- Policy Test（`make tf-policy`、`plan.deployment_identity_apply_identity_output`）: 決定10。Bucket の object に届く S3 の Action と Resource、宣言した policy の付き先、ほかの付け方の不在を、`state-backend` の reference の plan と結合した入力で確かめる
- Policy Test（`make tf-policy`）: apply の role の inline policy が、鍵ごとに、同じ module の Key Policy がアカウントへ委任する Action のすべてを、その鍵の ARN（`state-backend` の plan の値）への Deny で拒むこと（決定5。`plan.deployment_identity_apply_role`）
- Policy Test（`make tf-policy`）: unlock-identity の role の Allow が決定9 の3つの Action と Resource に限られ、宣言した policy の外から権限が付かず、state の鍵の Key Policy がこの role に `kms:Decrypt` だけを、IAM が許す lock file の object の ARN に限って許すこと（決定9。`plan.deployment_identity_unlock_role`）
- Static Analysis（`make resource-order-check`）: apply-identity を除く role の resource が、apply-identity の inline policy の resource に依存すること（決定4）
- Policy Test（`make tf-policy`）: apply の role の inline policy が apply の role に付き、決定5 の S3・IAM の各 ARN（role・OIDC provider・Bucket は plan の値、identity root の key と lock file は宣言の `state_backend.roots` から組む）について、`*` か、読み取りの名前（動詞が Get・List・Describe・Head で wildcard を含まないもの）だけを除く `NotAction` を、条件なしの Deny で拒むこと（identity root の key と lock file は `*` だけ）。state Bucket のすべての object への `s3:DeleteObjectVersion` を拒むこと。apply の role に、その inline policy のほかの policy が付かないこと（排他の2つ、role の `inline_policy` と `managed_policy_arns`、`aws_iam_role_policy_attachment`、`aws_iam_policy_attachment`。決定17 の policy を付けるまでの形で、PR-2b（#25）で改める）。identity root の bootstrap の use-case の下の resource の型が宣言ですべて分類され、設定を変える resource が、宣言した属性の値で bootstrap の構成物を指すこと。宣言の形が崩れていれば落ちること（決定5・7。`plan.deployment_identity_apply_role`）。宣言が書き込みの名前（`writes`）を持つ子の ARN については、ちょうどその名前だけを除く `NotAction` で拒むこと。構成物の ARN への Deny の Resource は、IAM がその ARN に当てる pattern（`"*"` を除く）も覆いと数える（決定5 の CI の role と policy の pattern）。鍵、書き込み先の子、identity root の key と lock file、版の削除の Deny は完全一致で見る

## 影響

- identity root に構成物を足す変更と、管理アカウントに workload の usecase を足す変更は、まずこの policy を広げる変更を apply してから、その権限を使う変更を apply する。CI の role を足す変更は、決定4 の順序により1回の apply に収まる。権限の変更と、その権限で作る resource を同じ apply に入れると、両者の間に依存が無く失敗しうる
- inline policy は role あたり 10,240 文字、customer managed policy は1つ 6,144 文字（どちらも空白を除く）が上限である。入力の境界での長さは、`permissions.tftest.hcl` の `policy_length`（`admin`）と `policy_length_outside_admin`（`admin` 以外）が上限以下であることを固定する。boundary（決定15）と apply の role の workload の policy（決定17）も同じ2つの run で測る（未配線。PR-2b（#25）で配線する）
- IAM の role を作る workload root の usecase は、出力 `permissions_boundary_arns`（未配線。PR-2b（#25）で配線する）のうち自分の名前の boundary の ARN を入力で受け、作るすべての role に付ける。対象は `ops-notification`（入力 `permissions_boundary_arn`）と、以後 role を作る usecase のすべて（`modules/vpc` の flow logs の role を使う `network-foundation` を含む）。boundary の中身はこの usecase（identity root）が持ち、role を作る usecase は決めない。role を作る usecase を足す変更は、その usecase の boundary を足す変更（この ADR の書き換え）を先に merge して apply する。入力は policy の文書ではなく、この usecase が持つ1つの policy の ARN であり、repository-wide/ADR-0204 決定2 の、意味が AWS の表現に依存する入力ではない
- workload root は、boundary の ARN を identity root の state から読めない（決定5 の `DenyIdentityStateChange`）。env の root が、名前から組んだ ARN を usecase に渡す
- 決定15・17 の policy を作って付ける変更は、それを作る権限（apply-identity の inline policy）を入れる変更を `admin` へ昇格し apply した後に merge する。権限と、その権限で作る policy を同じ apply に入れると、IAM の反映の遅れで1回目の apply が落ちうる

## 見直し条件

- AWS Provider の版を上げるとき
- boundary の文書が入力の境界で 6,144 文字に近づいたとき（boundary の Deny を短い形にするかを決める）
- apply の role の workload の policy が 6,144 文字を超えるとき（決定17 のとおり policy を足す。role に付けられる managed policy の数のクォータを確かめる）
- workload root の Provider の版が identity root と違うとき（決定2 の版を root ごとに書く）
- Scheduler・Chatbot が `iam:AssociatedResourceArn` を入れることが確かめられたとき（`iam:PassRole` をその条件で限る）
- inline policy の文字数が上限に近づいたとき
- CI の plan か apply が AccessDenied で失敗したとき
- `modules/kms` が Key Policy でアカウントへ委任する Action を変えるとき（決定5 の鍵の Deny の列挙を合わせる）
- apply-identity の policy が、入力の境界で 10,240 文字を超える変更を入れるとき（policy を割り、決定4 の順序を見直す）。統制の customer managed policy が 6,144 文字を超えるとき（決定7 のとおり、同じ役割の policy を足す）
- state の鍵の作成の権限を足すとき（鍵の種類 `kms:KeySpec`・`kms:KeyUsage`、多リージョン `kms:MultiRegion`、鍵素材 `kms:KeyOrigin` を限る条件と、`resource_wildcard_actions` への `kms:CreateKey` の追加を併せて決める。決定13 の workload の鍵の条件と揃える）
- bootstrap の構成物に、resource type を持たない Action で設定を変えられる型が入るとき（apply の role に Resource `"*"` の Deny を足すかを決める）
