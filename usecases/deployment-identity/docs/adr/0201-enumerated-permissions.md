# ADR-0201: CI の role の権限を、Provider が呼ぶ API から導いた Action の列挙で与える

- Status: Accepted
- Date: 2026-10-25
- Scope: deployment-identity
- Related: repository-wide/ADR-0602, repository-wide/ADR-0604, repository-wide/ADR-0301, repository-wide/ADR-0402, repository-wide/ADR-0208, repository-wide/ADR-0207, finops/ADR-0001, organization-baseline/ADR-0202

## Context

repository-wide/ADR-0602 (bootstrap-and-ci-authentication) 決定16 は、apply の role の権限の与え方（Action の列挙か permissions boundary か）を use-case の ADR に委ねる。同 決定13 は、plan の role に変更系の権限を与えず、apply の role に bootstrap の構成物を変更する権限を与えないことを求める。repository-wide/ADR-0604 (state-split-by-apply-role) 決定8-10 は、plan の role が state にも lock file にも書かないこと、apply の role が自分の root の key と lock file にだけ書けること、apply の role が state Bucket の設定を変更する有効な権限を持たないことを求める。同 決定13 は、lock の解除の role に、lock file の一覧・読み取り・削除と、その lock file の復号だけを持たせる。

AWS Provider は、resource の refresh で、設定していない属性の API も呼ぶ。6.70.0 の `aws_s3_bucket` の Read は、Bucket の Policy・ACL・CORS・website・版管理・accelerate・request payment・logging・lifecycle・replication・暗号化・Object Lock・tag を読み、拒否を許容しない。読み取りの権限が1つ欠けると、plan は AccessDenied で失敗する。apply-identity の role の読み取りが欠けると、その role 自身の policy を直す apply が refresh で失敗し、repository-wide/ADR-0602 決定9 の回復の契機になる。

管理アカウントの identity root は、統制の構成物（repository-wide/ADR-0602 決定1）を持つ `organization-baseline` も呼ぶ。apply-identity の role は、それを変更する権限を持つ。apply の role は持たない（同 決定13、repository-wide/ADR-0604 決定10）。Organizations と root の資格情報の中央管理には、resource-level の権限を持たない書き込みの Action（`organizations:CreateOrganization`・`EnableAWSServiceAccess`、`iam:EnableOrganizationsRoot*` など）がある。これらは Resource の ARN ごとの Deny では拒めない。

workload root の usecase（`ops-notification`）は、SNS の Topic、KMS の鍵、EventBridge Scheduler の schedule、Amazon Q Developer in chat applications（以下 Chatbot）の Slack の channel の構成と、それらが使う IAM の role と customer managed policy を作る。apply の role が IAM の role を作り、その role に権限を書ける時点で、apply の role は作った role を経由して、自分に Deny された bootstrap の構成物と統制の構成物へ届きうる。AWS は、他者に role の作成を委ねるときの機構として permissions boundary を示す（IAM User Guide「Permissions boundaries for IAM entities」の「Delegating responsibility to others using permissions boundaries」）。委ねられる側は、決めた boundary を付けるときだけ作成と変更ができ、boundary の policy の変更と boundary の除去を拒まれる。boundary は role の ARN を名指す resource-based policy の許可も削る（同文書「Resource-based policies for IAM roles」）。IAM の inline policy は role あたり 10,240 文字、customer managed policy は1つ 6,144 文字が上限で、permissions boundary は role に1つしか付かない。

## Decision

1. 5つの role の権限を、role ごとの inline policy に Action を列挙して与える（apply の role の workload の権限は決定17 の、apply-identity の role の核の外の権限は決定21 の customer managed policy に置く）。Allow の文に `*` と `service:*` の Action、`"*"` の Resource、部分的なワイルドカード（`s3:GetBucket*` 等）を使わない。5つの role に permissions boundary を課さない（apply の role が作る role には決定14 で課す）。ただし、resource-level 権限を持たない Action（Service Authorization Reference で判定する。`kms:ListAliases`）は、`"*"` の Resource を Action ごとの別の文で与える（repository-wide/ADR-0301 (least-privilege-policy) 決定9）。Key Policy の書き込みでの lockout の安全チェックの迂回（`kms:BypassPolicyLockoutSafetyCheck`）は Deny で拒む。
2. 列挙は、identity root の resource について AWS Provider 6.70.0 の source（`internal/service/s3`・`internal/service/iam`・`internal/service/kms`、管理アカウントの apply-identity と plan の role では `internal/service/organizations`・`internal/service/cloudformation` も）の Read・Create・Update・Delete が呼ぶ API から導く。対応は下の表が持つ。Provider の版を上げる変更は、この表を見直す。
3. 権限は段4 の構成物と、決定13 の workload root の usecase の構成物と、identity root が持つアカウントの前提の構成物（repository-wide/ADR-0602 決定1）（段4 の構成物は OIDC provider、5つの role と inline policy、state Bucket の段1-4 の設定とその lifecycle、plan の出力の Bucket とその lifecycle、workload root の apply の出力の Bucket（CI の apply-identity が作る）、state の鍵（鍵、Key Policy、alias））に要る分に限る。identity root に構成物を足す変更は、その構成物に要る権限を足す変更と同じ昇格に入れてよい（影響）。apply-identity の role に、鍵と alias を作る権限は与えない。state の鍵と alias は、新しいアカウントでは段4 の apply が一時 IAM user の権限で作る。state の鍵と alias の作り直しは CI では行えず、要るときは作成の権限を足す変更を先に merge する。apply の role は workload の鍵を作る（決定13）が、state の鍵とその alias は決定5 の Deny で変えられない。5つの role の暗号操作は IAM では与えず、state の鍵の Key Policy が role を名指して許す（repository-wide/ADR-0301 (least-privilege-policy) 決定12）。 管理アカウント（env が `admin`）の apply-identity の role には、加えて `organization-baseline` の構成物に要る分を与える。対象は、組織・OU・policy とその付け先、IAM の信頼アクセス、root の資格情報の中央管理、break-glass の IAM user・group・role、IAM の password policy、メンバーアカウントへ break-glass の role を配る CloudFormation の StackSet とその stack instance である。StackSet の名前は break-glass の role の名前と同じとし（organization-baseline/ADR-0202 決定3）、Resource をその StackSet の ARN（末尾の ID は pattern）に限る。次の3つは意図して与えない: 組織の削除（`organizations:DeleteOrganization`）、メンバーの閉鎖（`organizations:CloseAccount`・`account:CloseAccount`）、組織からの除外（`organizations:RemoveAccountFromOrganization`）。`prevent_destroy` と `plan.stateful_protection` に加えて、権限の側でも止める。サービスが service-linked role を作る Action のために、`iam:CreateServiceLinkedRole` を `iam:AWSServiceName` の条件で該当するサービスに限って与える。env が `admin` でない role には、これらを与えない。段4 の構成物の書き込みのうち、決定21 の核に入らないものは、決定21 の customer managed policy に置く。統制の構成物の作成と設定の権限は、決定7 の customer managed policy に置く。読み取りは plan の role と同じ文で inline policy に置く。 env によらず、partition が `aws` のとき、apply-identity の role に、Chatbot の service-linked role（`arn:<partition>:iam::<account>:role/aws-service-role/management.chatbot.amazonaws.com/AWSServiceRoleForAWSChatbot`）に要る分を、Resource をその ARN に限って与える。`iam:CreateServiceLinkedRole` を条件 `iam:AWSServiceName` を `StringEquals` で `management.chatbot.amazonaws.com` に限る1つの文で、`iam:UpdateRole` を別の1つの文で、決定21 の customer managed policy に置く。`iam:GetRole` は読み取りなので、決定21 の核として inline policy に置く。`iam:UpdateRole` は、人がコンソールで変えた description を次の apply が宣言の値へ戻すためである。`aws_iam_service_linked_role` の Update は description だけを `iam:UpdateRole` で書き、Read は `iam:GetRole` の応答から tag を読む（決定2 の方法で導いた）。tag を付けないので `iam:TagRole`・`iam:UntagRole`・`iam:ListRoleTags` は与えない。削除（`iam:DeleteServiceLinkedRole`・`iam:GetServiceLinkedRoleDeletionStatus`）は与えない。`prevent_destroy` と `plan.stateful_protection` に加えて、権限の側でも止める。plan の role と、apply の role の読み取りの policy（決定17）には、`iam:GetRole` を同じ ARN に限って与える。workload root の usecase がその存在を data source で読むからである。partition が `aws` でないときは、これらの文を置かない。その partition にはこの role が無いからである（repository-wide/ADR-0208 決定5 の us-east-1 と同じ扱い）。apply の role の `iam:CreateServiceLinkedRole`（決定14）は partition で分けない。
4. Resource は、state Bucket と plan の出力の Bucket と apply の出力の Bucket の ARN とその key、5つの role と OIDC provider、state の鍵で限定する。role の ARN は、resource 参照ではなく、partition・アカウント・role 名から組んだ完全な ARN で書く。prefix の pattern ではないので、repository-wide/ADR-0301 (least-privilege-policy) 決定11 の対象ではない。apply-identity の role の inline policy は、他の role より先に書き込む。他の role の作成は、apply-identity の inline policy の書き込みに依存させる。role を足す変更は、1回の apply で、その role を管理する権限を apply-identity へ足してから role を作る。state の鍵の ARN は入力の `state_key_arn`（`state-backend` の出力）で受け、role と同じ partition・リージョン・アカウントの鍵であることを plan で（ARN が plan で決まらなければ apply で）確かめる。 `organization-baseline` の構成物の Resource は、作る前に組織の ID が決まらないので、ARN の pattern で書く。例: `arn:<partition>:organizations::<管理アカウント>:ou/o-*/ou-*`。pattern は repository-wide/ADR-0301 決定11 の対象で、その根拠をこの決定に置く。break-glass の IAM の Resource は、path（`/break-glass/`）と名前から組んだ完全な ARN で書く。メンバーへ break-glass の role を配る StackSet の Resource は、ARN の末尾の ID が作るまで決まらないので、`stackset/<名前>:*` の pattern で書く。StackSet の書き込みと stack instance の操作が要る stackset-target の resource は、同じ理由で `stackset-target/<名前>:*` で書き、region を空にする。実際の要求の stackset-target の ARN は、Service Authorization Reference の形と違い region を持たないからである。type の resource は、StackSet のテンプレートが作る型（`AWS::IAM::Role`）に限り、region とアカウントを `*` にした `type/resource/AWS-IAM-Role` で書く。実際の要求の type の ARN は、region が `*` という文字列で、アカウントを持たないからである（`arn:<partition>:cloudformation:*::type/resource/AWS-IAM-Role`）。stack instance の操作では、type の ARN の region は展開先の region になる。Resource の `*` は、その文字列にも空の値にも当たる。stack instance の操作は `cloudformation:TargetRegion` を provider の region に限る。このキーは、実際の要求では type の resource の評価にだけ付き、stackset と stackset-target の評価には付かない。Service Authorization Reference は、3つの resource 型のすべてにこのキーが付くと書いている。そのため、条件は type の ARN だけの文に置き、stackset と stackset-target の ARN の文には付けない。このキーは要求の region を一覧で持つので、`ForAllValues:StringEquals` ですべての region が provider の region であることを求め、`Null` でキーが要求に在ることを求める。`StringEquals` は、一覧で渡したこのキーに成り立たない。`ForAllValues` は、空の一覧にも成り立つ。IAM の policy simulator は、context に与えたキーをすべての resource の評価に付ける。そのため、どの resource にキーが付くかは simulator では分からない。一時の主体にこの文を付け、存在しない OU を指して `CreateStackInstances` を呼んで確かめた（provider の region は通り、us-east-1 と、provider の region と us-east-1 の組は type で拒まれた）。`UpdateStackSet` には条件を付けない。付けると、region を渡さない更新の要求はこのキーを持たず、`Null` の条件で拒まれるからである。
5. apply の role に、次を Deny で与える（repository-wide/ADR-0301 (least-privilege-policy) 決定8 は Deny の wildcard を許す）。名前が `<project>-<env>-ci-` で始まる IAM の role と customer managed policy（`role/<project>-<env>-ci-*`・`policy/<project>-<env>-ci-*`。5つの role、決定7 の統制の policy、決定15 の boundary、決定17・21 の policy を含む）と OIDC provider、identity root の key と lock file、plan の出力の Bucket とそのすべての object への、すべての Action（`*`）。CI の role と policy を名前の pattern で書くのは、CI の構成物が増えても文書が伸びず、apply の role が CI の構成物と紛らわしい名前の role や policy を作ることも、小文字で綴る限り拒むためである。IAM の Resource の照合は大文字・小文字を区別するので、この Deny は大文字で綴った ARN を拒まない。主な守りは、IAM の書き込みの Allow を小文字の usecase の接頭辞に限る決定13 であり、この Deny は二重の守りである。この pattern は repository-wide/ADR-0301 決定11 の対象で、その根拠をこの決定に置く。state Bucket への、`s3:ListBucket` と `s3:GetEncryptionConfiguration` を除くすべての Action（`NotAction`）。state Bucket のすべての object への `s3:DeleteObjectVersion`。state の鍵への、`modules/kms` が Key Policy でアカウントへ委任する管理の Action のすべて（repository-wide/ADR-0604 (state-split-by-apply-role) 決定10）。Deny を Action の列挙やサービスの wildcard（`s3:Put*`、`iam:*`）で書くと、AWS が足す変更系の Action（tag や metadata の設定）と、別のサービスの名前で同じ ARN を対象とする Action（role の ARN への `sts:AssumeRole`）を覆わない。S3・IAM の構成物への Deny は、`*` か、許す読み取りの名前だけを除く `NotAction` で書く。`s3:GetEncryptionConfiguration` を除くのは、init の前に運用機構が Bucket の既定の暗号化と鍵の一致を確かめるためである（state-backend/ADR-0101 決定3）。workload root の key と lock file への書き込みは apply の role が行うので拒まない。鍵の Deny は `kms:*` にしない。Key Policy が role を名指して許す暗号操作（決定3）まで塞ぐからである。KMS では IAM の Allow は Key Policy がアカウントへ委任した Action にしか効かないので、委任の Action を覆えば足りる。alias の削除と付け替えは鍵への権限も要るので、鍵の Deny が塞ぐ。以後 workload の usecase のための Allow を足しても、bootstrap の構成物、identity root の state、3つの Bucket の設定、state の版、plan の出力、state の鍵の設定を変えられないようにする。apply の出力の Bucket（決定12）への、すべての Action（`*`）。apply の出力の Bucket のすべての object への、`s3:PutObject` を除くすべての Action（`NotAction`）。ただし、apply の role の書き込み先として宣言した構成物の子（apply の出力の Bucket の object）への Deny は、その書き込みの名前だけを除く `NotAction` で書き、読み取りも除かない。 apply の role に、統制の構成物を変更する Action を Deny で与える（`DenyGovernanceChange`）。Resource は `"*"`、条件は付けない。対象は次の書き込みの Action である。Organizations は、書き込みの動詞（Accept・Attach・Cancel・Close・Create・Decline・Delete・Deregister・Detach・Disable・Enable・Invite・Leave・Move・Put・Register・Remove・Tag・Terminate・Untag・Update）を接頭辞で拒む。Account Management は `account:CloseAccount`。IAM は `iam:EnableOrganizationsRoot*`・`iam:DisableOrganizationsRoot*` と、password policy の削除（`iam:DeleteAccountPasswordPolicy`）と、管理アカウント（env が `admin`）でだけ password policy の更新（`iam:UpdateAccountPasswordPolicy`）。管理アカウントの password policy は break-glass の構成物として apply-identity の role が持ち、メンバーの password policy は account-baseline の構成物として apply の role が置く（決定13）。Identity Center は permission set と割当の書き込み。これは、接尾辞の wildcard（`sso:*AccountAssignment`・`sso:*FromPermissionSet`・`sso:*ToPermissionSet`）と、`sso:CreatePermissionSet`・`sso:DeletePermissionSet`・`sso:ProvisionPermissionSet`・`sso:PutPermissionsPolicy`・`sso:UpdatePermissionSet` で書く。wildcard は、Service Authorization Reference の IAM Identity Center の頁で Access level が Read か List の Action のどれにも当たらないものに限る（`sso:*PermissionSet` は `sso:DescribePermissionSet`・`sso:GetPermissionSet` などに当たるので使わない）。14 の Action を並べると、この文が決定15 の boundary の上限を詰めるからである。CloudFormation は StackSet と stack instance の作成・更新・削除、既存の stack の取り込み（`cloudformation:ImportStacksToStackSet`）、操作の停止（`cloudformation:StopStackSetOperation`）と、組織への信頼アクセスの有効化と無効化（`cloudformation:ActivateOrganizationsAccess`・`DeactivateOrganizationsAccess`）。`cloudformation:TagResource`・`UntagResource` は拒まない。Resource `"*"` の Deny は、workload の stack と change set の tag まで塞ぐからである。STS は `sts:AssumeRoot`。読み取り（Describe・List・Get）は拒まない。委任管理者のアカウントの CI が、組織を読んで行う運用を塞がないためである。この Deny は、password policy の更新を除き、管理アカウントの外でも同じ文で置く。メンバーで Organizations の書き込みを呼ぶ正当な経路は、委任管理者の設定に限る。どの Action がそれに当たるかは、#22 の交差の表で確かめ、当たる Action をこの列挙から外すか、その委任をこの usecase の外で行うかを、その時点で決める。break-glass の IAM user・group・role には、`DenyBreakGlassChange` として Action `"*"` を Deny で与える。Resource は、path が `/break-glass/` の user・group・role の ARN の pattern（`arn:<partition>:iam::<account>:user/break-glass/*`・`group/break-glass/*`・`role/break-glass/*`）で書く。入力 `break_glass_arns`（`organization-baseline` の出力）は path を `/break-glass/` に限り（validation）、module は入力のすべてがこの pattern に入ることを plan で確かめる（precondition）。pattern は、入力に無い同じ path の user・group・role も拒む。拒む範囲が広がるだけで、Allow は広がらない。apply の role が作る role は決定13 で名前が usecase の接頭辞に限られ、path が `/break-glass/` にならない。入力の ARN を並べると、名前が上限の長さのとき、この文が決定15 の boundary の上限を詰めるからである。この pattern は repository-wide/ADR-0301 決定11 の Deny の但し書きの対象で、その根拠をこの決定に置く。管理アカウントの決定7 の統制の customer managed policy も、名前が `<project>-<env>-ci-` で始まるので、5つの role と OIDC provider と同じ Deny（Action `*`）の対象に入る。workload の apply の role が、apply-identity の role に付く統制の権限を書き換えられないようにするためである。接頭辞で拒む Deny は、AWS が後から足す書き込みの Action の名前が、その接頭辞に当たる限りで覆う。当たらない名前の Action を覆わないことは、repository-wide/ADR-0602 の保証しないことに在る。 `DenyIdentityChange` から `DenyBreakGlassChange` までの Deny の文は、決定15 の boundary にも同じ文で置く。apply の role の Deny を変える変更は、boundary の Deny を変える変更である。
6. apply-identity の role は、自分を含む5つの role の信頼条件と policy を変更できる。誤った信頼条件が apply されると CI は締め出され、回復は repository-wide/ADR-0602 決定9 の回復の契機になる。
7. CI の role に AWS managed policy を付けない。customer managed policy は、apply-identity の role に、決定21 の `<project>-<env>-ci-apply-identity-manage` を env によらず付け、管理アカウント（env が `admin`）では加えて統制の構成物（決定3）の作成と設定の権限を持つ `<project>-admin-ci-apply-identity-governance` を付ける。apply の role に、workload の権限を持つ3つ（決定17。管理の `<project>-<env>-ci-apply-workload` と `<project>-<env>-ci-apply-workload-2`、読み取りの `<project>-<env>-ci-apply-workload-read`）を付ける。plan の role に付けてよいのは決定17 の読み取りの policy だけで、unlock-identity と unlock の role には managed policy を付けない。 統制の権限を inline policy に置かないのは、IAM の role の inline policy の合計が 10,240 文字を上限とし、統制の分を足すと入力の境界でそれを超えるためである。AWS も、多くの場合に inline policy より managed policy を使うことを勧める（IAM User Guide「Choose between managed policies and inline policies」）。統制の権限が増えるとき（Identity Center の permission set と割当など）は、決定21 の規則で同じ役割の customer managed policy を足して伸ばす。 apply-identity の role には、この決定で apply-identity の role に付ける customer managed policy（統制の policy と決定21 の policy）の作成・版の更新・削除の Action（`iam:CreatePolicy`・`iam:CreatePolicyVersion`・`iam:SetDefaultPolicyVersion`・`iam:DeletePolicyVersion`・`iam:DeletePolicy`）を、Resource をそれらの ARN に限って inline policy で与える。読み取りの 15. permissions boundary の customer managed policy を、IAM の role を作る workload root の usecase ごとに1つ（`<project>-<env>-ci-boundary-<usecase>`。`ops-notification` は `<project>-<env>-ci-boundary-ops-notification`）、この usecase（identity root）が持つ。apply-identity の role が作り、その作成・読み取り・版の更新・削除の Action を、Resource をその ARN に限って inline policy で与える（決定7 の統制の policy と同じ Action と同じ文）。読み取りは、apply-identity の role と plan の role に、決定7 の pattern で与える。ARN は出力 `permissions_boundary_arns`（usecase の名前を key にした map）で公開する。role を作る usecase は、自分の名前の boundary の ARN を入力で受け、作るすべての role に付ける。boundary の中身（何を上限とするか）はこの usecase が決め、role を作る usecase は決めない。 boundary の文書は Allow と Deny から成る。Allow は、その usecase が作る role の要る Action の和で、決定1 と決定4 の Action と Resource の規則を当てる（Action を列挙し、`service:*` を使わない。repository-wide/ADR-0301 決定8）。AWS の例は boundary の Allow をサービスの wildcard で書くが、この ADR はそれを採らない。Deny は、apply の role の Deny（決定5）のうち、`DenyIdentityChange` から `DenyBreakGlassChange` までの文を、同じ文（同じ local）で持つ。作った role を経由して、apply の role に拒んだ変更（統制の構成物、break-glass、bootstrap の構成物、identity root の state、3つの Bucket、state の鍵）を行えないようにするためである。boundary の名前は `<project>-<env>-ci-` で始まるので、決定5 の `DenyIdentityChange` に入る。apply の role も、作った role も、boundary の policy を変更・削除できない。 `ops-notification` の boundary の Allow は、心拍の role の `sns:Publish`（Topic の pattern）、Chatbot の channel role の CloudWatch の読み取り（alarm の pattern と、resource-level 権限を持たない5つの Action の Resource `"*"` の別の文）、心拍の role が暗号化した Topic へ publish するための `kms:Decrypt`・`kms:GenerateDataKey`（決定16）である。
16. boundary の Allow に、KMS の暗号操作 `kms:Decrypt`・`kms:GenerateDataKey` を、Resource を鍵の pattern に、条件 `kms:ViaService` を `sns.<region>.amazonaws.com`（`<region>` は provider の region と us-east-1）に限って置く。`modules/kms` の Key Policy は心拍の role の ARN を名指して暗号操作を許すが、IAM の role の ARN を名指す resource-based policy の許可は permissions boundary の暗黙の拒否に削られる。boundary に暗号操作が無いと、心拍の publish が暗号化で失敗する。SNS は、暗号化した Topic へ publish する主体に `kms:GenerateDataKey*` と `kms:Decrypt` を求め（Amazon SNS Developer Guide「Managing Amazon SNS encryption keys and costs」の、SSE の Topic へ送る主体の policy の例）、Topic の暗号化の手順の Key Policy の例は `kms:Decrypt` と `kms:GenerateDataKey` を名指す（同「Setting up Amazon SNS topic encryption with server-side encryption」）。boundary は部分 wildcard を使わず（決定1）、この2つを列挙する。repository-wide/ADR-0301 決定12 の「暗号操作を IAM policy で与えない」を、boundary は上限を置くだけで権限を与えないと読み、これはそれに反しないとする。KMS は、Key Policy がアカウントへ委任しない暗号操作に IAM の Allow を効かせず、`modules/kms` は暗号操作を委任しないので、boundary があっても Key Policy に名指されない主体は鍵を使えない。Policy Test の `PLAN-IAM-04`（IAM の Allow の暗号操作の禁止）は、宣言した boundary の文書の、`kms:ViaService` の条件を持つ文だけを外す。 repository-wide/ADR-0207 決定11 の記録として: 外れる対象は repository-wide/ADR-0301 決定12 の字義（IAM policy の文書に暗号操作の Allow を書かない）である。理由は上のとおりで、影響は次のとおりである。security: boundary の文書に暗号操作の Allow が現れ、`PLAN-IAM-04` に除外ができる。実効の暗号操作は、Key Policy が名指す主体に限られる。availability: これを置かないと、心拍の publish が暗号化で失敗する。cost: 無い。代替案と採らない理由: (a) Key Policy が role の session の ARN を名指す。session の ARN は Scheduler が assume するたびに決まり、前もって書けない。(b) 心拍の role に boundary を付けない。決定14 の、作るすべての role に boundary を付けることが崩れる。(c) KMS の grant で許す。`kms:CreateGrant` は repository-wide/ADR-0301 決定12 が IAM で与えることを禁じ、使う主体を Key Policy の1箇所に揃える性質も崩れる。(d) Topic を暗号化しないか、AWS managed key で暗号化する。`modules/sns` の暗号化と、CloudWatch・EventBridge などの送り手が AWS managed key の Topic へ送れないことに反する。見直し条件: `PLAN-IAM-04` の除外を、`kms:ViaService` で限った文の外へ広げる必要が出たとき。boundary に SNS のほかの `kms:ViaService` の暗号操作が要るとき。AWS が、permissions boundary と role の ARN を名指す resource-based policy の評価を変えたとき。
17. apply の role の workload の Allow（決定13・14 の読み取りと管理）は、3つの customer managed policy に置き、apply の role に付ける。決定13 の管理（作成・変更・付け外し）のうち、account-baseline の分は `<project>-<env>-ci-apply-workload-2` に、ほかは `<project>-<env>-ci-apply-workload` に置き、読み取りは `<project>-<env>-ci-apply-workload-read` に置く。1つの policy は 6,144 文字が上限で、provider の region と us-east-1 の2つの ARN を並べると、入力の境界で1つに収まらないからである。管理を2つに分けるのは、account-baseline の管理を足すと `-ci-apply-workload` が 6,144 文字を超えるからである（決定21）。plan の role には、読み取りの policy を同じものとして付け、plan の role の inline policy に workload の読み取りを置かない。plan の role の inline policy は、workload の読み取りを足すと入力の境界で 10,240 文字を超えるからである。決定13 の `DenyBaselineOutsideRegions` は plan の role の inline policy に置く。apply の role の inline policy には、state の読み書き（決定12 まで）と、決定5・13・14 の Deny を残す。inline に workload の Allow を置くと、入力の境界で 10,240 文字を超えるからである。3つの policy は apply-identity の role が作り、その作成・読み取り・版の更新・削除と、apply の role への付け外し（`iam:AttachRolePolicy`、Resource を apply の role の ARN に、条件 `iam:PolicyARN` を3つの policy の ARN に限る）と、plan の role への読み取りの policy の付け外し（Resource を plan の role の ARN に、条件 `iam:PolicyARN` を読み取りの policy の ARN に限る）を inline policy で与える（決定7 の統制の policy と同じ形）。apply の role へは policy ごとの `aws_iam_role_policy_attachment` で3つの policy を付け、plan の role へは読み取りの policy を同じ形で付ける。`aws_iam_role_policy_attachments_exclusive` には、apply の role では3つの policy の ARN だけを、plan の role では読み取りの policy の ARN だけを載せる。どれかが 6,144 文字を超えるときは、同じ役割の customer managed policy を足して伸ばし、この決定の名前を改める。
18. apply の role に、`aws_kms_key`・`aws_kms_key_policy`・`aws_sns_topic` の削除（`kms:ScheduleKeyDeletion`、`sns:DeleteTopic`）を与えない。これらは `plan.stateful_protection` の保護の型であり、決定3 の「権限の側でも止める」と同じ扱いにする。Scheduler・Chatbot の構成・alias・IAM の role と policy・予算・anomaly monitor と subscription の削除は与える。置換と、usecase から外す変更に要るからである。sandbox の apply と destroy の経路（repository-wide/ADR-0601 決定3・4）が鍵と Topic の削除を要するときは、その経路の role で与え、apply の role には足さない。
19. Chatbot の構成の作成で、apply の role に `sns:Subscribe` を与えない。Topic への購読は Chatbot の service-linked role（`AWSServiceRoleForAWSChatbot`）が自分の権限で作る（Chatbot Administrator Guide「Service-linked role for performing operations on Amazon SNS topics and CloudWatch Logs」）。Service Authorization Reference も、`CreateSlackChannelConfiguration` の依存に `sns:Subscribe` を挙げない。
20. plan と apply の role に、`aws-portal:ViewBilling`・`aws-portal:ModifyBilling` を与えない。Service Authorization Reference の Budgets の頁は、API と Action の対応の表で、Budgets の各 API に `budgets:` の Action と並べて `aws-portal:ViewBilling`（読み）か `aws-portal:ModifyBilling`（書き）を挙げる。一方、AWS Billing User Guide と AWS Cost Management User Guide の「Migrating access control」の頁は、`aws-portal` の名前空間が 2023年7月に標準サポートを終えたこと、2023年3月6日 11:00（PDT）以降に作った AWS Organizations の組織では細粒度の Action が既に有効であること、Budgets と Cost Explorer の API の呼び出しはこの移行の影響を受けないこと（"API access to AWS Cost Explorer, AWS Cost and Usage Reports, and AWS Budgets remains unaffected."）を述べる。`aws-portal:ModifyBilling` は resource-level 権限を持たず、旧来の Action の評価が残る組織では、請求の設定の変更に届く。 repository-wide/ADR-0207 決定11 の記録として: 外れる対象は、Service Authorization Reference の Budgets の API の表が挙げる `aws-portal:ViewBilling`・`aws-portal:ModifyBilling` である。理由は上のとおりである。ユースケース上の制約は、組織を `organization-baseline` が段4 の apply で作り、既に組織を持つ管理アカウントを unsupported とすること（`docs/setup/organization-baseline.md` の 3.1。組織が無いことは段2 と段4 の `make bootstrap-verify STAGE=before-apply` が確かめる）で、組織は 2023年3月6日 より後に作られる。影響は次のとおりである。security: CI の role の権限が請求の設定へ広がらない。availability: Budgets の API が `aws-portal` を今も評価するなら、finops を置く env の CI の plan と apply が Budgets の呼び出しで AccessDenied になる。cost: 無い。代替案と採らない理由: (a) `aws-portal:ViewBilling` を plan と apply の role に、`aws-portal:ModifyBilling` を apply の role に、Resource `"*"` の別の文で与える。旧来の評価が残る組織では、apply の role の権限が請求の設定の書き込みへ広がる。(b) `aws-portal:ViewBilling` だけを与える。書きの側の失敗が残る。見直し条件: finops を置く env の CI の plan か apply が、Budgets の API で `aws-portal` の Action を名指す AccessDenied で失敗したとき。Service Authorization Reference の Budgets の表から `aws-portal` が消えたとき。組織が細粒度の Action に移っていないと分かったとき（確かめ方は `docs/setup/organization-baseline.md` の 3.2）。
21. CI の role の inline policy には、その role が自分を保つのに要る権限（核）だけを置き、ほかの権限は役割ごとの customer managed policy に置く。apply-identity の role の核は、identity root の state の key と lock file の読み書き、plan の出力の Bucket の `apply/*` への書き込み（決定10）、5つの role の管理（決定4）、CI の customer managed policy の作成・読み取り・版の更新・削除とその付け外し（決定7・15・17 とこの決定）、identity root の構成物の読み取り（統制の構成物とアカウントの前提の構成物の読み取りを含む。決定3）、決定1 の Deny である。核を外の policy に置くと、その policy が壊れたとき、それを直す apply が refresh か policy の作成と付与で失敗し、CI では直せなくなるからである。apply-identity の role のほかの書き込み（3つの Bucket の設定、apply の出力の Bucket の作成、OIDC provider の管理、state の鍵の rotation と Key Policy の設定、アカウントの前提の構成物の作成と description の更新（決定3））は `<project>-<env>-ci-apply-identity-manage` に置き、env によらず apply-identity の role に付ける。env によらず付けるのは、同じ文の置き場所を env で変えないためである。置き場所が env で違うと、ある文が核かどうかが env で変わり、文書の形とテストと段2 の plan の期待値が env ごとに分かれる。統制の構成物の作成と設定は決定7 の統制の policy に置く。inline policy は role あたり 10,240 文字、customer managed policy は1つ 6,144 文字（どちらも空白を除く）が上限で（IAM User Guide「IAM and STS quotas」）、管理アカウントの apply-identity の role の inline policy は、核の外の書き込みを置いたままでは、入力の境界で権限を足す余地が無かったからである。 1つの policy が入力の境界で上限の 90% を超えるときは、inline policy なら核を見直し、customer managed policy なら同じ役割の policy を足す（名前の末尾に `-2` から番号を付け、この決定と決定7・17 の名前を改める）。role に付ける managed policy の数は、IAM の既定のクォータ（role あたり 20）の半分を超えない。 apply-identity の role が作る customer managed policy を足す変更は2つに分ける。先の変更は、その ARN を作成・読み取り・版の更新・削除の Resource と付与の条件 `iam:PolicyARN` に足すだけとし、`admin` へ昇格して apply する。後の変更がその policy を作って付ける（影響の項）。apply-identity の role に付き、inline policy から文を受け取る policy は、inline policy の書き込みに依存させない（inline policy がその付与に依存するので、依存が循環する）。その作成と付与の権限は、先の変更の apply で inline policy に入っている。inline policy の書き込みはその policy の `aws_iam_role_policy_attachment` に依存させ、付けてから inline policy から外す。移した Action は、移す変更の apply の中では使わない（移す変更はほかの変更を含めない）。ほかの CI の customer managed policy（決定7 の統制の policy、決定15・17 の policy）は、inline policy の書き込みに依存させる。

## 検討した代替案

### 案A: 5つの role 自身に permissions boundary を課し、Allow を広く与える

5つの role の権限は Action の列挙で閉じており、boundary を重ねても上限は変わらない。boundary の内側の Allow を広く与えると、repository-wide/ADR-0301 決定8 の Action wildcard に当たる。apply の role が作る role に課す boundary は決定14・15 が持つ。

### 案B: AWS managed policy（`ReadOnlyAccess` 等）を plan の role に付ける

plan の role は Pull Request の作者が任意のコードで使える資格情報であり、アカウントの全 resource を読める。repository-wide/ADR-0301 決定10 に反する。

### 案C: 後から足す構成物の権限を、まとめて先に入れる

構成物の形が決まる前は正しく列挙できず、使わない権限を先に与えることになる。鍵の権限は、鍵の形（`modules/kms`）から Provider が呼ぶ API を列挙できるので、鍵を作る変更と同じか、それより前に入れる（決定3）。

### 案D: 作る role を完全な ARN に限り、permissions boundary を課さない

作る role の ARN と、それに付ける policy の ARN を、usecase の名前から組んで列挙する。role を作る usecase を足すたびにこの ADR の書き換えを要し、`iam:PutRolePolicy` で書く文書の中身は IAM の条件で限れないので、作った role を経由した bootstrap の構成物への到達は Policy Test でしか止まらない。

### 案E: boundary の Allow を AWS の例のようにサービスの wildcard で書く

文書が短く、usecase を足しても伸びにくい。repository-wide/ADR-0301 決定8 の例外を要し、作る role の inline policy が上限まで広がりうる。

### 案F: workload の構成物の Resource を usecase ごとの完全な ARN にする

最も狭い。usecase の構成物の名前を変える変更が、そのたびにこの ADR の書き換えを要する。

### 案G: permissions boundary を1つにする

boundary は role に1つしか付かず、文書は 6,144 文字が上限である。Deny の文を共有すると、入力の境界で Allow に使える文字が少なく、role を作る2つ目の usecase で上限を超える。

## 影響

- identity root に構成物を足す変更と、管理アカウントに workload の usecase を足す変更は、この policy を広げる変更と、その権限を使う変更を、同じ Pull Request・同じ昇格に入れてよい。CI の role を足す変更は、決定4 の順序により1回の apply に収まる。そのほかは権限の変更と resource の間に依存が無いので、IAM の反映の遅れで初回の apply が AccessDenied で落ちうる。そのときは失敗した job を走らせ直す（見分け方は `docs/setup/bootstrap.md` の「段5 の CI の apply が失敗した」）。権限と resource を別の昇格に分けると、レビューと昇格が2回になる
- inline policy は role あたり 10,240 文字、customer managed policy は1つ 6,144 文字（どちらも空白を除く）が上限である。入力の境界での長さは、`permissions.tftest.hcl` の `policy_length`（`admin`）と `policy_length_outside_admin`（`admin` 以外）が上限以下であることを固定する。boundary（決定15）、apply の role の workload の2つの policy（決定17）、統制の policy（決定7）と決定21 の policy も同じ run で測る。宣言（`customer_managed_policies`）の policy がすべて測られることは、Policy Test（`PLAN-CMP-*`）と Unit Test が見る。us-east-1 と Chatbot の service-linked role の文（決定3）は aws の partition にだけ置くので、aws の最長の region と us-east-1 を並べた形を `policy_length_aws`・`policy_length_outside_admin_aws` で測る。policy によっては aws の run の方が長い。上限と 90% の見直し条件は、4つの run の最大で見る
- IAM の role を作る workload root の usecase は、出力 `permissions_boundary_arns`のうち自分の名前の boundary の ARN を入力で受け、作るすべての role に付ける。対象は `ops-notification`（入力 `permissions_boundary_arn`）と、以後 role を作る usecase のすべて（`modules/vpc` の flow logs の role を使う `network-foundation` を含む）。boundary の中身はこの usecase（identity root）が持ち、role を作る usecase は決めない。role を作る usecase を足す変更は、その usecase の boundary を足す変更（この ADR の書き換え）を先に merge して apply する。入力は policy の文書ではなく、この usecase が持つ1つの policy の ARN であり、repository-wide/ADR-0204 決定2 の、意味が AWS の表現に依存する入力ではない
- workload root は、boundary の ARN を identity root の state から読めない（決定5 の `DenyIdentityStateChange`）。env の root が、名前から組んだ ARN を usecase に渡す
- 決定15・17・21 の policy を作って付ける変更は、それを作る権限（apply-identity の inline policy）を入れる変更と同じ昇格でよい。IAM の反映の遅れで1回目の apply が落ちたら、項目1 と同じく走らせ直す
- apply-identity の inline policy から決定21 の policy へ文を移す変更は、1回の apply で、policy の作成、付与、inline policy の縮小の順に進む（決定21 の依存）。途中で失敗しても、付与より前に inline policy から文は消えず、再実行で収束する。
- 管理アカウントの workload root に `finops` を置く変更は、`docs/setup/bootstrap.md` の 2-4 の tag を付けてから apply する。tag が無いと、apply の role は bootstrap の前提の AWS services monitor とその subscription を変更・削除でき、その plan は Pull Request のレビューでしか止まらない

## 見直し条件

- AWS Provider の版を上げるとき
- CI の role の policy（inline policy、boundary、決定7・17・21 の policy）のどれかが、入力の境界で上限の 90%（inline policy は 9,216 文字、customer managed policy は 5,529 文字）を超える変更を入れるとき（決定21。boundary は共有の Deny を短い形にするか、usecase の中で boundary を分けるかを決める）
- apply の role の workload の3つの policy のどれかが 6,144 文字を超えるとき（決定17 のとおり policy を足す。role に付けられる managed policy の数のクォータを確かめる）
- workload root の Provider の版が identity root と違うとき（決定2 の版を root ごとに書く）
- Scheduler・Chatbot が `iam:AssociatedResourceArn` を入れることが確かめられたとき（`iam:PassRole` をその条件で限る）
- CI の plan か apply が AccessDenied で失敗したとき
- `modules/kms` が Key Policy でアカウントへ委任する Action を変えるとき（決定5 の鍵の Deny の列挙を合わせる）
- state の鍵の作成の権限を足すとき（鍵の種類 `kms:KeySpec`・`kms:KeyUsage`、多リージョン `kms:MultiRegion`、鍵素材 `kms:KeyOrigin` を限る条件と、`resource_wildcard_actions` への `kms:CreateKey` の追加を併せて決める。決定13 の workload の鍵の条件と揃える）
- bootstrap の構成物に、resource type を持たない Action で設定を変えられる型が入るとき（apply の role に Resource `"*"` の Deny を足すかを決める）
- AWS が、Cost Anomaly Detection の monitor か subscription の ARN に名前を含めるか、tag のほかの条件キーを足したとき（決定13 の Resource と Deny を見直す）
- Budgets の API が `aws-portal` の Action を要すると分かったとき（決定20）
- Service Authorization Reference の IAM Identity Center の頁に、決定5 の `sso:` の wildcard に当たる Action が足されたとき
